Optimize TypeScript Monorepo Compilation

TypeScript project references significantly reduce build times and enhance developer velocity in monorepos by breaking monolithic codebases into smaller, independently compiled units. Instead of treating an entire repository as a single giant program, project references allow individual packages to reference one another cleanly, enabling the compiler to perform incremental compilation, cache build outputs, and skip recompiling unchanged code. This article explains how project references work under the hood to accelerate compilation, reduce memory consumption, and enforce modular code architecture.

The Bottleneck of Monolithic Compilation

In a standard monorepo setup without project references, the TypeScript compiler (tsc) often analyzes every source file across all packages within a single execution context. As the codebase grows, this approach faces severe limitations:

  • Excessive Memory Usage: The compiler must hold Abstract Syntax Trees (ASTs) and symbol tables for the entire repository in memory simultaneously.
  • Redundant Work: Modifying a single file in a leaf package often triggers a full re-evaluation of downstream packages, even if the public-facing types of the modified package have not changed.
  • Lack of Boundaries: Without explicit compilation boundaries, packages can inadvertently introduce circular dependencies or import private, internal implementation details of neighboring packages.

How Project References Solve the Problem

Project references address these issues by introducing an explicit dependency graph between multiple tsconfig.json files. Using the references property, a project defines which other projects it depends on.

{
  "compilerOptions": {
    "composite": true,
    "declaration": true
  },
  "references": [
    { "path": "../core" },
    { "path": "../utils" }
  ]
}

This configuration fundamentally changes how the TypeScript compiler processes the repository.

1. Enabling composite and .d.ts Boundaries

When using project references, upstream projects must enable the composite setting. This setting enforces several rules:

  • Declaration files (.d.ts) must be generated alongside JavaScript outputs.
  • Incremental build tracking is strictly enabled via .tsbuildinfo files.
  • File inputs must be explicitly tracked without overlapping with other projects.

Because declaration files are generated for each project, dependent packages compile against these lightweight .d.ts contracts instead of the upstream package's raw TypeScript source code. If an implementation file inside a package changes without modifying exported types, dependent packages do not need to be rechecked or recompiled.

2. Smart Rebuilds with tsc --build

Project references leverage the --build (or -b) CLI flag, which transforms tsc into an intelligent build orchestrator. When executing tsc --build:

  • Dependency Topological Sorting: TypeScript analyzes all referenced configurations and builds them in the correct dependency order.
  • Timestamp and Hash Tracking: The compiler checks .tsbuildinfo files to determine whether a project's inputs or outputs have changed. If a package and its dependencies are up to date, TypeScript skips compilation entirely.
  • Up-to-Date Checking: Upstream builds are verified instantly, eliminating repeated type-checking passes across stable parts of the codebase.

3. Lower Memory Footprint and Parallel Execution

By isolating packages into separate compilation tasks, TypeScript avoids constructing a massive, single-program AST. Memory is reclaimed as individual projects finish compiling. Furthermore, build orchestrators such as Turborepo, Nx, or Wireit can leverage the explicit dependency graph defined by project references to execute package builds in parallel across multiple CPU cores.

4. Enforcement of Architecture and Anti-Cycle Guarantees

Project references enforce strict acyclic dependency structures. If two packages reference each other directly or indirectly, the compiler immediately issues an error. This prevents architectural decay over time and ensures that the codebase remains modular, predictable, and maintainable.
