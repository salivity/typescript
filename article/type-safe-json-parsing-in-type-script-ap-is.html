Type-Safe JSON Parsing in TypeScript APIs

TypeScript cannot guarantee type safety during JSON parsing on its own because JSON.parse() operates at runtime, while TypeScript’s type checking occurs strictly at compile time. By default, JSON.parse() returns any, bypassing the compiler's safety mechanisms. To achieve genuine type safety when consuming API responses, developers must combine TypeScript's static type system with runtime validation strategies, such as type assertions, custom type guards, or schema validation libraries.

The Problem with Native JSON.parse

When fetching data from an external API, the response payload is unknown until runtime. The standard JavaScript JSON.parse() method returns any:

const response = await fetch("https://api.example.com/user");
const data = JSON.parse(await response.text()); // Type of data is 'any'

Because any disables TypeScript's type checking, accessing non-existent properties will not trigger compile-time errors, risking unexpected runtime crashes.

Method 1: Type Assertions (Compile-Time Only)

A common but fragile approach is casting the parsed result using a type assertion (as Type):

interface User {
  id: string;
  name: string;
}

const data = JSON.parse(jsonString) as User;
console.log(data.name);

While this informs the compiler to treat data as a User, it performs no checks at runtime. If the API returns an unexpected structure, the assertion creates a false sense of safety.

Method 2: The unknown Type and Custom Type Guards

A safer native approach is typing the parsed output as unknown and verifying its shape using TypeScript type guards. The unknown type forces developers to inspect the data before performing operations on it.

interface User {
  id: string;
  name: string;
}

function isUser(obj: unknown): obj is User {
  return (
    typeof obj === "object" &&
    obj !== null &&
    "id" in obj &&
    typeof (obj as User).id === "string" &&
    "name" in obj &&
    typeof (obj as User).name === "string"
  );
}

const rawData: unknown = JSON.parse(jsonString);

if (isUser(rawData)) {
  // rawData is safely typed as User here
  console.log(rawData.name);
} else {
  throw new Error("Invalid API response structure");
}

Type guards validate properties at runtime. Once the conditional check passes, TypeScript narrows the type from unknown to User.

Method 3: Schema Validation Libraries (Recommended)

Writing manual type guards for complex API payloads is verbose and error-prone. The modern industry standard is using runtime validation libraries such as Zod, Yup, or Valibot. These libraries parse unknown data at runtime and automatically infer static TypeScript types from the schema.

import { z } from "zod";

// Define the runtime schema
const UserSchema = z.object({
  id: z.string(),
  name: z.string(),
  email: z.string().email().optional(),
});

// Infer the TypeScript type from the schema
type User = z.infer<typeof UserSchema>;

// Validate the payload
try {
  const rawData: unknown = JSON.parse(jsonString);
  const user: User = UserSchema.parse(rawData);
  
  // user is guaranteed to match the User interface
  console.log(user.name);
} catch (error) {
  console.error("Validation failed:", error);
}

Using this pattern, the application fails safely at the network boundary if the API contract changes, ensuring that all downstream code operates with fully validated, type-safe data.
