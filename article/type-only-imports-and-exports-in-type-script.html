Type-Only Imports and Exports in TypeScript

This article provides an overview of type-only imports and exports in TypeScript, explaining what they are, how their syntax works, and why they were introduced. You will learn how this feature resolves compilation ambiguities for single-file transpilers like Babel, eliminates accidental runtime side effects, and helps developers maintain clean and predictable compiled JavaScript code.

What Are Type-Only Imports and Exports?

Type-only imports and exports, introduced in TypeScript 3.8, allow developers to explicitly state that an imported or exported item is strictly used for type checking and should never be emitted into the final JavaScript output.

Before this feature, TypeScript used heuristic analysis to determine whether an import was used purely as a type. If an import was only used in type positions (such as type annotations or interfaces), the TypeScript compiler automatically omitted it from the emitted JavaScript.

With type-only syntax, you use the type keyword directly in the import or export statement:

// Type-only import
import type { User, Credentials } from './models';

// Type-only export
export type { User };

TypeScript 4.5 expanded this feature by introducing inline type qualifiers, allowing you to mix values and types in a single import statement:

// Inline type-only import
import { loginUser, type AuthToken } from './auth';

Why Were They Introduced?

1. Compatibility with Single-File Transpilers

Modern build tools like Babel, esbuild, and SWC transpile TypeScript files into JavaScript on a file-by-file basis without running the full TypeScript type checker. This isolated approach makes builds significantly faster, but it creates an ambiguity problem.

When a single-file transpiler encounters:

import { SomeIdentifier } from './module';

It cannot determine whether SomeIdentifier is a JavaScript value (like a class or const) or a TypeScript-only construct (like an interface or type alias). If SomeIdentifier is only a type, emitting the import into JavaScript causes a runtime error because the module might not export anything by that name at runtime.

Using import type guarantees that transpilers can safely drop the import statement entirely without needing to resolve the imported file. This behavior is reinforced by setting "isolatedModules": true in tsconfig.json.

2. Eliminating Unintended Runtime Side Effects

When an import statement is preserved in compiled JavaScript, the imported file is loaded and executed at runtime. If an imported file contains side effects—such as initializing a database connection, reading configuration files, or logging—a standard import could trigger this code unexpectedly.

By using import type, the compiler guarantees that the import will be completely stripped from the emitted JavaScript. This guarantees that the target file is not loaded at runtime simply because a type was needed during development.

3. Resolving Circular Dependencies

Circular dependencies between types are common and usually harmless in TypeScript because types disappear at runtime. However, if those circular dependencies cause runtime import statements to be generated, they can lead to undefined module evaluations or circular dependency errors in JavaScript. Type-only imports break these runtime loops by ensuring that only actual runtime dependencies are evaluated.
