TypeScript Composite Mode and Project References

This article explains TypeScript's composite project mode and why it is an essential requirement when configuring project references. You will learn what enabling the composite compiler flag does under the hood, how it enables fast and incremental builds in multi-package repositories, and the specific structural guarantees TypeScript demands to make project references function reliably.

What Is Composite Project Mode?

Composite project mode is a setting in TypeScript enabled by setting "composite": true in a project's tsconfig.json. It informs the TypeScript compiler (tsc) that the project is a modular piece of a larger codebase—such as a monorepo or a multi-tier application—and can be referenced by other TypeScript projects.

When you enable composite: true, TypeScript automatically enforces several settings:

  • Declaration Emit ("declaration": true): The project must generate type declaration files (.d.ts).
  • Declaration Maps ("declarationMap": true recommended): Generates source maps for declarations to enable "Go to Definition" navigation across project boundaries in IDEs.
  • Build Info (.tsbuildinfo): Automatically enables incremental compilation metadata so TypeScript can determine if an output is up-to-date without rechecking all source files.

Why Composite Mode Is Required for Project References

TypeScript introduced project references to allow developers to split large codebases into smaller, independently compiled units. To link these units using the "references" array in tsconfig.json, any referenced project must have "composite": true.

TypeScript strictly enforces this requirement for three main reasons:

1. Separate and Fast Compilation via Type Definitions

When Project B references Project A, TypeScript does not parse and type-check the raw .ts source files of Project A when compiling Project B. Instead, it relies exclusively on the emitted .d.ts declaration files of Project A.

Composite mode mandates declaration file generation. This separation allows tsc to verify Project B against Project A's public API surface without having to re-evaluate Project A's internal implementation details, significantly reducing memory usage and compile times.

2. Reliable Incremental Builds (tsc --build)

Project references are designed to work with the build orchestrator flag: tsc --build (or tsc -b). For the build tool to decide whether a project needs recompilation or can be skipped, it requires persistent state tracking.

Composite mode guarantees that a .tsbuildinfo file is created. This file tracks file hashes, configuration options, and dependency graphs. Without composite: true, TypeScript cannot reliably determine the freshness of build artifacts across multiple project boundaries.

3. Enforcing Project Isolation and Boundaries

In a standard TypeScript project, loose path mapping and relative imports can inadvertently introduce circular dependencies or cause files to be compiled into multiple output bundles.

Composite mode imposes strict structural constraints:

  • Explicit Inputs and Outputs: Every source file in a composite project must be accounted for within its own rootDir and outDir.
  • No Leaking Source Code: A project cannot silently pull in untracked source files from another project; everything cross-project must flow through explicit references and pre-built declarations.
  • Prohibition of Circular References: Project reference graphs must be directed acyclic graphs (DAGs). Composite mode helps the build orchestrator validate this topology before running.

Minimal Configuration Example

To configure a library as a composite project, set up its tsconfig.json as follows:

{
  "compilerOptions": {
    "composite": true,
    "declaration": true,
    "declarationMap": true,
    "outDir": "./dist",
    "rootDir": "./src"
  },
  "include": ["src/**/*"]
}

A consuming project can then reference it cleanly:

{
  "compilerOptions": {
    "outDir": "./dist",
    "rootDir": "./src"
  },
  "references": [
    { "path": "../shared-library" }
  ],
  "include": ["src/**/*"]
}

Running tsc --build from the root directory will automatically build the shared library first, generate its declaration artifacts, and then compile the consumer using those pre-built definitions.
