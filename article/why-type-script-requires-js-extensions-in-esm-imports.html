Why TypeScript Requires .js Extensions in ESM Imports

When configuring TypeScript to target modern ECMAScript Modules (ESM), developers are often surprised to find they must use .js extensions in their import paths—even when importing .ts files. This requirement stems from TypeScript's core architectural decision not to rewrite module specifiers, combined with the strict resolution algorithms of native ECMAScript and Node.js module loaders. This guide explains why this rule exists, how the TypeScript compiler handles it under the hood, and how to manage it across different module configurations.

TypeScript's Non-Goal: Specifier Rewriting

The primary reason for this behavior is a fundamental design principle of the TypeScript compiler: TypeScript does not rewrite import or export specifiers.

When you write an import statement such as:

import { add } from "./math.js";

TypeScript emits that specifier identically into the compiled JavaScript:

import { add } from "./math.js";

If TypeScript allowed you to write import { add } from "./math.ts", it would compile to import { add } from "./math.ts". In a standard JavaScript runtime like Node.js or a modern web browser, attempting to execute code importing a .ts file directly will fail with a module resolution error because runtime environments only evaluate JavaScript files.

TypeScript intentionally avoids translating ./math or ./math.ts into ./math.js during compilation because doing so would require deep, contextual knowledge of the runtime environment, the file system, build plugins, and how external bundlers or loaders interpret paths. To avoid generating unexpected output, TypeScript leaves paths untouched.

Native ECMAScript Modules Require Explicit Paths

In traditional CommonJS (require("./math")) and legacy bundler setups, the module resolver performed implicit lookup. If a file extension was missing, the resolver would probe the file system, checking for ./math.js, ./math.json, or ./math/index.js.

Native ESM in browsers and modern Node.js (via "type": "module") abandoned this automatic file extension probing. Under the native ECMAScript specification:

  • Relative module specifiers must be fully specified URLs or path references.
  • Specifiers must include the exact runtime file extension (.js, .mjs, etc.).
  • Directory imports (such as omitting /index.js) are not supported by default.

Because native Node.js ESM demands explicit extensions to resolve files, and because TypeScript outputs files with .js extensions, your source code must explicitly reference the eventual runtime extension: .js.

How TypeScript Maps .js to .ts at Compile Time

When you use modern resolution settings—specifically "moduleResolution": "node16" or "moduleResolution": "nodenext" in tsconfig.json—the TypeScript compiler is aware of Node's ESM resolution requirements.

When it encounters:

import { utility } from "./utility.js";

TypeScript's internal resolver performs a reverse lookup:

  1. It sees the reference to ./utility.js.
  2. It looks on the disk for ./utility.ts, ./utility.tsx, or ./utility.d.ts in the same directory.
  3. If found, it uses the TypeScript source file for type checking and IntelliSense, while preserving ./utility.js in the compiled emission.

Bundlers vs. Native Node.js

The requirement to write .js extensions depends on your moduleResolution setting in tsconfig.json:

  • Node16 / NodeNext: Enforces strict Node.js ESM rules. You must provide .js (or .mjs / .cjs) extensions on relative paths.
  • Bundler: Designed for tools like Vite, Webpack, or esbuild. Because these bundlers handle extension resolution and file packing at build time, you can omit the .js extension without TypeScript raising an error, provided "moduleResolution": "bundler" is enabled.

In short, requiring .js extensions allows TypeScript to align directly with web standards and Node.js ESM mechanics without introducing specifier-rewriting side effects during compilation.
