Stage 3 Decorators in Modern TypeScript

TypeScript 5.0 officially adopted the ECMAScript Stage 3 decorators standard, marking a major transition away from the decade-old experimental implementation. This article explores how native Stage 3 decorators integrate into modern TypeScript projects, detailing the new runtime API, structural type checking, the introduction of auto-accessors, and how configuration requirements differ from legacy decorators.

The Standardized Decorator Architecture

Unlike legacy decorators, which relied on the non-standard experimentalDecorators flag and optional metadata emission, Stage 3 decorators conform to the official TC39 specification. Modern TypeScript enables these by default when compiling with TypeScript 5.0 or later, provided experimentalDecorators is set to false or omitted in tsconfig.json.

In the Stage 3 design, a decorator is a function applied to a class definition or a class element (methods, getters, setters, fields, or auto-accessors). Every decorator function receives two arguments:

  1. target: The entity being decorated (e.g., the method function, class constructor, or undefined for fields).
  2. context: A context object containing structured metadata about the decorated member.

The context object provides a standardized DecoratorContext type in TypeScript with the following properties:

  • kind: Indicates the type of member ("class", "method", "getter", "setter", "field", or "accessor").
  • name: The name of the member (string or symbol).
  • static: A boolean indicating if the member is static.
  • private: A boolean indicating if the member is private (#field).
  • access: An object containing get and set methods to dynamically read or write the member's value.
  • addInitializer: A hook allowing code to run during class definition or instance construction.

Method and Member Decorators

Method decorators receive the original function and can return a replacement function that alters execution. TypeScript enforces strict type checking between the original method's signature and the returned function.

function logged<This, Args extends any[], Return>(
  target: (this: This, ...args: Args) => Return,
  context: ClassMethodDecoratorContext<This, (this: This, ...args: Args) => Return>
) {
  return function (this: This, ...args: Args): Return {
    console.log(`Calling ${String(context.name)}`);
    return target.apply(this, args);
  };
}

class UserService {
  @logged
  fetchUser(id: string): string {
    return `User: ${id}`;
  }
}

The ClassMethodDecoratorContext generic parameters ensure that this scoping and function parameters remain strictly typed.

Auto-Accessors

Stage 3 introduces a new class member syntax: the accessor keyword. Auto-accessors define a private storage slot with implicit getter and setter methods. Decorating an auto-accessor allows interception of both read and write operations.

function loggedAccessor<This, Value>(
  target: ClassAccessorDecoratorTarget<This, Value>,
  context: ClassAccessorDecoratorContext<This, Value>
): ClassAccessorDecoratorResult<This, Value> {
  return {
    get(this: This): Value {
      console.log(`Getting ${String(context.name)}`);
      return target.get.call(this);
    },
    set(this: This, value: Value): void {
      console.log(`Setting ${String(context.name)} to`, value);
      target.set.call(this, value);
    },
    init(initialValue: Value): Value {
      return initialValue;
    }
  };
}

class Account {
  @loggedAccessor
  accessor balance = 0;
}

Field Decorators and Initializers

Field decorators do not receive the field's value at runtime because field initialization occurs during instantiation. Instead, the target parameter is undefined, and the decorator can return an initialization function that transforms the initial value when the instance is created.

function bound<This, Args extends any[], Return>(
  target: undefined,
  context: ClassFieldDecoratorContext<This, (...args: Args) => Return>
) {
  context.addInitializer(function (this: any) {
    this[context.name] = this[context.name].bind(this);
  });
}

Key Differences from Legacy Decorators

Integrating Stage 3 decorators requires addressing several divergences from the old experimental model:

  • Parameter Decorators: Stage 3 does not support method parameter decorators. Frameworks that relied on parameter injection must adapt using method-level configuration or alternative patterns.
  • Metadata Reflection: The legacy emitDecoratorMetadata option is incompatible with Stage 3 decorators. Metadata is instead addressed by a companion proposal (Decorator Metadata), natively supported in TypeScript 5.2+ via context.metadata.
  • Execution Order: Decorators execute inside-out for expressions, but the application order runs: member decorators first (grouped by type and definition order), followed by class decorators. Initializers run at construction time.

By aligning with the ECMAScript standard, TypeScript enables portable, type-safe metaprogramming without requiring proprietary compilation flags or non-standard runtime dependencies.
