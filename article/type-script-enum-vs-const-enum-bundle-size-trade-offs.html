TypeScript Enum vs Const Enum Bundle Size Trade-Offs

TypeScript developers often weigh standard enums against const enums to optimize application performance and output size. Standard enums generate runtime JavaScript objects that prevent efficient dead-code elimination, directly inflating bundle sizes. In contrast, const enums completely remove runtime object overhead by inlining values at compile time. While const enums yield smaller initial payloads, they introduce distinct build tool constraints, code duplication risks, and compatibility trade-offs that can inadvertently affect production codebases.

Standard Enums: Runtime Overhead and Tree-Shaking Issues

Standard enums in TypeScript generate an immediately invoked function expression (IIFE) and a lookup object in the compiled JavaScript. For numeric enums, TypeScript also generates a reverse mapping from value to name.

// TypeScript
enum Status {
  Active,
  Inactive,
}

// Compiled JavaScript Output
var Status;
(function (Status) {
    Status[Status["Active"] = 0] = "Active";
    Status[Status["Inactive"] = 1] = "Inactive";
})(Status || (Status = {}));

This implementation has significant bundle size consequences:

  1. Prevented Tree-Shaking: Modern bundlers like Rollup, Webpack, and esbuild struggle to reliably tree-shake IIFEs because they are treated as potential side effects. Even if you only import a single member, the entire enum object remains in the bundle.
  2. Reverse Mapping Overhead: Generating both forward and reverse lookups doubles the number of keys assigned to the object, adding unnecessary bytes to production builds.

Const Enums: Zero-Cost Declarations and Inlining

Const enums omit runtime object generation entirely. Instead, the TypeScript compiler replaces every occurrence of the enum member directly with its literal value at the call site.

// TypeScript
const enum Status {
  Active = "ACTIVE",
  Inactive = "INACTIVE",
}

const current = Status.Active;

// Compiled JavaScript Output
const current = "ACTIVE";

Because the declaration produces zero JavaScript, the initial footprint of the enum definition is completely eliminated. When an enum member is never used, it adds no bytes to the final bundle, solving the tree-shaking limitations of standard enums.

The Hidden Trade-Offs of Const Enums

Despite their immediate bundle-size advantages, const enums carry critical technical trade-offs:

  • Code Repetition vs. Object Allocation: Inlining long string enum values across hundreds of call sites duplicates those strings throughout your bundle. While gzip handles repeated strings well, the uncompressed file size and JavaScript parsing time in the browser increase. A single shared runtime object might consume fewer raw bytes than widespread inlining in massive codebases.
  • Single-File Transpilation Failures: Modern build tools (such as Babel, esbuild, and SWC) transpile each file in isolation without evaluating cross-file type definitions. When isolatedModules: true is enabled, const enums cannot be safely inlined across file boundaries, leading to compilation errors or forcing the bundler to retain the runtime object anyway.
  • Library Distribution Hazards: If you publish an npm package that exports const enums, consumers compiling their projects with single-file transpilers or pure JavaScript will encounter runtime errors unless you configure your build to preserve or fully resolve them beforehand.

Alternative Approaches

To achieve zero-cost bundle impact without the tooling friction of const enums, string literal unions combined with as const objects serve as the current industry standard:

export const Status = {
  Active: "ACTIVE",
  Inactive: "INACTIVE",
} as const;

export type Status = (typeof Status)[keyof typeof Status];

This pattern provides the same type safety and autocompletion as enums, plays cleanly with all modern bundlers and transpilers, and minimizes bundle size without hidden compilation side effects.
