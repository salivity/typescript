Why noPropertyAccessFromIndexSignature Requires Brackets

TypeScript’s noPropertyAccessFromIndexSignature compiler option enforces the use of bracket notation (obj['key']) over dot notation (obj.key) when accessing dynamic properties defined by an index signature. By mandating this syntactic distinction, the rule prevents developers from mistaking speculative, dynamic properties for statically declared, guaranteed fields. This article breaks down why this requirement exists, how it improves type safety, and how it guards against runtime errors.

The Problem with Dot Notation on Index Signatures

An index signature allows an object to accept arbitrary properties of a given type:

interface UserScores {
  [username: string]: number;
}

const scores: UserScores = { alice: 100 };

By default, TypeScript allows you to access properties on scores using standard dot notation:

console.log(scores.bob); // Valid at compile time, but returns undefined at runtime

Dot notation traditionally implies that a property is an explicitly declared member of an object structure. When dot access is permitted on broad index signatures, typos and assumptions about an object's contents go unnoticed. Writing scores.bob visually mimics a fixed property contract, making code review and refactoring prone to missed undefined values.

Why Bracket Notation Is Enforced

When noPropertyAccessFromIndexSignature is set to true, TypeScript explicitly forbids dot notation for any property not defined directly on the type:

// Error: Property 'bob' comes from an index signature, so it must be accessed with ['bob'].
console.log(scores.bob);

// Allowed:
console.log(scores['bob']);

TypeScript enforces this requirement for several key reasons:

1. Semantic Clarity

Bracket notation explicitly indicates dynamic or uncertain lookup. When skimming code, developers intuitively recognize obj['prop'] as a dictionary lookup or dynamic map query, whereas obj.prop signals a known, stable property guaranteed to exist on the interface.

2. Clear Separation of Known and Unknown Keys

Consider a type with both fixed properties and an index signature:

interface Settings {
  theme: string;
  [key: string]: string;
}

const userSettings: Settings = { theme: 'dark', customSidebar: 'open' };

userSettings.theme;             // Allowed (explicitly declared)
userSettings.customSidebar;      // Compile error
userSettings['customSidebar'];   // Allowed

The rule ensures that explicitly declared properties remain distinct from arbitrary extensions. If you accidentally misspell an explicit property (e.g., userSettings.thmee), TypeScript will reject it instead of silently falling back to the index signature.

3. Synergy with noUncheckedIndexedAccess

When used alongside noUncheckedIndexedAccess, bracket notation access automatically typed as T | undefined:

const value = scores['bob']; // Type is number | undefined

This combination forces developers to handle missing keys defensively while maintaining normal, non-optional types for properties accessed via dot notation that are guaranteed by the interface.

Requiring bracket notation creates a strict boundary between static object shapes and dynamic dictionaries, making code intent clearer and preventing accidental undefined runtime crashes.
