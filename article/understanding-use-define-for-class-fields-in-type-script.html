Understanding useDefineForClassFields in TypeScript

The useDefineForClassFields compiler flag in TypeScript switches class field initialization from traditional assignment semantics ([[Set]]) to ECMAScript-standard define semantics ([[Define]]). This article explains how this setting alters JavaScript code generation, why it causes derived class fields to override parent getters and setters, and how it changes the handling of uninitialized properties and legacy decorators.

Assignment Semantics vs. Define Semantics

Before the ECMAScript class fields specification was standardized, TypeScript initialized public class properties using basic assignments (this.prop = value).

When useDefineForClassFields is set to false, TypeScript generates code equivalent to:

class Example {
  foo = 1;
}

// Emits approximately:
class Example {
  constructor() {
    this.foo = 1;
  }
}

When useDefineForClassFields is set to true, TypeScript adheres to the standard ECMAScript specification by defining fields via Object.defineProperty:

class Example {
  foo = 1;
}

// Emits standard define behavior:
class Example {
  constructor() {
    Object.defineProperty(this, "foo", {
      enumerable: true,
      configurable: true,
      writable: true,
      value: 1
    });
  }
}

If the compilation target is set to ES2022 or later, native class field syntax is emitted directly, which natively uses [[Define]] semantics.

Impact on Getters and Setters

The most noticeable difference occurs when a subclass property shares a name with a getter or setter in a base class.

Under assignment semantics (useDefineForClassFields: false), assigning a property in a derived class triggers the parent's setter:

class Base {
  set data(value: string) {
    console.log("Setter called:", value);
  }
}

class Derived extends Base {
  data = "hello"; // Invokes Base's setter
}

Under define semantics (useDefineForClassFields: true), the subclass defines an own property directly on the instance using [[Define]]. The base class setter is bypassed completely, and an own property is created on the instance that shadows the getter/setter on the prototype:

const instance = new Derived();
// "Setter called" is NOT logged.
// instance.data is an own property with the value "hello".

Impact on Uninitialized Properties

Under the legacy behavior (false), declaring a class field without an initializer does not emit any runtime code:

class User {
  name: string; // Emits nothing to JS
}

When useDefineForClassFields is true, declaring a property without an initializer still generates an initialization to undefined:

class User {
  name: string;
}

// Emits:
class User {
  constructor() {
    this.name = void 0;
  }
}

This can unexpectedly overwrite values set by a super() constructor. To retain a type-only declaration without emitting runtime code when useDefineForClassFields is enabled, use the declare modifier:

class User {
  declare name: string; // Emits no JavaScript
}

Impact on Legacy Decorators

Many libraries that rely on experimental decorators (such as MobX, TypeORM, or older Angular versions) mutate properties by installing getters and setters on the prototype or the instance.

With useDefineForClassFields: true, instance property definitions run after the decorator setup and will overwrite or detach the accessors established by decorators. When using legacy experimental decorators ("experimentalDecorators": true), useDefineForClassFields typically needs to remain false unless the underlying library explicitly supports standard TC39 class fields.

Default Behavior by Target

  • target: "ES2021" or lower: Defaults to false unless explicitly enabled in tsconfig.json.
  • target: "ES2022" or later (including ESNext): Defaults to true to match standard JavaScript runtime semantics.
