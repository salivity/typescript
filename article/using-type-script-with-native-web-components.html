Using TypeScript with Native Web Components

This article explores how TypeScript interacts with native Web Components and Custom Elements to provide end-to-end type safety across standard browser APIs. It covers authoring custom elements by subclassing HTMLElement, managing lifecycle methods with strict typing, augmenting the global HTMLElementTagNameMap for standard DOM queries, and declaring types within JSX/TSX environments.

Extending HTMLElement

Creating a custom element in TypeScript begins by subclassing the standard HTMLElement class (or specific subclasses such as HTMLButtonElement). TypeScript leverages its built-in DOM type definitions to ensure standard methods and lifecycle hooks are implemented correctly.

class UserCard extends HTMLElement {
  static get observedAttributes(): string[] {
    return ['user-id', 'name'];
  }

  connectedCallback(): void {
    this.render();
  }

  disconnectedCallback(): void {
    // Cleanup event listeners or timers
  }

  attributeChangedCallback(
    name: string,
    oldValue: string | null,
    newValue: string | null
  ): void {
    if (oldValue !== newValue) {
      this.render();
    }
  }

  private render(): void {
    this.textContent = `User: ${this.getAttribute('name') ?? 'Anonymous'}`;
  }
}

customElements.define('user-card', UserCard);

By subclassing HTMLElement, TypeScript ensures that standard DOM methods like attachShadow, getAttribute, and dispatchEvent are statically checked, preventing runtime errors caused by typos or improper access.

Augmenting the DOM with HTMLElementTagNameMap

When custom elements are registered with customElements.define(), the runtime browser environment recognizes the new HTML tag, but the TypeScript compiler does not know about it by default. Calling document.createElement('user-card') would normally return a generic HTMLElement.

To provide full type inference when querying or creating elements via DOM APIs, you must augment the global HTMLElementTagNameMap interface:

declare global {
  interface HTMLElementTagNameMap {
    'user-card': UserCard;
  }
}

Once declared, methods like document.createElement, document.querySelector, and document.querySelectorAll automatically resolve to the correct element type:

// Type is inferred as UserCard, not HTMLElement
const card = document.createElement('user-card');

// Type is inferred as UserCard | null
const existingCard = document.querySelector('user-card');

Typing Properties vs. Attributes

Web Components rely on attributes (HTML strings) and properties (JavaScript object state). TypeScript helps distinguish between the two:

  • Attributes: Synchronized through getAttribute and setAttribute. Types should account for string values or null.
  • Properties: Declared directly on the class with explicit types, allowing complex data structures such as objects, arrays, or functions.
interface UserData {
  id: string;
  roles: string[];
}

class UserCard extends HTMLElement {
  private _data: UserData | null = null;

  get data(): UserData | null {
    return this._data;
  }

  set data(value: UserData | null) {
    this._data = value;
    this.render();
  }
}

Integrating with JSX and TSX

If custom elements are consumed within TSX files (such as in React, Preact, or custom JSX runtimes), TypeScript will report an error if the tag is missing from the JSX definitions. You can add the element to the JSX namespace by augmenting JSX.IntrinsicElements:

declare global {
  namespace JSX {
    interface IntrinsicElements {
      'user-card': React.DetailedHTMLProps<
        React.HTMLAttributes<HTMLElement>,
        HTMLElement
      > & {
        'user-id'?: string;
        name?: string;
      };
    }
  }
}

This mapping guarantees that attributes passed to the custom element in templates are validated during compilation, completing the type-safety pipeline from the native browser implementation to consuming frameworks.
