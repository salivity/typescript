Category Theory and Monads in TypeScript with fp-ts

This article explores how the fp-ts library brings mathematical abstractions from category theory into TypeScript, focusing on its representation of monads and the simulation of Higher-Kinded Types. Because TypeScript lacks native higher-kinded polymorphism, fp-ts employs a technique known as Lightweight Higher-Kinded Polymorphism to represent structures like Functors, Applicatives, and Monads. By separating data from behavior and leveraging TypeScript’s advanced type system, fp-ts delivers a rigorous, type-safe implementation of category-theoretic patterns for practical application development.

The Higher-Kinded Type Challenge

Category theory abstractions rely on Higher-Kinded Types (HKTs). In functional programming, a standard type constructor like Array<T> or Option<T> takes a concrete type T and yields a new type. However, abstractions such as Functor or Monad operate over the type constructor itself—often denoted as F<_>.

Because TypeScript does not allow generic types to accept other generic type constructors without applying them (e.g., you cannot write interface Functor<F> where F is F<A>), standard category theory representations cannot be expressed directly.

Lightweight Higher-Kinded Polymorphism

To circumvent this limitation, fp-ts utilizes Lightweight Higher-Kinded Polymorphism, a technique based on defunctionalization at the type level.

Instead of passing the type constructor directly, fp-ts represents type constructors using unique string literals known as Uniform Resource Identifiers (URIs). The system maps these string identifiers to their respective generic implementations using TypeScript’s module augmentation and interface merging:

  1. The Type-Level Dictionary: The library defines a central interface, URItoKind<A>, which acts as a lookup table mapping URIs to concrete generic types:

    interface URItoKind<A> {
  readonly Option: Option<A>;
  readonly Either: Either<unknown, A>;
}

  2. The HKT Representation: The type Kind<F, A> looks up the URI F inside URItoKind<A>:

    type Kind<F extends URIS, A> = URItoKind<A>[F];

This mechanism allows fp-ts to write general interfaces parameterized over F extends URIS while retaining accurate type inference.

Modeling Typeclasses as Dictionaries

In pure category theory and languages like Haskell, concepts like Monads are represented via typeclasses. In fp-ts, typeclasses are modeled as standard TypeScript objects containing pure functions rather than classes or object methods.

A Functor dictionary provides the mapping capability:

interface Functor<F extends URIS> {
  readonly URI: F;
  readonly map: <A, B>(f: (a: A) => B) => (fa: Kind<F, A>) => Kind<F, B>;
}

By keeping functions outside the data structures, fp-ts maintains separation between data and behavior, avoids prototype pollution, and enables efficient tree-shaking.

Constructing the Monad Hierarchy

In category theory, a Monad is a Monoid in the category of endofunctors. In programming terms, it combines the capabilities of a Functor and an Applicative with sequencing capabilities. In fp-ts, this hierarchy is constructed through interface extension:

  1. Functor: Introduces map to transform wrapped values.
  2. Apply: Extends Functor by adding ap, allowing functions wrapped in a context to be applied to values in that same context.
  3. Applicative: Extends Apply by adding of (often called pure or return), lifting an uncontextualized value into the context.
  4. Chain: Extends Apply with chain (equivalent to flatMap or bind), which allows sequential computation where the next step depends on the output of the previous step.
  5. Monad: Combines Applicative and Chain.
interface Monad<M extends URIS> extends Applicative<M>, Chain<M> {}

An instance of Monad must satisfy three fundamental categorical laws:

  • Left Identity: pipe(M.of(a), M.chain(f)) === f(a)
  • Right Identity: pipe(m, M.chain(M.of)) === m
  • Associativity: pipe(m, M.chain(f), M.chain(g)) === pipe(m, M.chain(x => pipe(f(x), M.chain(g))))

Practical Usage via Combinators and pipe

Rather than invoking typeclass instances directly as method calls on objects, fp-ts uses standalone combinators designed for functional composition. Data transformation pipelines are written using the pipe operator.

For example, interacting with the Option Monad:

import { option as O } from 'fp-ts';
import { pipe } from 'fp-ts/function';

const parseNumber = (s: string): O.Option<number> => {
  const n = Number(s);
  return isNaN(n) ? O.none : O.some(n);
};

const doublePositive = (n: number): O.Option<number> =>
  n > 0 ? O.some(n * 2) : O.none;

const result = pipe(
  "42",
  parseNumber,          // Returns Option<number>
  O.chain(doublePositive) // Sequences computation: unwraps, applies, flattens
);

In this pipeline, O.chain fulfills the monadic bind operation. If any step yields O.none, the remaining evaluations are skipped, demonstrating how fp-ts encodes effects through standard monadic behavior.
