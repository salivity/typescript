TypeScript Phantom Types for Safe State Transitions

The phantom type pattern is an advanced typing technique where a generic type parameter is used solely at compile time without appearing as a runtime property of a data structure. In TypeScript, this pattern allows developers to tag data structures with metadata that tracks their lifecycle state. By binding transition functions to specific phantom states, you can turn runtime sequence bugs—such as sending an unsaved draft or approving an already processed order—into compile-time type errors with zero runtime performance cost.

What is a Phantom Type?

In TypeScript, a phantom type occurs when a generic type parameter T is declared on a type or interface, but T is not actually used by any value-holding property in the underlying runtime object. Because TypeScript uses a structural type system rather than a nominal one, simply declaring an unused generic parameter (e.g., interface Order<T> { id: string }) will cause TypeScript to discard the type parameter during structural comparison.

To retain the type parameter, a phantom field—typically marked optional and hidden via unique symbols or private-like naming conventions—is added:

declare const phantom: unique symbol;

interface Order<State> {
  readonly [phantom]?: State;
  id: string;
  amount: number;
}

Because the property [phantom] is optional, it never needs to exist at runtime. However, TypeScript's compiler tracks State and refuses to assign an Order<StateA> to an Order<StateB> unless the two states are structurally compatible.

The Problem: Unchecked State Transitions

Consider an e-commerce order that transitions through three stages: Draft, Submitted, and Paid. Without phantom types, modeling these states often relies on a string field or completely unchecked interfaces:

interface Order {
  id: string;
  status: "Draft" | "Submitted" | "Paid";
  amount: number;
}

function processPayment(order: Order): Order {
  return { ...order, status: "Paid" };
}

In this model, calling processPayment on a Draft order is syntactically valid TypeScript. Developers must rely on manual runtime assertions inside every function, which can be bypassed, forgotten, or discovered only in production:

const draftOrder: Order = { id: "1", status: "Draft", amount: 100 };
// Valid at compile-time, but a logical bug:
processPayment(draftOrder);

Enforcing Transitions with Phantom Types

To restrict invalid transitions, define unique types representing each lifecycle phase and restrict functions to accept only the appropriate state.

1. Define State Markers

Define types that represent the allowed states. Empty interfaces or empty object types are sufficient:

interface DraftState { readonly _tag: "Draft" }
interface SubmittedState { readonly _tag: "Submitted" }
interface PaidState { readonly _tag: "Paid" }

2. Define the Parametrized Entity

Define the entity using the phantom state parameter:

declare const StateTag: unique symbol;

interface Order<State> {
  readonly [StateTag]?: State;
  id: string;
  amount: number;
}

3. Implement Transition Functions

Create factory and transition functions where the argument requires a specific source state, and the return type produces the destination state:

// Creation produces a Draft
function createOrder(id: string, amount: number): Order<DraftState> {
  return { id, amount };
}

// Submitting requires a Draft and produces a Submitted order
function submitOrder(order: Order<DraftState>): Order<SubmittedState> {
  return { id: order.id, amount: order.amount };
}

// Payment requires a Submitted order and produces a Paid order
function processPayment(order: Order<SubmittedState>): Order<PaidState> {
  return { id: order.id, amount: order.amount };
}

How It Restricts Invalid Transitions

When functions are typed with specific phantom states, TypeScript ensures that states are executed in the correct linear order.

const draft = createOrder("ord-123", 250);

// COMPILE ERROR:
// Argument of type 'Order<DraftState>' is not assignable to parameter of type 'Order<SubmittedState>'.
processPayment(draft);

// CORRECT FLOW:
const submitted = submitOrder(draft);
const paid = processPayment(submitted); // Compiles successfully

Attempting to skip the submitOrder step causes a static compilation failure. Similarly, attempting to re-submit an already paid order (submitOrder(paid)) will fail because Order<PaidState> cannot be assigned to Order<DraftState>.

Benefits of the Phantom Type Pattern

  • Zero Runtime Overhead: Phantom markers are completely erased during compilation, resulting in identical JavaScript output to untyped structures.
  • Deterministic Sequences: Invalid sequences of operations are caught during development or CI pipelines, eliminating entire classes of state machine bugs.
  • Self-Documenting Code: Function signatures explicitly declare their prerequisites and outputs, making system workflows transparent directly in the code editor.
