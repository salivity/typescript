tsc --noEmit vs ESLint with TypeScript Rules

While both tsc --noEmit and ESLint with TypeScript rules analyze your codebase to catch errors before runtime, they serve fundamentally different purposes. tsc --noEmit runs the official TypeScript compiler solely to perform type checking across your entire project without producing JavaScript build files. In contrast, ESLint parses code to enforce code quality, style consistency, and best practices. Understanding how their internal mechanics, performance footprints, and rule scopes differ is essential for setting up an efficient development and CI/CD workflow.

Primary Purpose and Scope

  • tsc --noEmit (Type Checking): The primary goal of tsc --noEmit is type verification and semantic correctness. It inspects whether variables, function parameters, return values, and module contracts conform to TypeScript’s type system. It determines whether your code is mathematically sound from a type perspective (e.g., preventing you from accessing properties on undefined or passing a string where a number is expected).
  • ESLint (Code Quality and Linting): ESLint is an AST (Abstract Syntax Tree) linter designed to enforce developer guidelines, identify anti-patterns, and catch logic flaws that are syntactically and type-wise valid. For instance, tsc will not care if you leave a dangling console.log, write an empty function, or create cyclomatic complexity that makes code unreadable, but ESLint will.

Analysis Method and Architecture

  • Whole-Program Type Checking: tsc evaluates your entire codebase as an interconnected program. It resolves cross-file dependencies, global ambient definitions, declaration merges, and complex generic constraints. Because it was purpose-built for type checking, its internal pipeline is heavily optimized for resolving deep type dependencies across files.
  • AST Rule Traversal: ESLint inspects files by traversing an Abstract Syntax Tree node-by-node. When using @typescript-eslint, ESLint leverages TypeScript's parser to produce an AST that mirrors TypeScript code. While ESLint can run "type-aware" rules by creating a TypeScript compiler instance under the hood, it is fundamentally designed to evaluate discrete rules on syntax nodes rather than validating global type integrity.

Ability to Auto-Fix Code

  • tsc --noEmit: The TypeScript compiler does not automatically fix errors via the CLI. It only reports type mismatches, syntax errors, and missing declarations as exit codes and terminal logs.
  • ESLint: ESLint features a built-in --fix flag. Many lint rules (such as removing unused imports, enforcing specific quote styles, or rewriting deprecated syntax) can be automatically corrected without developer intervention.

Performance and Resource Usage

  • Speed of Type Validation: tsc is significantly faster at purely validating types than running ESLint with type-aware rules enabled.
  • Type-Aware ESLint Overhead: When ESLint rules require type information (like @typescript-eslint/no-floating-promises), ESLint must request type definitions from the TypeScript compiler API for each inspected node. This adds overhead and can drastically increase linting times on large codebases.

Summary of Differences

Feature tsc --noEmit ESLint with TypeScript Rules
Core Function Static type checking and compiler verification Code quality, conventions, and pattern enforcement
Analyzes Semantic type correctness across the entire project Syntax patterns, AST nodes, and style guidelines
Auto-Fix No Yes (via --fix)
Style Checking Minimal (only strict compiler flags) Extensive (indentation, naming conventions, formatting)
Speed Highly optimized for full type evaluation Fast for syntactic rules; slower for type-aware rules

Best Practice

These tools are complementary rather than mutually exclusive. The standard industry practice is to run both: use tsc --noEmit to verify type safety and handle type checking in your CI pipeline, and use ESLint to maintain clean, readable code and prevent common runtime and stylistic mistakes.
