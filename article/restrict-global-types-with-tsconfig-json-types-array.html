Restrict Global Types with tsconfig.json types Array

By default, the TypeScript compiler automatically includes all packages found within node_modules/@types into the global compilation scope. This article explains how specifying the types array inside compilerOptions overrides this automatic behavior, allowing developers to restrict global package visibility, prevent ambient namespace collisions, and maintain clean type boundaries.

Default Global Type Resolution

When TypeScript compiles a project, its default behavior is to scan all parent directories for node_modules/@types. Every package located inside these folders—such as @types/node, @types/jest, or @types/mocha—is automatically loaded into the global scope.

Because these definitions are ambient, any global identifiers they define become accessible across the entire project without requiring an explicit import statement. This can introduce subtle bugs, such as code using Node.js runtime globals like process or Buffer inside client-side browser code, or Jest's global test() function leaking into production source files.

Overriding Global Inclusions with the types Array

The types setting in tsconfig.json acts as an allowlist for ambient declarations. When this array is defined, TypeScript ceases its automatic scanning of all @types packages and strictly includes only the packages listed.

{
  "compilerOptions": {
    "types": ["node"]
  }
}

In the configuration above, only declarations from @types/node are made globally accessible. If @types/jest or @types/jquery exist in node_modules, their global declarations are ignored by the compiler. Attempting to use identifiers like describe() or $ globally will result in a compilation error (Cannot find name ...), unless they are explicitly imported within the file.

Disabling Global Inclusions Completely

To prevent any third-party declarations from leaking into the global namespace, set the types array to an empty list:

{
  "compilerOptions": {
    "types": []
  }
}

With an empty array, TypeScript does not expose any @types package globally. This is common practice in library development and clean architecture setups where dependencies must always be explicitly imported, ensuring zero reliance on ambient runtime assumptions.

types vs. typeRoots

It is important to distinguish types from typeRoots:

  • typeRoots specifies the directories where TypeScript looks for type definitions (defaulting to node_modules/@types).
  • types specifies the exact packages within those directories that should be included globally.

If both are specified, TypeScript looks inside the directories listed in typeRoots, but only resolves the packages named in types.

Impact on Explicit Imports

The types array strictly affects ambient global inclusion. It does not prevent files from importing packages directly. For instance, if @types/lodash is omitted from the types list, it will not exist as a global variable, but writing import _ from "lodash"; will still locate and apply the correct type definitions.
