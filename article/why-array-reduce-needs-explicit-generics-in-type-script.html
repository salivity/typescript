Why Array Reduce Needs Explicit Generics in TypeScript

In TypeScript, Array.prototype.reduce frequently causes compiler errors because the compiler determines the accumulator's type solely from the provided initial value rather than inferring it from the callback's return type. This article explains how TypeScript's overload signatures for reduce operate, why default inference breaks when accumulating into objects or arrays, and how using explicit generic type arguments resolves these type-checking issues cleanly and safely.

How TypeScript Types Array.prototype.reduce

The standard TypeScript library defines two primary overloads for reduce:

  1. Without an initial value:

    reduce(callbackfn: (previousValue: T, currentValue: T, currentIndex: number, array: T[]) => T): T;

    Here, the accumulator must be the same type T as the array elements.

  2. With an initial value:

    reduce<U>(callbackfn: (previousValue: U, currentValue: T, currentIndex: number, array: T[]) => U, initialValue: U): U;

    Here, the accumulator introduces a new generic type U, which matches the type of initialValue.

The Root Cause: Left-to-Right Type Inference

TypeScript infers the generic type U directly from the initialValue argument. It does not infer U by examining the operations or return statements inside the callback function. This behavior leads to common type issues in two typical scenarios.

1. Initializing with an Empty Object ({})

When transforming a list into a lookup dictionary or map, developers often pass an empty object as the initial value:

const items = [{ id: "a", val: 1 }, { id: "b", val: 2 }];

const lookup = items.reduce((acc, item) => {
  acc[item.id] = item.val; // Error: Property does not exist on type '{}'
  return acc;
}, {});

Because initialValue is {}, TypeScript infers U as {} (an object with no known properties). When the callback attempts to assign acc[item.id], TypeScript rejects it because the key does not exist on type {}. The compiler will not expand U to include dynamic keys automatically.

2. Initializing with an Empty Array ([])

When flattening or filtering into a new array with an empty array literal:

const numbers = [1, 2, 3];

const result = numbers.reduce((acc, num) => {
  acc.push(num.toString()); // Error: Argument of type 'string' is not assignable to parameter of type 'never'
  return acc;
}, []);

An unannotated empty array literal [] is inferred as never[]. Consequently, U is fixed to never[], making it impossible to add elements of any type into the accumulator.

Why TypeScript Does Not Infer from Callback Returns

Inferring U from the callback's return value would require the compiler to solve a circular dependency:

  • To validate the callback implementation, the compiler must know the type of previousValue (U).
  • To know U, the compiler would need to evaluate what the callback returns across all execution branches.

To prevent expensive and potentially ambiguous bidirectional type checks, TypeScript uses unidirectional inference: it fixes U using initialValue, then applies U contextually to the callback's first parameter.

The Solution: Explicit Type Arguments

Providing the generic argument explicitly overrides automatic inference and gives TypeScript the complete contract upfront:

// For objects:
type Lookup = Record<string, number>;

const lookup = items.reduce<Lookup>((acc, item) => {
  acc[item.id] = item.val;
  return acc;
}, {});

// For arrays:
const strings = numbers.reduce<string[]>((acc, num) => {
  acc.push(num.toString());
  return acc;
}, []);

By providing <Lookup> or <string[]>, U is explicitly defined. TypeScript now types initialValue and the accumulator parameter acc as the target type, allowing valid modifications while ensuring the returned value matches the intended structure.
