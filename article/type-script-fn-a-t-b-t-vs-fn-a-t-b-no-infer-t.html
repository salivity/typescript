TypeScript fn(a: T, b: T) vs fn(a: T, b: NoInfer<T>)

In TypeScript, the behavioral difference between fn(a: T, b: T) and fn(a: T, b: NoInfer<T>) lies in how the compiler selects candidate types for the generic parameter T. In fn(a: T, b: T), TypeScript infers T from both arguments, often widening T to a union type if the arguments differ. In fn(a: T, b: NoInfer<T>), the NoInfer intrinsic utility (introduced in TypeScript 5.4) excludes the second argument from participating in type inference, forcing T to be determined solely by the first argument while still validating that the second argument satisfies that inferred type.

How fn(a: T, b: T) Works

When a generic parameter appears in multiple function parameters, every position is treated as an inference site. TypeScript evaluates the types passed into each parameter and attempts to find a common supertype or creates a union type to satisfy both positions.

function compare<T>(a: T, b: T): boolean {
  return a === b;
}

// Inferred type: T is "red" | "blue"
compare("red", "blue"); 

// Inferred type: T is number | string
compare(42, "hello");

In this setup, passing two completely different values does not trigger a compiler error. Instead, TypeScript widens T to accommodate both values. This behavior is problematic when one argument is meant to define the allowed values and the other is meant to adhere to that definition.

How fn(a: T, b: NoInfer<T>) Works

Wrapping a generic parameter in NoInfer<T> turns that parameter position into a validation-only site. TypeScript skips the argument during the initial type deduction phase and infers T strictly from non-wrapped positions. Once T is determined, the compiler validates the NoInfer<T> argument against the resolved type.

function compare<T>(a: T, b: NoInfer<T>): boolean {
  return a === b;
}

// Inferred type: T is "red"
// Error: Argument of type '"blue"' is not assignable to parameter of type '"red"'.
compare("red", "blue");

// Valid: T is "red", and the second argument is assignable to "red"
compare("red", "red");

Because b cannot contribute to T, passing an incompatible type causes an immediate type error instead of widening T to a union.

Real-World Use Case: Default Options and Handlers

The distinction is most critical when writing APIs where one argument must act as the source of truth, such as state machines, configuration objects, or selection handlers.

// Without NoInfer:
function createSelector<T extends string>(
  options: T[], 
  defaultOption: T
) { /* ... */ }

// TypeScript infers T as "apple" | "banana" | "orange"
// No compile error occurs, allowing an invalid default option:
createSelector(["apple", "banana"], "orange");

// With NoInfer:
function createSelectorStrict<T extends string>(
  options: T[], 
  defaultOption: NoInfer<T>
) { /* ... */ }

// TypeScript infers T solely as "apple" | "banana"
// Compile Error: Argument of type '"orange"' is not assignable to parameter of type '"apple" | "banana"'.
createSelectorStrict(["apple", "banana"], "orange");

Summary of Differences

  • Type Candidate Selection: fn(a: T, b: T) treats both a and b as inference candidates. fn(a: T, b: NoInfer<T>) treats only a as an inference candidate.
  • Widening vs. Type Checking: fn(a: T, b: T) widens T to a union type if a and b have different types. fn(a: T, b: NoInfer<T>) locks T to the type of a and raises a type error if b cannot be assigned to T.
  • Authority: In fn(a: T, b: NoInfer<T>), argument a becomes the single source of truth for the type parameter.
