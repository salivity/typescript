Stage 3 Decorators vs TypeScript Experimental Decorators

JavaScript decorators have evolved from a legacy TypeScript-specific implementation into an official ECMAScript standard currently at Stage 3. While both versions allow developers to annotate and modify classes and their members, modern Stage 3 decorators introduce a completely redesigned API, replace property descriptors with a dedicated context object, alter how return values manipulate targets, and drop native support for parameter decorators while adding native support for private class elements.

The Decorator Signature and Context Object

The most fundamental structural difference lies in the arguments passed to the decorator functions.

Experimental Decorators: In the legacy implementation (enabled via "experimentalDecorators": true), the signature varied heavily based on the target member:

  • Classes: Received the constructor function (target).
  • Methods and Accessors: Received (target, propertyKey, descriptor).
  • Fields: Received (target, propertyKey).
  • Parameters: Received (target, propertyKey, parameterIndex).

Legacy decorators relied heavily on mutating the target prototype or modifying the provided PropertyDescriptor.

Stage 3 Decorators: Modern decorators standardize the function signature across all member types to exactly two parameters: (value, context).

  • value: The element being decorated (e.g., the method, class, getter, setter, or undefined for fields).
  • context: A standardized DecoratorContext object providing metadata about the target:
    • kind: Specifies the type of decorated member ("class", "method", "getter", "setter", "field", or "accessor").
    • name: The name of the member (string, symbol, or private identifier).
    • static: Boolean indicating whether the member is static.
    • private: Boolean indicating whether the member is a private class element (e.g., #myField).
    • access: An object with get and set methods to dynamically read or assign the value.
    • addInitializer: A hook to schedule initialization logic relative to class creation or instance construction.

Return Values and Target Transformation

Legacy and modern decorators fundamentally differ in how they apply changes back to the class.

  • Experimental: Method and accessor decorators modified the member by returning a modified PropertyDescriptor. Class decorators returned a new constructor class or sub-class.
  • Stage 3: Decorators rarely interact with property descriptors directly. Instead, they transform targets by returning a new value of the same type:
    • A method decorator returns a new function that replaces the original method.
    • A class decorator returns a new constructor function.
    • A field decorator returns an initializer function: (initialValue) => modifiedValue. This allows modern decorators to manipulate field values at construction time, a capability that legacy field decorators lacked without hacky prototype definitions.

Auto-Accessor Decorators

Stage 3 introduces a new class member syntax known as auto-accessors, written as:

class Example {
  accessor value = 1;
}

An accessor keyword automatically generates a private backing storage field along with getter and setter pairs. Modern decorators can target accessors (kind: "accessor"), accepting an object with { get, set } and returning an object overriding either access method or providing a custom initializer. Experimental decorators have no concept of auto-accessors.

Parameter Decorators

A major structural departure in Stage 3 is the removal of parameter decorators.

  • Experimental: Supported decorating individual parameters of methods or constructors, commonly used by dependency injection frameworks (e.g., @Inject()).
  • Stage 3: Does not include parameter decorators in the core specification. Parameter decoration has been split into a separate, future TC39 proposal.

Private Identifiers and Encapsulation

Experimental decorators were designed before native private class fields (#field) were integrated into ECMAScript. Consequently, legacy decorators can only operate on public or TypeScript-level private properties (which compile to regular public properties).

Stage 3 decorators natively support true ECMAScript private identifiers. The context.private boolean denotes whether an element is private, and the context.access functions allow the decorator to safely read and write to private fields without violating class encapsulation.

Metadata Reflection

  • Experimental: Relied on the external reflect-metadata polyfill and the TypeScript compiler flag "emitDecoratorMetadata": true to infer and store type signatures at runtime.
  • Stage 3: The standard includes a built-in metadata proposal. The DecoratorContext contains a metadata property (a plain JavaScript object shared across all decorators in the class hierarchy), establishing a native platform standard for storing and retrieving runtime reflection data without external shims.
