Web Worker Global Typings in TypeScript

Web workers execute in a separate thread from the main browser environment and do not have access to standard DOM globals like window or document. In TypeScript, providing distinct global typings for worker files prevents the invalid use of DOM APIs and provides accurate autocompletion for worker-specific interfaces like DedicatedWorkerGlobalScope. This separation is primarily achieved through dedicated tsconfig.json configurations, file-level triple-slash directives, or explicit contextual type casting.

The Conflict Between DOM and WebWorker Libraries

By default, front-end TypeScript projects specify "DOM" in the lib array of tsconfig.json. This injects DOM globals directly into the ambient global scope. TypeScript also provides a "WebWorker" library containing global declarations for DedicatedWorkerGlobalScope, postMessage, and importScripts.

Because both "DOM" and "WebWorker" define conflicting identifiers on the global scope (such as the global self object and shared event listeners), TypeScript will throw duplicate identifier errors if both libraries are loaded into the same compilation context.

Approach 1: Dedicated tsconfig.json (Recommended)

The cleanest and most robust method to provide distinct global scopes is to isolate worker files into their own TypeScript compilation context using TypeScript project references or separate config files.

  1. Main Application Configuration (tsconfig.json): Exclude worker scripts and include the standard DOM library.

    {
  "compilerOptions": {
    "target": "ESNext",
    "lib": ["DOM", "DOM.Iterable", "ESNext"],
    "module": "ESNext"
  },
  "exclude": ["src/**/*.worker.ts"]
}

  2. Worker Configuration (tsconfig.worker.json): Create a dedicated configuration targeting only worker scripts that substitutes the DOM library with WebWorker.

    {
  "compilerOptions": {
    "target": "ESNext",
    "lib": ["WebWorker", "ESNext"],
    "module": "ESNext",
    "noEmit": true
  },
  "include": ["src/**/*.worker.ts"]
}

Modern bundlers like Vite, Webpack (via ts-loader), and esbuild can be configured to consume this dedicated configuration when bundling worker entries.

Approach 2: Triple-Slash Directives

If maintaining multiple tsconfig.json files is impractical, you can load worker typings at the file level using triple-slash reference directives.

Add the following directive at the very top of your worker file:

/// <reference lib="webworker" />

// Ensure the file is treated as an isolated module
export {};

addEventListener("message", (event: MessageEvent) => {
  postMessage(`Received: ${event.data}`);
});

Note: If your root tsconfig.json already includes "DOM" in its lib array, name collisions can still occur. This approach works best when the base configuration contains only ECMAScript libraries (such as "ESNext") without "DOM".

Approach 3: Explicit Global Casting

For small projects or single-file workers operating in a project dominated by DOM typings, you can explicitly redefine self within the worker file. By treating the worker file as an ES module (using export {}), you can restrict type definitions locally without leaking them to the rest of the project.

export {};

declare const self: DedicatedWorkerGlobalScope;

self.onmessage = (event: MessageEvent) => {
  self.postMessage({ response: event.data });
};

This bypasses the need for the "WebWorker" standard library altogether while retaining type safety for worker-specific methods and properties.
