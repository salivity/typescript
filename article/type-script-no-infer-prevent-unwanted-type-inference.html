TypeScript NoInfer: Prevent Unwanted Type Inference

TypeScript 5.4 introduced the NoInfer<T> intrinsic utility type to give developers precise control over generic type argument inference. By default, TypeScript attempts to infer generic types from every parameter where the type appears, which can unintentionally widen types or allow invalid values to pass without compile errors. This article explains how generic inference works, demonstrates the problems caused by multi-site inference, and shows how NoInfer restricts inference candidates to ensure specific parameters only consume types rather than contribute to them.

The Problem with Default Generic Inference

When a function accepts a generic type T across multiple parameters, TypeScript inspects all provided arguments to determine the shape of T. Instead of prioritizing one argument over another, the compiler creates a union of all inferred types.

Consider a function designed to define allowable options and set an initial fallback:

function setSelection<T extends string>(options: T[], defaultOption: T) {
  // ...
}

// Desired behavior: error on "purple", because it is not in the array.
// Actual behavior: TS infers T as "red" | "green" | "blue" | "purple"
setSelection(["red", "green", "blue"], "purple");

In this scenario, rather than checking if "purple" exists within ["red", "green", "blue"], TypeScript uses "purple" as a candidate to infer T. Consequently, T becomes "red" | "green" | "blue" | "purple". The invalid default option passes compilation quietly because TypeScript inferred the type from both parameters simultaneously.

Before NoInfer, developers relied on complex type hacks, such as [T][T extends any ? 0 : never], to trick the compiler into ignoring an argument during inference. These workarounds were difficult to read, hard to maintain, and prone to breaking in subtle edge cases.

How NoInfer Works

The NoInfer<T> intrinsic type instructs the TypeScript compiler to exclude an argument position from candidate type inference. The parameter wrapped in NoInfer<T> still requires the type T, but it cannot contribute to what T is resolved to.

Rewriting the previous example with NoInfer:

function setSelection<T extends string>(
  options: T[], 
  defaultOption: NoInfer<T>
) {
  // ...
}

// Type Error: Argument of type '"purple"' is not assignable 
// to parameter of type '"red" | "green" | "blue"'.
setSelection(["red", "green", "blue"], "purple");

Here, TypeScript resolves the type of T solely from the options argument, establishing T as "red" | "green" | "blue". When evaluating defaultOption, the compiler sees NoInfer<T> and refrains from adding "purple" to the inference candidates. Instead, it checks "purple" against the already resolved T, properly triggering a compiler error.

Underlying Mechanism

During type checking, TypeScript operates in phases:

  1. Candidate Collection: The compiler traverses the arguments and collects candidate types for each generic type parameter.
  2. Type Resolution: The candidates are merged (typically into a union or intersection) to establish the final type for the generic parameter.
  3. Type Checking: Arguments are checked against the resolved parameters.

When an expression is wrapped in NoInfer<T>, TypeScript skips that expression during step 1 (Candidate Collection). The compiler defers evaluating that parameter until step 2 is complete. Once T is resolved using the non-wrapped parameters, the NoInfer<T> position is unblocked and evaluated strictly during step 3 (Type Checking).

Common Use Cases

1. Function Handlers with State

When configuring handlers that should only access properties defined in an initial state object:

interface StateConfig<S> {
  initialState: S;
  reducers: Record<string, (state: NoInfer<S>) => void>;
}

function createStore<S>(config: StateConfig<S>) {
  return config;
}

createStore({
  initialState: { count: 0 },
  reducers: {
    increment: (state) => {
      // TypeScript knows state has `count`.
      // It won't let reducers infer a wider state shape.
      state.count += 1;
    }
  }
});

2. Event Listeners and Callbacks

When an event listener needs to infer the event name, but callback parameters must strictly match the inferred event without defining their own:

function emit<Events extends Record<string, any>, K extends keyof Events>(
  eventName: K,
  payload: NoInfer<Events[K]>
) {
  // ...
}

By placing NoInfer on the payload, the payload must conform strictly to the event schema dictated by eventName, preventing mismatched payload structures from altering the inference of K.

Summary

The NoInfer intrinsic solves a fundamental ambiguity in TypeScript's generic resolution. By explicitly marking parameters that should act solely as consumers of a type, it prevents accidental type widening and eliminates the need for obscure compiler workarounds.
