TypeScript Enums and Const Enums Explained

TypeScript enums provide a way to define collections of related named constants, offering strong typing and semantic clarity. This article explains how the TypeScript compiler implements standard enums as JavaScript runtime objects, contrasts this with the compile-time inlining of const enum types, and highlights the performance and architectural trade-offs between both approaches.

How TypeScript Implements Standard Enums

Unlike most TypeScript features, standard enums are not purely type-level constructs; they emit actual JavaScript code. When TypeScript compiles an enum, it generates an Immediately Invoked Function Expression (IIFE) that populates an object with key-value pairs.

Numeric Enums

By default, enums in TypeScript are numeric, starting at index 0.

enum Direction {
  Up,
  Down,
  Left,
  Right,
}

The TypeScript compiler outputs the following JavaScript:

var Direction;
(function (Direction) {
    Direction[Direction["Up"] = 0] = "Up";
    Direction[Direction["Down"] = 1] = "Down";
    Direction[Direction["Left"] = 2] = "Left";
    Direction[Direction["Right"] = 3] = "Right";
})(Direction || (Direction = {}));

This pattern creates a reverse mapping. The runtime object contains mappings from property names to values, as well as values back to property names:

console.log(Direction.Up); // 0
console.log(Direction[0]);  // "Up"

String Enums

When values are explicitly set to strings, reverse mapping is omitted.

enum Status {
  Active = "ACTIVE",
  Inactive = "INACTIVE",
}

Compiles to:

var Status;
(function (Status) {
    Status["Active"] = "ACTIVE";
    Status["Inactive"] = "INACTIVE";
})(Status || (Status = {}));

Because string values can be arbitrary and do not benefit from positional indexing, TypeScript only generates forward mappings from key to value.

What is a const enum?

A const enum is declared using the const modifier before the enum keyword. Unlike standard enums, const enum definitions are completely erased during compilation.

const enum LogLevel {
  Debug = 0,
  Info = 1,
  Warn = 2,
  Error = 3,
}

const currentLevel = LogLevel.Warn;

TypeScript does not emit an IIFE or create a runtime object for LogLevel. Instead, it inlines the literal value directly at every call site:

var currentLevel = 2 /* LogLevel.Warn */;

Benefits of const enum

  • Zero Runtime Overhead: No JavaScript objects or functions are created in the output bundle.
  • Performance: Direct property access avoids object lookup overhead at runtime.
  • Code Size: Bundles remain smaller, which is particularly beneficial for high-performance applications or large codebases.

Caveats and Considerations

While const enum types save bundle size, they come with technical constraints:

  1. No Dynamic Member Access: You cannot iterate over a const enum (e.g., using Object.keys() or Object.values()) because the underlying object does not exist at runtime.
  2. Issues with Isolated Transpilation: Transpilers that compile files independently without full type information (such as Babel, SWC, or esbuild using --isolatedModules) cannot resolve imported const enum values. In such setups, TypeScript will issue an error unless configured otherwise.
  3. Cross-Package References: Consuming a const enum across library boundaries can cause issues if the consuming project compiles without the original TypeScript declaration files.

Standard enums provide runtime flexibility and reflection, whereas const enum types offer strict compile-time optimization. Choosing between them depends on whether your application requires runtime introspection or prioritized bundle efficiency.
