How to Infer TypeScript Types from Runtime Schemas

Static TypeScript types can be inferred directly from runtime validation schemas by using generic schema definitions paired with TypeScript's type-level operators, such as the infer keyword and conditional types. Instead of manually maintaining separate TypeScript interfaces and runtime validators, developers can define a single runtime schema—using libraries like Zod, Yup, Valibot, or TypeBox—and extract the corresponding static type automatically. This approach establishes a single source of truth for data models, eliminating type drift and reducing boilerplate code across applications.

The Problem of Dual Declarations

In standard TypeScript development, handling external data (such as API payloads or form inputs) often leads to redundancy:

  1. A static TypeScript interface or type is written to satisfy compile-time checking.
  2. A runtime validation schema or parsing function is written to ensure the incoming data actually matches that structure at execution time.

When the data contract changes, developers must update both declarations. Failing to update one results in runtime errors or misleading static checks.

How Type Inference from Schemas Works

Runtime libraries bridge runtime and compile-time domains by carrying type metadata within their schema definitions.

At a conceptual level, a schema instance is typed generically with the shape it validates:

interface Schema<T> {
  parse(input: unknown): T;
}

When you define a schema using helper functions, the library builds up this generic T through mapped types and generic constraints.

To retrieve T as a standalone static type, TypeScript's infer keyword extracts the generic type parameter from the schema instance:

type InferSchemaType<S> = S extends Schema<infer T> ? T : never;

Implementing Type Inference with Popular Libraries

Modern schema validation libraries provide built-in type inference utilities that follow this pattern.

Example: Zod

In Zod, schemas wrap data rules, and the z.infer<> utility extracts the static type via typeof:

import { z } from "zod";

// Define the runtime schema
const UserSchema = z.object({
  id: z.string().uuid(),
  name: z.string().min(1),
  email: z.string().email(),
  role: z.enum(["admin", "user"]).default("user"),
  tags: z.array(z.string()).optional(),
});

// Infer the static TypeScript type
type User = z.infer<typeof UserSchema>;

// The resolved static type is:
// type User = {
//   id: string;
//   name: string;
//   email: string;
//   role: "admin" | "user";
//   tags?: string[] | undefined;
// }

Any modification to UserSchema immediately reflects in the User type throughout the codebase during compilation.

Example: Valibot

Valibot functions similarly while focusing on modularity and tree-shaking, using InferOutput to extract static shapes:

import * as v from "valibot";

const ProductSchema = v.object({
  id: v.number(),
  title: v.string(),
  price: v.number(),
});

type Product = v.InferOutput<typeof ProductSchema>;

Creating a Minimal Custom Type-Inference Engine

Understanding how this operates without external dependencies requires only a few primitive validators:

// Base Validator type carrying phantom type T
type Validator<T> = {
  validate: (value: unknown) => value is T;
};

// Factory functions that generate typed validators
const stringValidator: Validator<string> = {
  validate: (v): v is string => typeof v === "string",
};

const numberValidator: Validator<number> = {
  validate: (v): v is number => typeof v === "number",
};

// Object validator combining schema properties
type ObjectSchema<T> = { [K in keyof T]: Validator<T[K]> };

function createObjectValidator<T>(schema: ObjectSchema<T>): Validator<T> {
  return {
    validate: (value: unknown): value is T => {
      if (typeof value !== "object" || value === null) return false;
      return Object.entries(schema).every(([key, validator]) =>
        (validator as Validator<unknown>).validate((value as Record<string, unknown>)[key])
      );
    },
  };
}

// Extraction utility using conditional inference
type FromValidator<V> = V extends Validator<infer T> ? T : never;

// Usage
const ConfigSchema = createObjectValidator({
  host: stringValidator,
  port: numberValidator,
});

type AppConfig = FromValidator<typeof ConfigSchema>;
// Resolved: type AppConfig = { host: string; port: number; }

Key Considerations

  • Input vs. Output Types: Some schemas transform data during parsing (e.g., converting an ISO date string into a Date object, or applying default values). Libraries like Zod address this by offering both z.input<typeof Schema> and z.output<typeof Schema> (which is what z.infer aliases).
  • Compile-Time Performance: Highly complex schemas with deep nesting or recursive properties can increase compiler workload. Using modular schemas and avoiding unnecessary recursive definitions keeps compilation fast.
  • Type Narrowing: When a schema parses unvalidated data (such as request bodies), the parser functions as a type guard, transforming dynamic unknown types into guaranteed static types safely at application boundaries.
