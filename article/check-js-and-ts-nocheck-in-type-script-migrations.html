checkJs and ts-nocheck in TypeScript Migrations

Migrating a large JavaScript codebase to TypeScript often introduces an overwhelming volume of type errors if enabled all at once. Combining the checkJs compiler option with the // @ts-nocheck comment directive solves this by creating an inverted, opt-out migration workflow. This strategy establishes an immediate baseline of zero errors, enforces strict type checking on all newly created files by default, and allows developers to migrate legacy files incrementally without disrupting day-to-day feature development.

The Problem with Traditional Migrations

When adopting TypeScript in an existing JavaScript repository, enabling type checking across the project usually produces thousands of compilation errors overnight. Teams are often faced with two suboptimal choices: halt feature development to resolve all errors simultaneously, or leave type checking disabled and manually opt in file-by-file using // @ts-check.

The manual opt-in approach frequently fails because developers forget to add the comment to new files, allowing untyped or error-prone code to continue entering the codebase.

How the Combined Approach Works

The combination of checkJs and // @ts-nocheck flips the default behavior of the compiler across the repository through a three-step implementation:

  1. Enable Global Checking: Set "allowJs": true and "checkJs": true in the project's tsconfig.json. This instructs the TypeScript compiler to analyze and type-check every JavaScript file it encounters.
  2. Bulk Opt-Out Existing Files: Run an automated script across the codebase that prepends // @ts-nocheck to the very first line of every existing .js and .jsx file.
  3. Establish a Clean Baseline: The TypeScript compiler now runs across the entire project with zero reported errors, enabling TypeScript to be added to continuous integration (CI) pipelines immediately.

Core Benefits in Phased Migrations

Automatic Enforcement on New Code
Because checkJs is enabled at the compiler level, any newly created JavaScript or TypeScript file is type-checked automatically. A developer must actively go out of their way to add // @ts-nocheck to bypass type checks, preventing technical debt from growing during the migration phase.

Granular, Low-Risk Refactoring
Legacy files can be upgraded one at a time. A developer simply removes the // @ts-nocheck line from a target file, addresses the reported errors (either through JSDoc annotations or by converting the file extension to .ts), and submits a focused, easily reviewable pull request.

Measurable Progress Metrics
This strategy provides engineering teams with an exact metric for migration progress. By running a simple search or script to count the remaining instances of // @ts-nocheck across the repository, teams can track their burndown rate over time until every file is migrated and the directive is completely eliminated.
