How TypeScript Infers Object.keys and Object.entries

This article explores how TypeScript handles type inference for Object.keys and Object.entries, explains why it defaults to broader types like string[] rather than strict union types of object keys, and demonstrates how to safely override this behavior using custom utility functions and type assertions when strictness is required.

The Default Typing Behavior

When calling Object.keys() and Object.entries() in TypeScript, the standard library definitions yield broad, non-specific return types rather than types strictly tied to the provided object's shape:

const user = {
  id: 1,
  name: "Alice",
  isAdmin: true,
};

// Return type: string[]
const keys = Object.keys(user);

// Return type: [string, any][] (or [string, number | string | boolean][])
const entries = Object.entries(user);

Instead of typing keys as ("id" | "name" | "isAdmin")[], TypeScript assigns the type string[]. Similarly, Object.entries(user) types the keys in each tuple as string rather than the specific key union.

Why TypeScript Uses string[]

TypeScript’s type system is structural and "open" by design. An object type in TypeScript represents a minimum requirement rather than an exhaustive boundary. A value is allowed to have more properties at runtime than are declared in its type.

Consider the following example involving subtyping:

interface User {
  id: number;
  name: string;
}

const detailedUser = {
  id: 1,
  name: "Alice",
  role: "admin",
  lastLogin: new Date(),
};

// Valid assignment due to structural subtyping
const user: User = detailedUser;

// At runtime, keys are ["id", "name", "role", "lastLogin"]
const keys = Object.keys(user);

If TypeScript typed Object.keys(user) as (keyof User)[], the type would be ("id" | "name")[]. However, the runtime array actually contains "role" and "lastLogin". If the compiler assumed only "id" and "name" existed, downstream operations could access unexpected properties or fail runtime invariants. Because TypeScript cannot guarantee that an object has no extra runtime properties, it safely falls back to string[].

Working with Object.entries

Object.entries encounters the same issue with keys. Its standard lib declaration resolves to [string, any][] or [string, T[keyof T]][]. The key is always typed as string to account for excess runtime properties. Additionally, when using heterogeneous objects, the value type becomes a union of all possible property types across the object.

const config = {
  timeout: 3000,
  debug: true,
};

// Type: [string, number | boolean][]
const configEntries = Object.entries(config);

Inside a forEach or for...of loop over configEntries, TypeScript cannot discern which specific key corresponds to which specific value type in each iteration.

Enforcing Strict Types

When you are certain an object contains only the keys defined in its type, you can use type assertions or generic helper functions to narrow the types.

Strict Object.keys Helper

function getKeys<T extends object>(obj: T): (keyof T)[] {
  return Object.keys(obj) as (keyof T)[];
}

const userKeys = getKeys(user); // Type: ("id" | "name")[]

Strict Object.entries Helper

To capture exact key-value pairs without losing the association between the key and its specific type, use a generic helper with a mapped type:

type Entries<T> = {
  [K in keyof T]: [K, T[K]];
}[keyof T][];

function getEntries<T extends object>(obj: T): Entries<T> {
  return Object.entries(obj) as Entries<T>;
}

const userEntries = getEntries(user);
// Type: (["id", number] | ["name", string] | ["isAdmin", boolean])[]

By understanding TypeScript's open type system, you can accept string[] for open object types or deliberately introduce narrow helpers when working with strictly defined models.
