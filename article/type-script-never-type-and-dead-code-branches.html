TypeScript Never Type and Dead Code Branches

The never type in TypeScript represents values that can never occur, serving as the foundational mechanism for identifying unreachable code and ensuring exhaustive type checking. By leveraging control flow analysis, TypeScript automatically narrows types through conditional blocks; when all possible variants of a type have been accounted for, any remaining code paths are assigned the never type. This article explores how the compiler uses never to detect dead code branches, enforce exhaustiveness, and prevent runtime errors before code reaches production.

The Role of the Bottom Type

In type theory, never is the bottom type, meaning it is a subtype of every other type, but no type is a subtype of never (except never itself). Consequently, no runtime value can satisfy a variable of type never. Functions that never return—such as those containing infinite loops or functions that unconditionally throw exceptions—have a return type of never.

When analyzing control flow, TypeScript applies this concept to identify execution paths that cannot logically execute under normal conditions.

Type Narrowing and Dead Code Identification

TypeScript uses control flow analysis to narrow variable types sequentially through conditionals, such as if, else, and switch statements. When a union type is completely exhausted across these conditions, the compiler narrows the variable in the final unreachable branch down to never.

Consider the following example:

type Status = "success" | "failure";

function handleStatus(status: Status) {
  if (status === "success") {
    // status is narrowed to "success"
    return "Operation succeeded";
  } else if (status === "failure") {
    // status is narrowed to "failure"
    return "Operation failed";
  } else {
    // status is narrowed to never
    return status;
  }
}

In the else block, all valid states of status have been checked. Because there are no remaining valid values, TypeScript assigns never to status. If a developer writes logic inside this block, the compiler treats it as dead code because the branch cannot be reached given the defined types.

Exhaustive Type Checking

The most common practical application of never representing dead branches is exhaustive checking in pattern matching. Developers can intentionally assign a narrowed variable to a never-typed variable in a fallback branch. If a new member is later added to the union type without updating the conditional branches, the fallback branch stops being dead code, causing a compile-time error.

type Shape = 
  | { kind: "circle"; radius: number }
  | { kind: "square"; side: number };

function getArea(shape: Shape): number {
  switch (shape.kind) {
    case "circle":
      return Math.PI * shape.radius ** 2;
    case "square":
      return shape.side ** 2;
    default:
      // If all branches are handled, shape is of type never
      const _exhaustiveCheck: never = shape;
      return _exhaustiveCheck;
  }
}

If a new variant, such as { kind: "triangle"; base: number; height: number }, is added to the Shape union, shape in the default block ceases to be dead code. Its type becomes triangle instead of never. Because a variable of type triangle cannot be assigned to type never, TypeScript immediately raises a type error, alerting the developer to handle the missing case.

Compiler-Level Dead Code Elimination

When TypeScript's allowUnreachableCode compiler option is set to false, the compiler directly flags statements following never results or within never branches as errors. This integration ensures that dead code resulting from impossible conditions or unhandled states is highlighted immediately during compilation, preventing dead or misleading logic from persisting in the codebase.
