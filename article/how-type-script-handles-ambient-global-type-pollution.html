How TypeScript Handles Ambient Global Type Pollution

Ambient declaration files (.d.ts) provide type information for JavaScript code without altering runtime output, but without top-level import or export statements, they treat their contents as globally accessible. This behavior frequently leads to global type pollution, namespace collisions, and shadowed types across large codebases. TypeScript handles and mitigates this issue through module isolation boundaries, deliberate global augmentation mechanisms, compiler flags that restrict ambient type discovery, and strict declaration-merging rules.

In TypeScript, any file lacking a top-level import or export statement is classified as a script rather than a module. Types declared within scripts automatically merge into the global execution context. When a package or local declaration file declares types in this manner, those types become visible across the entire compilation context—even in files that never explicitly referenced or imported them.

The primary mechanism to contain ambient declarations is converting script files into external modules. Adding export {} to an ambient .d.ts file immediately drops it out of the global scope, encapsulating all internal types. Once a file is treated as a module, its declarations are isolated and must be explicitly exported and imported where needed, entirely preventing unintentional global pollution.

When genuine global augmentation is required—such as modifying window, process.env, or global prototypes—TypeScript requires the use of the declare global block within a module context. This separates global additions from module-scoped types. Developers can declare localized internal types safely while strictly scoping global modifications inside an explicit block:

export {}; // Marks the file as a module

declare global {
  interface Window {
    customAnalytics: () => void;
  }
}

Beyond file-level scoping, TypeScript gives developers control over ambient type loading through tsconfig.json. By default, the compiler scans all visible node_modules/@types directories and includes them in the global scope. This behavior can be restricted using the types array under compilerOptions. Specifying an explicit list of packages (for example, "types": ["node", "jest"]) instructs TypeScript to ignore all other ambient packages found in node_modules, directly cutting off untrusted or conflicting global definitions.

Similarly, configuring typeRoots allows teams to control the directories where TypeScript looks for declaration files, while the include, exclude, and files settings ensure that rogue internal .d.ts scripts are not inadvertently sucked into the compilation program.

When two ambient declarations introduce the same identifier, TypeScript relies on declaration merging. If the identifier is an interface, TypeScript merges the properties from both declarations into a single definition. However, if the merged properties possess incompatible types, or if conflicting declarations use non-mergeable constructs such as type aliases, const, or class, the compiler issues an immediate error (such as Duplicate identifier). This strict collision detection prevents silent type mutations from propagating through the project.
