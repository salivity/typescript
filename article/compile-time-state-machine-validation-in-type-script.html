Compile-Time State Machine Validation in TypeScript

This article demonstrates how to leverage TypeScript’s advanced type system to formally validate finite state machines (FSMs) directly at compile time. By utilizing discriminated unions, mapped types, generic constraints, and the satisfies operator, you can mathematically prove the correctness of state transitions, reject impossible transitions, and ensure exhaustive event handling before any code executes in production.

Modeling States and Events

Formal validation requires defining your states and events as strict literal types. By restricting states and events to string literal unions, TypeScript can track and verify every possible permutation of your system.

type State = 'idle' | 'loading' | 'success' | 'error';

type Event =
  | { type: 'FETCH' }
  | { type: 'RESOLVE'; data: string }
  | { type: 'REJECT'; error: Error }
  | { type: 'RETRY' };

Defining the Transition Matrix

A state machine consists of a set of valid states, a set of inputs (events), and a transition function mapping a (CurrentState, Event) pair to a NextState. To validate this structure at compile time, model the transitions as a type-level adjacency list:

type TransitionMap = {
  idle: {
    FETCH: 'loading';
  };
  loading: {
    RESOLVE: 'success';
    REJECT: 'error';
  };
  error: {
    RETRY: 'loading';
  };
  success: {};
};

Enforcing Strict Transitions via Generic Constraints

To guarantee that the machine definition contains no illegal states, missing events, or transitions to non-existent states, you can implement a type-level validator. The validator checks that every key exists within the State union and that every target state is also a member of State.

type ValidTransitions<T> = {
  [K in keyof T]: K extends State
    ? {
        [E in keyof T[K]]: E extends Event['type']
          ? T[K][E] extends State
            ? T[K][E]
            : `Error: Target state '${T[K][E] & string}' is not a valid State`
          : `Error: Event '${E & string}' is not a valid Event`;
      }
    : never;
};

function defineMachine<T extends ValidTransitions<T>>(transitions: T): T {
  return transitions;
}

If a developer attempts to transition from 'idle' to an invalid state such as 'unknownState', TypeScript catches the error immediately during compilation:

const machine = defineMachine({
  idle: {
    FETCH: 'loading',
  },
  loading: {
    // Type Error: Target state 'invalid' is not a valid State
    RESOLVE: 'invalid', 
    REJECT: 'error',
  },
  error: {
    RETRY: 'loading',
  },
  success: {},
});

Validating Execution and Preventing Illegal Transitions

Compile-time verification must extend beyond the declaration phase into the execution phase. A strictly typed transition function prevents passing events that are invalid for the current state:

function transition<
  CurrentState extends keyof TransitionMap,
  EventType extends keyof TransitionMap[CurrentState]
>(
  currentState: CurrentState,
  event: EventType
): TransitionMap[CurrentState][EventType] {
  // Implementation logic
  return {} as TransitionMap[CurrentState][EventType];
}

// Compiles successfully: returns 'loading'
const nextState = transition('idle', 'FETCH');

// Compile-time error: Argument of type '"RESOLVE"' is not assignable to parameter of type '"FETCH"'
const invalidTransition = transition('idle', 'RESOLVE');

Exhaustiveness Checking with Discriminated Unions

When handling side effects or state-dependent logic, enforce formal completeness using TypeScript's never type. This ensures that every declared state is accounted for:

function handleState(state: State): void {
  switch (state) {
    case 'idle':
      break;
    case 'loading':
      break;
    case 'success':
      break;
    case 'error':
      break;
    default: {
      // If a new state is added to `State` without handling it here,
      // TypeScript throws a compile-time error.
      const _exhaustiveCheck: never = state;
      return _exhaustiveCheck;
    }
  }
}

By encoding transition rules directly into TypeScript's type system, the compiler acts as a formal verification tool. Any structural defect, orphaned state, or impossible transition produces an immediate type-checking failure, eliminating entire classes of runtime errors.
