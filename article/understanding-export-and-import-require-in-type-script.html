Understanding export = and import = require in TypeScript

This article provides a comprehensive overview of how TypeScript handles CommonJS interoperability using the legacy export = and import = require() syntax. You will learn the mechanics behind these constructs, how they map directly to Node.js module behavior, and why they remain necessary for consuming and authoring traditional CommonJS packages alongside modern ECMAScript module patterns.

The CommonJS vs. ECMAScript Mismatch

In standard Node.js CommonJS (CJS), a module can export any single entity directly by assigning it to module.exports:

// math.js (CommonJS)
module.exports = function add(a, b) {
  return a + b;
};

ECMAScript modules (ESM), however, do not support reassigning the entire module namespace. ESM only supports named exports and a default export (export default). When TypeScript compiles an ESM export default to CommonJS, it generates an object with a default key:

// Compiled output of `export default function add() {}`
exports.default = add;

This divergence creates interoperability issues. If a CommonJS library assigns a function or class directly to module.exports, attempting to consume it with import add from './math' can fail or require awkward workarounds like add.default() unless synthetic interop flags are active.

The Role of export =

The export = syntax acts as TypeScript's native equivalent to Node's module.exports = value. It informs the TypeScript compiler that the exported entity represents the entire module's exported value, rather than a namespace member or a .default property.

// zipCodeValidator.ts
class ZipCodeValidator {
  isAcceptable(s: string) {
    return s.length === 5;
  }
}

export = ZipCodeValidator;

When emitted to CommonJS, this compiles directly to:

// zipCodeValidator.js
var ZipCodeValidator = /** @class */ (function () { ... })();
module.exports = ZipCodeValidator;

If you use export =, you cannot combine it with other top-level export statements within the same file.

The Role of import = require()

To consume a module declared with export =, TypeScript provides the matching import identifier = require('module-path') syntax. This models Node’s runtime const identifier = require('module-path') call while pulling in TypeScript's compile-time type definitions.

// consumer.ts
import ZipCodeValidator = require('./zipCodeValidator');

const validator = new ZipCodeValidator();
console.log(validator.isAcceptable('12345'));

When compiled to CommonJS, TypeScript emits:

// consumer.js
const ZipCodeValidator = require('./zipCodeValidator');
const validator = new ZipCodeValidator();
console.log(validator.isAcceptable('12345'));

This syntax bypasses the ESM namespace wrapper entirely, directly assigning the exact object, function, or class exported by the dependency.

Relationship to esModuleInterop

Modern TypeScript configurations often enable esModuleInterop: true in tsconfig.json. This compiler flag generates helper functions (__importDefault and __importStar) at compile time, allowing developers to use standard ESM import syntax on CommonJS modules:

// Requires "esModuleInterop": true
import ZipCodeValidator from './zipCodeValidator';

While esModuleInterop facilitates writing standard ESM syntax, export = and import = require() remain relevant:

  1. Exact CommonJS Modeling: import = require() provides an exact, 1:1 typed mapping to CommonJS's native require without relying on synthetic default transformations.
  2. Library Definitions: Many legacy @types/* definition files for popular npm libraries still rely on export = to accurately type packages that assign functions or classes directly to module.exports.
  3. Dual Compilation Targets: When emitting code strictly intended for Node.js CommonJS runtimes without transpilation helpers, export = guarantees no synthetic wrapper code is introduced.
