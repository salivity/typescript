Tail Call Elimination in TypeScript Conditional Types

Recursive conditional types allow you to model complex data transformations at the type level, but deeply nested operations often trigger compiler recursion limits. This article explains how TypeScript applies tail call elimination (TCE) to conditional types, why standard recursive types fail, and how to refactor your types using accumulator patterns to safely increase recursion depth limits from roughly 50 to nearly 1,000 iterations.

The Recursion Limit Problem

By default, TypeScript imposes a conservative recursion limit (typically around 50 iterations) on conditional types to prevent compiler crashes and infinite loops:

// Error: Type instantiation is excessively deep and possibly infinite.
type Reverse<T extends any[]> = T extends [infer Head, ...infer Tail]
  ? [...Reverse<Tail>, Head]
  : [];

In this non-tail-recursive pattern, Reverse<Tail> must resolve before the outer tuple [..., Head] can be constructed. The TypeScript compiler must retain the intermediate context on its internal evaluation stack for each element, hitting the recursion ceiling quickly.

How TypeScript Evaluates Tail Calls

Introduced in TypeScript 4.5, tail call elimination detects when the result of a conditional branch is directly another type instantiation, with no deferred work.

When a type branch returns an unresolved invocation directly, TypeScript unwinds the stack frame and loops internally instead of adding a new frame to the type checker's call stack. This raises the recursion limit up to 1,000 steps.

To trigger tail call optimization, the recursive call must sit in the tail position. It cannot be wrapped inside:

  • Tuples (e.g., [Recurse<T>])
  • Template literal types (e.g., ${Recurse<T>})
  • Unions or intersections (e.g., Recurse<T> | null)
  • Indexed access types (e.g., Recurse<T>[number])

The Accumulator Pattern

To place the recursive call in the tail position, you must push the intermediate state forward through an accumulator generic parameter instead of evaluating operations on the return path.

Example: Array Reversal

Refactoring the previous Reverse type using an accumulator:

type Reverse<T extends any[], Acc extends any[] = []> = 
  T extends [infer Head, ...infer Tail]
    ? Reverse<Tail, [Head, ...Acc]> // Direct recursive call in tail position
    : Acc;

In this version, [Head, ...Acc] is computed as an argument to the next iteration rather than being constructed around the result of Reverse<Tail>. Because the true branch evaluates directly to Reverse<...>, TypeScript eliminates the call stack frame.

Example: String Splitting

The same pattern applies to string manipulation:

// Non-tail-recursive (Fails on long strings)
type SplitNonTail<S extends string, Delimiter extends string> =
  S extends `${infer Head}${Delimiter}${infer Tail}`
    ? [Head, ...SplitNonTail<Tail, Delimiter>]
    : [S];

// Tail-recursive (Optimized)
type Split<
  S extends string,
  Delimiter extends string,
  Acc extends string[] = []
> = S extends `${infer Head}${Delimiter}${infer Tail}`
  ? Split<Tail, Delimiter, [...Acc, Head]>
  : [...Acc, S];

Rules for Writing Tail-Recursive Types

  1. Supply Default Accumulators: Provide a default value for your accumulator (e.g., Acc = [] or Acc = "") so consumer code does not need to pass an initial empty state.
  2. Compute Inputs, Not Outputs: Modify the inputs passed to the next recursive invocation instead of modifying the output returned by it.
  3. Avoid Intermediate Branching on Recursion: Ensure that conditional logic determines whether to recurse, not what to do with the result of the recursion.
