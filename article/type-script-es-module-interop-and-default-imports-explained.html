TypeScript esModuleInterop and Default Imports Explained

The esModuleInterop compiler option in TypeScript bridges the behavioral divide between CommonJS and ECMAScript (ES) modules, allowing developers to import CommonJS modules using standard ES module default import syntax. By automatically emitting helper functions that wrap imported modules, TypeScript ensures that CommonJS packages without an explicit default export behave seamlessly alongside native ES modules at both compile time and runtime.

The Incompatibility Between CommonJS and ES Modules

The ECMAScript specification draws a strict distinction between named exports and default exports. An ES module can have multiple named exports alongside a single default export:

// ES Module
export const namedValue = 42;
export default function defaultFunction() {}

Conversely, CommonJS exports a single entity using module.exports, which is traditionally an object, function, or primitive:

// CommonJS (e.g., standard Node.js library)
module.exports = function () { /* ... */ };

Under strict ECMAScript specification rules, importing a CommonJS module via import express from 'express' requires the target module to contain a property explicitly named default. Because vanilla CommonJS modules export directly to module.exports without a default key, standard ES module loaders would treat the default import as undefined.

Before esModuleInterop, TypeScript followed these strict rules by requiring developers to use either namespace imports or legacy TypeScript-specific syntax:

// Legacy TypeScript approaches
import * as express from 'express';
// or
import express = require('express');

Treating a CommonJS module as a namespace object (import * as ...) can lead to runtime crashes if the exported entity is a function or primitive rather than a plain object.

How esModuleInterop Fixes Default Imports

When you set "esModuleInterop": true in your tsconfig.json, TypeScript changes the JavaScript output generated during compilation by injecting runtime helper functions—primarily __importDefault and __importStar.

When TypeScript encounters a default import from a CommonJS module:

import express from 'express';
const app = express();

It compiles the code to call the __importDefault runtime helper:

var __importDefault = (this && this.__importDefault) || function (mod) {
    return (mod && mod.__esModule) ? mod : { "default": mod };
};

const express_1 = __importDefault(require("express"));
const app = (0, express_1.default)();

The Mechanism of __importDefault

The helper evaluates the imported module at runtime:

  1. Detection of ES Modules: It checks if the imported module has the __esModule property set to true. This flag is standard across tools like Babel and Webpack to denote that a module was originally an ES module compiled down to CommonJS. If __esModule is present, the helper returns the module as-is, preserving its native default export.
  2. Synthetic Default Creation: If __esModule is not present (standard CommonJS), the helper wraps the entire module.exports object inside a new object with a default property: { "default": mod }.

Because the CommonJS export is wrapped in an object exposing a default key, accessing .default on the imported object resolves to the original module.exports entity, satisfying both ECMAScript expectations and Node.js execution behavior.

Interaction with allowSyntheticDefaultImports

Enabling esModuleInterop also automatically enables the allowSyntheticDefaultImports flag.

  • allowSyntheticDefaultImports only alters the TypeScript type-checker, allowing you to write import express from 'express' without compiler errors, even if the type definitions lack a default export. However, it does not change the emitted JavaScript code.
  • esModuleInterop provides both the compile-time type compatibility and the necessary runtime code emission (__importDefault) to prevent runtime failures.
