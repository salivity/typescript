TypeScript Interface vs Type Intersection Performance

In TypeScript, both interface extension (interface Child extends Parent) and type intersection (type Child = Parent & Other) allow developers to compose types, but they differ significantly in compiler performance. The TypeScript compiler optimizes interfaces by caching their flat object structures and validating property conflicts eagerly. Conversely, type intersections construct compound types that the compiler must recursively evaluate across all constituent parts, resulting in higher memory usage, slower type-checking times, and reduced IDE responsiveness in large codebases.

Flat Object Shapes vs. Compound Types

When an interface extends another interface, TypeScript builds a single, flat type representing the merged shape. This flat representation is computed once and cached internally based on the interface's unique identifier. When the compiler needs to check whether a value satisfies that interface elsewhere, it performs a simple lookup against this pre-calculated shape.

Type intersections (&) do not immediately flatten properties. Instead, TypeScript maintains an internal list of all intersecting members. Every time the compiler references an intersected type, it must evaluate each component within the intersection to verify properties, check relationships, and construct synthetic representations. This recursive evaluation adds overhead during every type-checking pass.

Internal Caching Mechanisms

The TypeScript compiler uses identity-based caching for interfaces. Because interfaces are declared with fixed names and rigid inheritance trees, TypeScript can cache their evaluation results globally across files.

Intersections are structural operations. Even if two intersected types appear identical in different parts of a project, the compiler often treats them as distinct compound constructs unless they resolve to identical internal object instances. This lack of aggressive caching forces the compiler to re-compute relationships across intersecting branches frequently.

Property Conflict Resolution

Interface extension enforces strict conflict resolution at declaration time. If a child interface attempts to override a parent property with an incompatible type, the compiler immediately issues an error:

interface Parent {
  id: string;
}

// Compiler error: Types of property 'id' are incompatible
interface Child extends Parent {
  id: number;
}

Because conflicting declarations fail immediately, the compiler never has to maintain ambiguous shapes.

Type intersections handle conflicts by combining types rather than rejecting them:

type Parent = { id: string };
type Child = Parent & { id: number };
// Child['id'] resolves to: string & number (never)

By resolving the conflicting property to never, the compiler postpones error detection until an attempt is made to assign a value to that property. To handle this, the type checker must construct and track synthetic intersections for every conflicting property throughout the type tree, introducing substantial computational overhead.

Impact on Scale and Compile Times

In small applications, the performance difference between interfaces and intersections is negligible. However, in large enterprise codebases with thousands of models or deep component hierarchies, using intersections extensively creates a cumulative penalty:

  • Increased Build Times: Incremental and cold builds take longer as the compiler spends CPU cycles computing intersection trees.
  • IDE Latency: Features such as auto-complete, inline type hints, and hover previews slow down because language server queries require continuous re-evaluation of un-cached compound types.
  • Memory Footprint: The TypeScript compiler process consumes significantly more memory storing complex intersection trees compared to simple interface tables.

Recommendation

For composing object shapes, default to using interface extends rather than type intersections. Reserve intersection types (&) specifically for cases where interfaces are not supported, such as combining union types, primitives, or dynamically mapped types.
