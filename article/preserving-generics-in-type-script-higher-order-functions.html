Preserving Generics in TypeScript Higher-Order Functions

Higher-order functions in TypeScript often unintentionally erase or prematurely resolve generic type arguments, reducing dynamic functions to fixed or unknown types. To preserve generic type arguments, TypeScript relies on higher-rank polymorphism, where the returned function retains its own generic type parameters rather than binding them at the wrapper level. This article explains the mechanics of how TypeScript manages generic signatures within higher-order functions, demonstrating how to properly type wrappers, decorators, and composition utilities so that consumer type inference remains intact.

The Problem: Premature Type Instantiation

A common pitfall occurs when placing type parameters on the outer higher-order function rather than on the returned function itself. When type arguments are declared on the outer function, TypeScript attempts to infer or lock those types at the moment the wrapper is called, rather than when the resulting function is executed.

Consider an identity wrapper:

// Incorrect: Generics instantiated prematurely
function createLogger<T>(fn: (arg: T) => T) {
  return (arg: T) => {
    console.log("Input:", arg);
    return fn(arg);
  };
}

If you pass a generic function identity<T>(x: T): T into createLogger, TypeScript instantiates T immediately (often defaulting to unknown or inferring from contextual usage at the call site). The resulting function loses its ability to adapt dynamically to different input types across multiple invocations.

The Solution: Rank-2 Polymorphic Signatures

To preserve generic behavior, the higher-order function must return a function that introduces its own generic parameter. This technique is known in type theory as higher-rank polymorphism (or rank-2 types).

Instead of parameterizing the outer function, define the return type as a generic callable signature:

function withLogging(fn: (<T>(arg: T) => T)) {
  return <T>(arg: T): T => {
    console.log("Calling with:", arg);
    const result = fn(arg);
    console.log("Result:", result);
    return result;
  };
}

// Target generic function
const identity = <T>(x: T): T => x;

// Wrapped function preserves generic behavior
const loggedIdentity = withLogging(identity);

const num = loggedIdentity(42);       // Inferred as number
const str = loggedIdentity("hello");  // Inferred as string

In this pattern:

  1. fn is explicitly typed to require a generic function <T>(arg: T) => T.
  2. The returned wrapper declares <T>(arg: T): T.
  3. Type instantiation is deferred until loggedIdentity is called by the consumer.

Preserving Arbitrary Signatures with Generic Tuples

When creating higher-order functions that accept functions with arbitrary arguments and return values, you can combine generic rest parameters with the generic wrapper pattern.

function trace<TArgs extends any[], TReturn>(
  fn: (...args: TArgs) => TReturn
): (...args: TArgs) => TReturn {
  return (...args: TArgs): TReturn => {
    console.log("Arguments:", args);
    return fn(...args);
  };
}

While the implementation above works well for non-generic functions or specific calls, TypeScript cannot natively infer that an input function has an uninstantiated generic signature using pure type parameter inference (such as TArgs extends any[]).

To preserve generic capabilities across arbitrary functions, define an interface for the callable shape:

interface GenericTransformer {
  <T, R>(item: T, transform: (val: T) => R): R;
}

function decorateTransformer(fn: GenericTransformer): GenericTransformer {
  return <T, R>(item: T, transform: (val: T) => R): R => {
    console.log("Processing item:", item);
    return fn(item, transform);
  };
}

By explicitly typing both the input parameter and the return value with the call signature interface, the compiler enforces that the output function remains generic across all invocation sites.

Higher-Order Functions with Currying

Currying requires passing type arguments from one function layer to the next. When preserving generics in curried patterns, ensure each returned function defines the exact type variables it needs to capture:

function createPropExtractor<K extends PropertyKey>(key: K) {
  return <T extends Record<K, any>>(obj: T): T[K] => {
    return obj[key];
  };
}

const getName = createPropExtractor("name");

const user = { name: "Alice", age: 30 };
const product = { name: "Laptop", inStock: true };

const userName = getName(user);       // Inferred as string
const productName = getName(product); // Inferred as string

In this implementation, key is bound at the first invocation, while the object type T remains generic until the returned function is called. This separation allows getName to accept any object structure containing a name property while computing the exact property type for each unique object passed to it.
