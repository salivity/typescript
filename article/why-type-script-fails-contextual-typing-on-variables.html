Why TypeScript Fails Contextual Typing on Variables

When developers extract an inline callback into a separate variable in TypeScript, they often encounter type errors because parameters suddenly revert to any. This article explains contextual typing, why TypeScript cannot infer types across decoupled variable declarations, and the compiler mechanics that enforce this behavior.

How Contextual Typing Works

Contextual typing occurs when the type of an expression is inferred from its location in the code, rather than from the expression itself. When you pass a callback directly to a higher-order function like Array.prototype.map, TypeScript knows the signature that map expects:

const numbers = [1, 2, 3];
numbers.map((num) => num * 2); // 'num' is contextually typed as 'number'

In this inline form, the compiler uses the "target type" defined by Array<number>.prototype.map to push type information downward into the callback’s parameter list.

The Decoupling Problem

When you extract the callback into an independent variable, the inference mechanism breaks:

// Parameter 'num' implicitly has an 'any' type
const double = (num) => num * 2; 

[1, 2, 3].map(double);

TypeScript fails to infer num here because of how the compiler orders type evaluation.

1. Isolated Variable Evaluation

TypeScript determines types locally and unidirectionally. When evaluating const double = (num) => num * 2, the compiler evaluates the variable declaration in total isolation. At the moment of declaration, there is no target type available to inform what num should be. Consequently, TypeScript falls back to any (or triggers a compiler error if noImplicitAny is enabled).

2. Lack of Reverse Flow (No Whole-Program Inference)

TypeScript does not use full unification or Hindley-Milner type inference across statement boundaries. It will not look ahead to future calls—such as [1, 2, 3].map(double)—to retroactively infer the signature of double.

Implementing look-ahead type inference would introduce significant architectural trade-offs:

  • Ambiguity: If double is later passed to both [1, 2, 3].map(double) and ['a', 'b'].map(double), the compiler would face conflicting type constraints.
  • Performance: Scanning the entire codebase to solve for variable types creates a combinatorial explosion in compile times.
  • Poor Error Locality: If a parameter is typed retroactively, type mismatch errors would be reported far from where the actual mistake occurred, making debugging difficult.

Solutions for Decoupled Callbacks

To maintain type safety when separating callbacks, you must supply the context that the compiler no longer has access to.

Explicit Parameter Types

The simplest approach is to annotate the function's parameters directly:

const double = (num: number) => num * 2;
[1, 2, 3].map(double);

Explicit Function Signatures

If you are writing functions that must conform to a specific contract, you can type the variable explicitly:

type NumberMapper = (value: number) => number;

const double: NumberMapper = (num) => num * 2;
[1, 2, 3].map(double);

Parameter Helper Types

When reusing complex library signatures, you can extract the parameter types using TypeScript utility types:

import { type RequestHandler } from 'express';

const customHandler: RequestHandler = (req, res) => {
  res.send('Success');
};

By providing the type context at the site of declaration, you satisfy TypeScript's requirement for localized, unidirectional type inference.
