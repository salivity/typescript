TypeScript Signals: Compile-Time Safety and Tracking

Modern reactive state libraries like Signals achieve compile-time tracking and type safety in TypeScript by combining fine-grained generic interfaces, type-level variance annotations, read-only constraints, and phantom types. This article explores how these libraries leverage TypeScript's structural type system to catch missing dependencies, prevent illegal state mutations, and validate reactive dependency chains before runtime execution occurs.

Generic Interfaces and Mutability Separation

At the core of compile-time safety is the strict structural separation between reading and writing reactive values. Modern implementations define distinct interfaces for readable signals and mutable signals:

export interface ReadonlySignal<T> {
  readonly value: T;
  subscribe(fn: (value: T) => void): () => void;
}

export interface Signal<T> extends ReadonlySignal<T> {
  value: T; // mutable getter and setter
  set(value: T): void;
  update(fn: (prev: T) => T): void;
}

By decoupling these capabilities into distinct generic interfaces, libraries prevent unauthorized mutations at compile time. Functions that should only consume data accept ReadonlySignal<T>. Attempting to reassign .value or call .set() on a derived or consumed signal produces an immediate compiler error rather than a runtime failure.

Type Variance Annotations

To ensure that derived signals can be safely passed to functions expecting broader data types, libraries use TypeScript’s out and in variance annotations.

export interface ReadonlySignal<out T> {
  readonly value: T;
}

Marking T as covariant (out T) ensures that a ReadonlySignal<Dog> is structurally assignable to a ReadonlySignal<Animal> at compile time. Conversely, writable signals are invariant because they both consume and produce T. Explicit variance annotations allow TypeScript to evaluate signal assignments faster and prevent unsafe assignments where a write operation could compromise type integrity.

Phantom Types and Nominal Typing

TypeScript utilizes a structural type system, meaning two objects with the same shape are considered identical. If an object structurally matches { value: T }, the compiler accepts it as a signal, even if it lacks reactive internals.

Modern signal libraries prevent this using phantom types or branded types:

declare const SignalBrand: unique symbol;

export interface Signal<T> {
  readonly [SignalBrand]: void;
  value: T;
}

The brand symbol does not exist at runtime and adds zero runtime overhead. At compile time, however, TypeScript rejects standard objects that mimic the signal interface, ensuring that only genuine signals created via authorized factory functions can be passed into reactive operators.

Automated Return Type Inference in Computed Signals

Tracking dependencies accurately requires precise inference across transformation pipelines. Libraries like Preact Signals or Angular Signals use higher-order generics to automatically track and infer derived states:

function computed<T>(fn: () => T): ReadonlySignal<T>;

Because TypeScript evaluates the return type of fn, the resulting derived signal automatically inherits the exact narrowed type, including union types or nullability checks performed within the compute closure:

const count = signal<number>(0);
// Inferred at compile-time as ReadonlySignal<"even" | "odd">
const parity = computed(() => (count.value % 2 === 0 ? "even" : "odd"));

This ensures that downstream consumers are statically type-safe without requiring explicit type casts.

Compile-Time Context and Scope Enforcement

While dependency graphs are linked dynamically at runtime via subscriber stacks, TypeScript enforces scope boundaries statically using context types.

By typing computed closures as pure getter functions (() => T) and isolating mutations to discrete methods, libraries use TypeScript's type checker to disallow side effects. For example, by typing compute callbacks to disallow arguments, TypeScript prevents users from passing external mutation tokens into pure reactive computations. If an effect or computed block attempts to invoke an invalid operation, the compiler catches the violation prior to bundling.
