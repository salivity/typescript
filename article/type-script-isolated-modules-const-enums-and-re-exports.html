TypeScript isolatedModules: Const Enums and Re-exports

The TypeScript compiler option isolatedModules prevents errors caused by single-file transpilers, such as Babel, esbuild, and SWC, which process files independently without a global type graph. By enforcing this flag, TypeScript disallows features like const enum definitions and ambiguous ambient re-exports (export { X }) because these tools cannot resolve cross-file type information during single-pass transpilation.

The Role of isolatedModules

When TypeScript compiles code natively, it builds a complete program graph containing the full semantic understanding of every file, type, and symbol. This allows the compiler to know whether an imported identifier represents an actual JavaScript runtime value or merely a static type definition.

Modern build pipelines frequently offload TypeScript transpilation to tools like Babel, SWC, or Vite. These tools prioritize speed by compiling one file at a time in isolation, without parsing the entire project's type declarations. The isolatedModules flag instructs TypeScript to warn developers when they use language features that cannot be safely transpiled in isolation.

Why const enums Are Disallowed

Under normal TypeScript compilation, const enum statements are fully erased. Instead of generating a runtime object, TypeScript looks up the enum's member values at compile time and inlines the raw literals directly into the consuming code.

When a single-file transpiler encounters an import of a const enum from another module:

// fileA.ts
export const enum Direction {
  Up = "UP",
  Down = "DOWN"
}

// fileB.ts
import { Direction } from "./fileA";
const move = Direction.Up;

A tool transpiling fileB.ts on its own cannot inspect fileA.ts. Because it does not know the actual value of Direction.Up, it cannot inline the value "UP". It also cannot leave Direction.Up as a standard property access because fileA.ts will not emit a runtime Direction object. Because the code would crash at runtime, isolatedModules disallows const enum statements to guarantee that all emitted enums either exist at runtime as real objects or are replaced by string unions.

Why export { X } Ambient Re-exports Are Disallowed

JavaScript code generated from TypeScript must strip away interfaces, type aliases, and other compile-time constructs. When a symbol is re-exported using standard export syntax, a single-file transpiler must decide whether to retain or strip that export:

// types.ts
export interface User {
  id: string;
}

// index.ts
export { User } from "./types";

While compiling index.ts in isolation, the transpiler has no access to ./types.ts. It cannot determine whether User is an interface (which must be erased from the JavaScript output) or a runtime value like a class or const (which must be preserved in the JavaScript output).

If the transpiler guesses incorrectly and emits export { User } from "./types", the resulting JavaScript throws a runtime error because User does not exist in ./types.js. Conversely, if the transpiler strips the export assuming it is a type, it risks dropping actual runtime code.

TypeScript resolves this ambiguity by requiring explicit type-only exports under isolatedModules. Developers must use the type modifier to explicitly declare the intent:

export type { User } from "./types";

With export type, a single-file transpiler can safely and unambiguously remove the entire statement from the JavaScript output without inspecting the referenced file.
