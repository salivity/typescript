TypeScript isolatedDeclarations Type Restrictions

TypeScript's isolatedDeclarations compiler option requires all exported declarations to be easily statically analyzable without full type checking, allowing single-file transpilers to generate declaration (.d.ts) files. Because tools cannot traverse imports or perform complex type inference on an isolated file, this mode imposes strict restrictions on exported signatures, requiring explicit type annotations wherever the type cannot be trivially determined.

Explicit Return Types on Exported Functions

Any exported function, generator, or method must include an explicit return type annotation. TypeScript will not infer the return type from the function body, even if the body consists of a simple return statement:

// Error under isolatedDeclarations
export function add(a: number, b: number) {
  return a + b;
}

// Correct
export function add(a: number, b: number): number {
  return a + b;
}

This restriction applies to:

  • Standard function declarations
  • Arrow functions assigned to exported variables
  • Public and protected class methods
  • Getter and setter accessors

Explicit Parameter Annotations

Parameters of exported functions and methods must have explicit type annotations. TypeScript will not infer parameter types from default parameter values if the inference is complex or if the parameter is a destructured object:

// Error
export const greet = (name = "World") => `Hello, ${name}`;

// Correct
export const greet = (name: string = "World"): string => `Hello, ${name}`;

Untyped rest parameters are also prohibited on exported signatures.

Variable and Constant Exports

Exported variables and constants must have explicit type annotations unless they are initialized with a trivial, literal expression.

Trivial expressions that do not require annotations include:

  • Primitive literals: strings, numbers, booleans, null, and undefined
  • Simple as const expressions on literal values
  • Simple object and array literals consisting only of trivial expressions
// Allowed without annotations
export const COUNT = 10;
export const NAME = "Alice";
export const FLAGS = [true, false] as const;

// Error: Complex expressions require annotations
export const computed = calculateValue(); 

// Correct
export const computed: number = calculateValue();

If an exported constant is initialized by calling a function, instantiating a class, or referencing another variable whose type cannot be verified in isolation, it must have an explicit type annotation.

Public and Protected Class Members

Classes follow the same boundary rules as top-level declarations. Public and protected fields must have explicit type annotations unless assigned a trivial literal:

  • Fields: Public and protected fields must have type annotations if initialized with complex expressions or left uninitialized in the declaration.
  • Private Members: Fields marked with #private or the private keyword do not require type annotations because they do not appear in the public .d.ts output.
  • Methods: Public and protected methods require explicit parameter and return types.

Restrictions on Internal and Unexported Types

When assigning a type annotation to an exported declaration, the referenced type must also be exported. isolatedDeclarations prevents an exported signature from referencing a type alias or interface that cannot be included in the generated declaration file.

Computed Property Names

Classes and objects with computed property keys cannot use arbitrary expressions for key names. The property name must be a trivial literal or a well-known symbol (such as Symbol.iterator). Computed properties generated from complex runtime expressions will trigger an error unless explicitly resolved or typed.
