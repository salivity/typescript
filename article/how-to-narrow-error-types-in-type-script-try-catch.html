How to Narrow Error Types in TypeScript Try-Catch

In modern TypeScript, variables caught in a try-catch block are typed as unknown (or any in legacy configurations). Because JavaScript permits throwing any value—including strings, plain objects, or numbers—TypeScript prevents you from directly accessing properties like error.message. To handle errors safely and avoid runtime exceptions, you must narrow the unknown error type using runtime checks. This article covers the most effective techniques for safely narrowing errors in TypeScript, including instanceof checks, user-defined type guards, and fallback extraction patterns.

Why Caught Errors Are unknown

Under TypeScript's strict mode (specifically the useUnknownInCatchVariables flag enabled in TypeScript 4.0+), catch clauses default to:

try {
  // execute code
} catch (error: unknown) {
  // error.message will throw a compile-time error:
  // 'error' is of type 'unknown'.
}

Since any arbitrary data type can be thrown at runtime via throw "Something went wrong" or throw { code: 500 }, you cannot assume the caught value inherits from JavaScript's native Error prototype.

Method 1: Using the instanceof Operator

The most straightforward way to narrow an error is the JavaScript instanceof operator. When you verify that an object is an instance of Error, TypeScript automatically narrows its type within that block.

try {
  fetchData();
} catch (error: unknown) {
  if (error instanceof Error) {
    // TypeScript now recognizes 'error' as Error
    console.error(error.message);
    console.error(error.stack);
  } else {
    // Handles non-standard thrown values
    console.error("An unexpected error occurred:", error);
  }
}

This pattern also works cleanly with custom error subclasses:

class DatabaseError extends Error {
  public code: number;
  constructor(message: string, code: number) {
    super(message);
    this.code = code;
  }
}

try {
  queryDatabase();
} catch (error: unknown) {
  if (error instanceof DatabaseError) {
    console.error(`Database Error (${error.code}): ${error.message}`);
  } else if (error instanceof Error) {
    console.error(`General Error: ${error.message}`);
  } else {
    console.error("Unknown throw:", error);
  }
}

Method 2: Custom User-Defined Type Guards

When working with plain JSON responses, API errors, or third-party libraries where instanceof checks fail across execution contexts (like iframes or certain serialized boundaries), you can use custom type guards with the is operator.

interface ApiError {
  status: number;
  message: string;
}

function isApiError(error: unknown): error is ApiError {
  return (
    typeof error === "object" &&
    error !== null &&
    "status" in error &&
    "message" in error &&
    typeof (error as Record<string, unknown>).status === "number" &&
    typeof (error as Record<string, unknown>).message === "string"
  );
}

try {
  callExternalApi();
} catch (error: unknown) {
  if (isApiError(error)) {
    console.error(`API Error ${error.status}: ${error.message}`);
  } else {
    console.error("Unrecognized error format");
  }
}

Method 3: Normalizing Errors with a Helper Function

In many applications, the primary goal is simply to extract an error message safely without writing repetitive if-else blocks in every catch statement. A standard helper function can normalize any thrown value into an Error instance or a string:

function toError(maybeError: unknown): Error {
  if (maybeError instanceof Error) {
    return maybeError;
  }

  try {
    return new Error(JSON.stringify(maybeError));
  } catch {
    // Fallback for circular structures or non-serializable objects
    return new Error(String(maybeError));
  }
}

function getErrorMessage(error: unknown): string {
  return toError(error).message;
}

Usage:

try {
  performRiskyOperation();
} catch (error: unknown) {
  const message = getErrorMessage(error);
  displayNotification(message);
}

Summary Checklist

  1. Avoid typing catch variables as any: Doing so bypasses type safety and can cause unhandled runtime exceptions.
  2. Use instanceof Error for standard errors and custom class-based error hierarchies.
  3. Use custom type guards (error is Shape) when validating structured error payloads or serialized responses.
  4. Use an error normalizer to extract strings cleanly when fine-grained error branching is unnecessary.
