Using stripInternal in TypeScript Libraries

The stripInternal compiler option in TypeScript automatically removes declarations marked with the /** @internal */ JSDoc annotation from generated declaration (.d.ts) files. In library development, it solves the problem of exposing private implementation details that must be shared across internal modules, allowing maintainers to keep a clean, reliable, and strictly defined public API for end users.

The Problem in TypeScript Library Design

When building a TypeScript package, you often need to share utility functions, classes, or helper types between different files inside your project. To make these elements accessible across files, you must use the export keyword.

However, exporting a symbol also means TypeScript will include it in the generated .d.ts files if that module is part of the library's public entry point. As a result, consumers of your package can see and import implementation details that were never meant for public consumption, leading to accidental dependencies on unstable code.

How stripInternal Works

When you enable stripInternal, the TypeScript compiler inspects exported elements for the /** @internal */ JSDoc tag during declaration emission. Any construct carrying this annotation is omitted from the resulting .d.ts output.

Enabling the Option

Add stripInternal to the compilerOptions section of your tsconfig.json:

{
  "compilerOptions": {
    "declaration": true,
    "stripInternal": true
  }
}

Code Example

Consider an exported helper function inside your library:

/**
 * A public API function.
 */
export function calculateTotal(price: number, tax: number): number {
  return applyInternalDiscount(price) + tax;
}

/**
 * @internal
 */
export function applyInternalDiscount(price: number): number {
  return price * 0.9;
}

Without stripInternal, the emitted .d.ts file includes both calculateTotal and applyInternalDiscount.

With stripInternal: true, the generated .d.ts file only contains:

export declare function calculateTotal(price: number, tax: number): number;

Key Benefits for Library Authors

  • Cleaner Public API: Consumers only see the intended API surface in their IDE autocomplete, reducing confusion.
  • Freedom to Refactor: Maintainers can modify or delete internal helpers across major versions without introducing breaking changes to public typings.
  • Simpler Architecture: Developers can use standard TypeScript import and export statements across the codebase without relying on complex multi-entry build pipelines to hide types.

Important Considerations

  • Emitted JavaScript is Unaffected: The stripInternal setting only strips typings from .d.ts files. It does not alter the emitted JavaScript files. The underlying functions will still be present in the runtime bundle.
  • Leaked Types: If a public function returns an @internal type or accepts one as a parameter, stripping the type will cause TypeScript errors in the emitted declaration files. Ensure that public signatures only reference non-internal types.
