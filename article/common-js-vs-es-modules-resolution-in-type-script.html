CommonJS vs ES Modules Resolution in TypeScript

Understanding the difference between CommonJS (CJS) and ECMAScript Modules (ESM) resolution is critical for configuring TypeScript projects correctly. While CommonJS resolves dependencies dynamically at runtime using legacy Node.js algorithms, ES module resolution operates statically with stricter requirements regarding file extensions and package boundary rules. This article explores how TypeScript handles both module systems, the compiler options that dictate their behavior, and the key differences in how paths, file extensions, and interop rules are resolved.

Module Syntax and Timing

CommonJS relies on the require() function to load modules synchronously at runtime and uses module.exports or exports to expose values. Because require() is a function call, module paths can be evaluated dynamically.

ES modules use top-level import and export statements. ESM is static; the module specifiers are analyzed and resolved before the code is executed. This static nature allows TypeScript and bundlers to perform optimizations such as tree-shaking, but it also imposes stricter rules during resolution.

The Role of moduleResolution in tsconfig.json

TypeScript uses the moduleResolution compiler option to determine how to resolve import specifiers to their target files:

  • node10 (formerly node): Emulates older Node.js CommonJS behavior. It resolves paths without requiring file extensions and automatically looks for index.js inside directories.
  • node16 / nodenext: Reflects modern Node.js module resolution, supporting both CJS and ESM side-by-side depending on file extensions and package.json configurations.
  • bundler: Designed for tools like Vite or Webpack that understand modern package.json fields (like exports) while still permitting relaxed, extensionless imports.

File Extensions and Directory Imports

The most noticeable difference between CJS and ESM resolution in TypeScript appears when using modern settings like node16 or nodenext:

  • CommonJS Resolution: Allows extensionless imports and automatic directory resolution. Writing import { utils } from "./utils" automatically resolves to ./utils.ts, ./utils.tsx, or ./utils/index.ts.
  • ESM Resolution: Mandates fully specified relative module paths. Because the runtime ECMAScript specification does not perform extension searching, TypeScript requires you to include the output extension in the import. In an ESM setup, you must write import { utils } from "./utils.js" even though the source file is actually utils.ts. Automatic lookup of index.js inside directories is also disallowed in standard ESM.

Package Exports and the Dual Package Hazard

Modern npm packages often provide both CommonJS and ES module builds using the "exports" field in package.json.

Under CommonJS resolution (moduleResolution: "node10"), TypeScript primarily ignores the "exports" map and relies on the legacy "main" and "types" fields.

Under ESM resolution (node16/nodenext), TypeScript respects conditional exports:

  • An ESM import statement searches the "import" condition in exports.
  • A createRequire or CJS context searches the "require" condition.

This prevents the "dual package hazard," where two different instances of a library are unintentionally loaded simultaneously, leading to broken singletons or duplicate code.

Interoperability and Synthetic Defaults

CommonJS modules export a single object, while ES modules distinguish between default exports (export default) and named exports (export const x).

By default, importing a CommonJS module into an ESM context using import foo from "foo" fails in TypeScript because the CommonJS file does not have a formal default export. To bridge this gap, TypeScript provides the esModuleInterop flag. Enabling esModuleInterop introduces helper functions in the emitted output that wrap CommonJS exports, allowing them to be imported seamlessly using standard ES module default syntax.
