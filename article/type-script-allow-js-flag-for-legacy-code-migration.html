TypeScript allowJs Flag for Legacy Code Migration

Migrating a legacy JavaScript codebase to TypeScript all at once is often impossible for active software projects. The allowJs compiler option solves this challenge by allowing JavaScript and TypeScript files to coexist and compile together inside the same project. This article explains the role of the allowJs flag, why it is critical for incremental migrations, how it pairs with complementary compiler settings, and the practical workflow for modernizing your codebase safely.

What is the allowJs Flag?

By default, the TypeScript compiler (tsc) only recognizes and processes files with .ts and .tsx extensions. Any existing .js or .jsx files are ignored during compilation, which causes module resolution errors when TypeScript files try to import them.

Setting "allowJs": true in your tsconfig.json instructs the TypeScript compiler to accept, process, and include JavaScript files as valid inputs in your project build.

{
  "compilerOptions": {
    "allowJs": true,
    "outDir": "./dist",
    "target": "ES2020"
  },
  "include": ["src/**/*"]
}

Why allowJs is Essential for Legacy Migrations

Rewriting an entire production application from JavaScript to TypeScript in a single pull request introduces extreme risk, halts feature development, and leads to severe merge conflicts. The allowJs flag enables an incremental migration strategy, providing several distinct advantages:

1. Seamless Interoperability

With allowJs enabled, TypeScript files can directly import modules from existing JavaScript files, and JavaScript files can import from newly created TypeScript files. The compiler bridges the gap between both ecosystems, allowing you to write new features in pure TypeScript without having to convert older dependencies first.

2. Zero-Downtime Incremental Adoption

Teams can migrate legacy applications file by file at their own pace. Developers can convert utility functions today, domain models next week, and UI components later. Because the application remains fully functional and deployable throughout the process, day-to-day product development is never blocked.

3. Unified Build Pipeline

Without allowJs, compiling a mixed codebase often requires chaining multiple build tools (such as maintaining separate Webpack or Babel loaders for .js and .ts). Enabling allowJs allows the TypeScript compiler to manage the bundling or transpilation step for the entire codebase, simplifying your build toolchain.

Complementary Flags: checkJs and noEmit

When migrating legacy code with allowJs, two companion flags are frequently used to improve type safety and workflow management:

  • checkJs: Setting "checkJs": true instructs TypeScript to report type errors inside .js files using type inference and JSDoc comments. This lets you catch bugs in legacy code before even renaming files to .ts.
  • noEmit: If you use bundlers like Vite, esbuild, or Babel to produce your final production assets, TypeScript is only needed for type analysis. Enabling "noEmit": true allows tsc to perform validation without outputting build files, speeding up type verification.

The Standard Migration Workflow

Using allowJs effectively involves a structured phase-out process:

  1. Initialize TypeScript: Add TypeScript to your project, create a tsconfig.json, and set "allowJs": true. Ensure your existing test suite passes and your build succeeds.
  2. Type the Foundation: Begin converting foundational layers—such as shared types, constants, and utilities—by renaming them from .js to .ts.
  3. Migrate High-Churn Files: Focus on files that are actively being updated for new business requirements. Rename each file to .ts or .tsx, resolve the resulting type errors, and commit the changes incrementally.
  4. Enforce Stricter Standards: As the percentage of TypeScript code grows, enable stricter settings such as strictNullChecks and noImplicitAny.
  5. Phase Out JavaScript: Once all .js and .jsx files have been migrated to .ts and .tsx, remove "allowJs": true (or set it to false) to ensure that untyped JavaScript files can no longer be introduced into the repository.
