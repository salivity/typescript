TypeScript Stage 3 Decorators Without reflect-metadata

TypeScript 5.0 introduced support for the official ECMAScript Stage 3 decorators specification, fundamentally changing how decorated code is transformed and executed. Unlike legacy experimental decorators, which relied on the non-standard reflect-metadata library and the emitDecoratorMetadata flag to inject design-time type information, standard Stage 3 decorators operate as standard JavaScript transformation functions. TypeScript compiles these decorators directly into native function calls and structural wrappers using internal helper functions, eliminating the need for external runtime reflection libraries.

The Shift from Reflection to Function Transformation

Legacy decorators in TypeScript (experimentalDecorators: true) functioned by mutating classes or property descriptors at runtime, frequently combined with emitDecoratorMetadata to serialize TypeScript types (such as parameter and return types) into the global Reflect registry via reflect-metadata.

Stage 3 decorators do not rely on type serialization. Instead, they are defined purely by their runtime execution semantics. A Stage 3 decorator is a function applied directly to a class, method, getter, setter, field, or auto-accessor. It receives two arguments:

  1. The target value being decorated (or undefined for class fields).
  2. A strongly typed context object containing metadata about the target (such as its kind, name, static status, and an addInitializer hook).

Because the decorator can return a replacement function, a new class, or an initializer hook, the transformation happens directly at the definition level without querying an external metadata registry.

Compilation Mechanics: __esDecorate and __runInitializers

When compiling Stage 3 decorators to older JavaScript targets (or when downleveling class elements), the TypeScript compiler replaces the @ syntax with emitted helper functions, primarily __esDecorate and __runInitializers.

1. Registration via __esDecorate

During class definition, TypeScript passes the target, an array of decorators, and the decorator context to the __esDecorate helper.

  • The helper iterates through the decorators in reverse order (evaluating inside-out).
  • Each decorator receives the element and its associated context object.
  • If a decorator returns a replacement implementation (for example, a wrapped method), __esDecorate stores this new value to overwrite the original member descriptor on the class prototype or constructor.
  • Any callbacks registered via context.addInitializer are collected into an array for subsequent execution.

2. Lifecycle Handling via __runInitializers

Decorators often need to run setup logic after a class element or instance is created. TypeScript handles this using __runInitializers:

  • For static members, __runInitializers executes immediately after the class is defined.
  • For instance members and fields, __runInitializers is inserted directly into the generated constructor.
  • For decorated fields, initializers returned by decorators transform the field's initial value when an instance is instantiated.

Because these operations are purely lexical and functional—passing functions into helpers that return modified functions—the output is self-contained JavaScript that requires no external reflection shim.

Native Decorator Metadata via context.metadata

The original need for reflect-metadata often stemmed from wanting to attach custom metadata to classes and read it later (common in dependency injection frameworks). Stage 3 addresses this natively through the Decorator Metadata proposal.

Every context object passed to a Stage 3 decorator includes a context.metadata property. This property references a plain JavaScript object shared across all decorators within the same class declaration (and prototypically inheriting from parent classes).

When metadata is attached:

function Tag(name: string) {
  return (value: any, context: ClassMethodDecoratorContext) => {
    context.metadata[name] = true;
  };
}

TypeScript compiles this so that the metadata dictionary is attached to the class constructor under the well-known symbol Symbol.metadata. Consumers inspect metadata simply by accessing MyClass[Symbol.metadata], bypassing the need for a global Reflect polyfill entirely.
