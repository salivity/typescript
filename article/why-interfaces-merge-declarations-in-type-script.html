Why Interfaces Merge Declarations in TypeScript

In TypeScript, interfaces can merge declarations while type aliases cannot due to fundamental differences in their architectural design and intended use cases. Interfaces were engineered to be open and extensible to accurately model JavaScript’s dynamic runtime environment and library augmentation, whereas type aliases were created as immutable, direct bindings to represent specific type expressions, including primitives, unions, and tuples.

Architectural Intent: Open vs. Closed

The primary reason for this distinction lies in the concept of "open" versus "closed" type systems:

  • Interfaces are "open": They are specifically designed to describe the shape of objects that may evolve across different files, packages, or scopes. This open-ended nature allows multiple definitions with the same name to automatically combine into a single, unified definition.
  • Type Aliases are "closed": A type alias is not a declaration of a new object shape; it is an alias—an exact alternative name—for an underlying type expression. Because it functions as a distinct identifier binding, defining the same name twice creates a duplicate identifier collision.

The Problem of Defining Merge Semantics for Types

Interfaces only describe object shapes and method signatures, making the rules for merging straightforward: properties are aggregated, and identical method signatures are overloaded.

Type aliases, however, can represent any type, such as primitives, unions, intersections, or tuples:

type Value = string;
type Value = number; // What should this mean?

If TypeScript allowed declaration merging for type aliases, the compiler would need arbitrary rules to handle conflicts:

  • Should Value become a union (string | number)?
  • Should it become an intersection (string & number, which evaluates to never)?
  • Should the second definition overwrite the first?

Because no single, intuitive rule applies to all non-object types, merging type aliases is prohibited entirely to preserve type safety and predictability.

Practical Necessity: Global and Library Augmentation

TypeScript was designed to easily interface with existing JavaScript environments, where scripts and libraries frequently augment global objects (such as window or Array.prototype).

Declaration merging enables developers to extend built-in APIs or third-party declarations without modifying the original source code:

// Initial definition (e.g., inside a third-party library)
interface Document {
  title: string;
}

// User augmentation (in a local project file)
interface Document {
  customProperty: boolean;
}

// Result: Document has both 'title' and 'customProperty'

If interfaces were closed like type aliases, extending global runtimes or modular libraries would require completely overriding the original types or using complex intersection patterns everywhere.

Composition Strategies

Because of these design rules, each construct has a dedicated approach for combining shapes:

  • Interfaces rely on declaration merging (implicit extension) and the extends keyword (explicit inheritance).
  • Type aliases rely on intersection types (&) for explicit composition without mutating or augmenting existing definitions.

This separation ensures that interfaces provide the necessary flexibility for library authoring and environment typing, while type aliases provide stable, immutable references for advanced type composition.
