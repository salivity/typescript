Custom TypeScript Transformers: ttypescript vs ts-patch

This article explores the critical role that ttypescript and ts-patch play in the TypeScript ecosystem by enabling custom Abstract Syntax Tree (AST) transformers. While TypeScript provides a robust compiler API capable of programmatically altering code during compilation, the standard command-line compiler (tsc) lacks native support for running these transformers via configuration files. Below, we examine why these tools exist, how they bridge this architectural gap, and how they differ in implementation and maintenance.

The Problem with Standard tsc

The official TypeScript compiler exposes hooks for AST transformers through its programmatic API (ts.transform). These transformers allow developers to inspect, modify, or inject code during compilation—useful for tasks like automatic dependency injection, runtime type validation, removing debug logs, or processing inline GraphQL queries.

However, standard tsc intentionally excludes the ability to declare and execute these transformers through tsconfig.json. The plugins array in tsconfig.json is strictly reserved for language server plugins (which enhance IDE tooling), not for emit-altering transformations. Without third-party tooling, developers are forced to write custom compiler scripts or rely on bundlers like Webpack, Rollup, or Vite to leverage custom transformers.

The Role of ttypescript

ttypescript (Transform TypeScript) was developed as an early solution to standard tsc's configuration limitation. It acts as an executable wrapper around the TypeScript compiler.

Instead of running tsc, developers run ttsc. Under the hood, ttypescript:

  1. Intercepts the build command.
  2. Reads the tsconfig.json file.
  3. Detects entries in compilerOptions.plugins configured with transform settings.
  4. Invokes the official TypeScript API programmatically, feeding the specified custom transformers into the emit pipeline.

While ttypescript established the convention for configuring transformers via tsconfig.json, it is largely considered unmaintained and can struggle to maintain compatibility with modern TypeScript releases.

The Role of ts-patch

ts-patch is the modern successor to ttypescript. Rather than acting as a wrapper executable, ts-patch directly patches the local typescript module installed inside node_modules.

By patching the compiler library directly, ts-patch provides several key advantages:

  • Native Tooling Compatibility: Because it modifies the underlying typescript package, you can continue executing the standard tsc command, rather than needing an alternative binary like ttsc.
  • Toolchain and IDE Integration: Tools and extensions that depend directly on the installed TypeScript module—such as ts-node, Jest (ts-jest), ESLint, and IDE language servers—automatically gain support for custom transformers without extra configuration wrappers.
  • Non-Destructive Patching: It hooks cleanly into the compiler's transform pipeline and can be automated to patch on installation via a package.json prepare script (ts-patch install).

Configuring Transformers

Both tools utilize the compilerOptions.plugins block inside tsconfig.json. A typical configuration specifies the transformer package and the transform stage:

{
  "compilerOptions": {
    "plugins": [
      {
        "transform": "transformer-module-name",
        "type": "config"
      }
    ]
  }
}

The type field dictates when the transformer executes, such as before (pre-compilation AST manipulation), after (post-compilation transformation), or afterDeclarations (transforming generated .d.ts declaration files).

Summary

Custom TypeScript transformers allow deep modifications to code emission, but standard tsc restricts their use through basic configuration. While ttypescript solved this by wrapping tsc with a custom binary, ts-patch has become the preferred approach by patching the installed compiler directly, ensuring seamless compatibility across standard CLI builds, testing frameworks, and IDEs.
