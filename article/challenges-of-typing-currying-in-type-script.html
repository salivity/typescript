Challenges of Typing Currying in TypeScript

Currying is a fundamental technique in functional programming where a function with multiple arguments is transformed into a sequence of unary functions. While straightforward in dynamically typed languages like JavaScript, implementing type-safe currying in TypeScript introduces significant complexity. This article explores the core technical hurdles developers face when defining types for curried functions, including recursive conditional types, generic argument inference, partial application variations, and compiler performance limits.

The Arity Problem and Recursive Types

In a purely curried function, a function (a: A, b: B, c: C) => D becomes (a: A) => (b: B) => (c: C) => D. To write a generic curry() utility that works for functions of arbitrary arity, TypeScript must inspect the function's parameter tuple and recursively construct nested function signatures.

Before TypeScript 4.1 introduced recursive conditional types, developers had to rely on manual function overloads up to a predetermined number of arguments (often 5 to 10). While modern TypeScript allows recursive tuple manipulation using variadic tuple types, constructing a generic type like:

type Curry<P extends any[], R> = P extends [infer Head, ...infer Tail]
  ? (arg: Head) => Curry<Tail, R>
  : R;

still fails to address edge cases such as functions with unknown or infinite parameter lengths, often resolving unexpectedly to never or generic function structures that break intellisense.

Real-World Currying: Multi-Argument Application

Libraries like Lodash and Ramda implement flexible currying, which permits callers to pass multiple arguments in a single step (e.g., curried(1, 2)(3) or curried(1)(2, 3)).

Modeling this behavior requires the type system to compute every possible combination of argument slices. The return type must branch depending on whether the supplied arguments satisfy the original parameter list completely or only partially. Creating types that accurately represent all partitions of a parameter tuple increases complexity exponentially:

type VariadicCurry<P extends any[], R> = <T extends any[]>(
  ...args: T
) => P extends [...T, ...infer Rest]
  ? Rest extends []
    ? R
    : VariadicCurry<Rest, R>
  : never;

This pattern quickly becomes brittle when types must handle empty argument calls, mismatched types, or excess arguments.

Loss of Generic Parameter Inference

One of the most persistent issues in TypeScript is the preservation of generic types through curried functions. If a function is generic:

function map<T, U>(fn: (x: T) => U, list: T[]): U[] {
  return list.map(fn);
}

Currying map breaks standard type inference. When calling curriedMap(x => x * 2), TypeScript must infer T and U at the point of the first argument. Because the context of list: T[] is deferred to the second invocation, TypeScript often prematurely widens T to unknown or fails to propagate the inferred type to subsequent calls. TypeScript does not support higher-rank types, meaning you cannot easily return a generic function from a type-level recursive operation.

Optional and Rest Parameters

Standard functions in TypeScript frequently feature optional parameters (foo?: string) and rest parameters (...args: number[]). Currying models break down under these semantics:

  • Optional parameters have ambiguous termination points. The type system cannot determine whether the caller intends to supply the optional argument in a later call or finish evaluation immediately.
  • Rest parameters represent unbounded arrays. A recursive type attempting to consume a rest parameter tuple cannot find an empty terminal state ([]), causing it to fall into infinite loops or drop the types entirely.

Compiler Recursion Limits and Performance

TypeScript enforces a maximum recursion depth on conditional types to avoid crashing the compiler. Highly nested or flexible currying types frequently trigger errors such as:

Type instantiation is excessively deep and possibly infinite.

Even when these types stay within compiler limits, they place heavy computational demands on TypeScript's language server. Complex curried types can lead to noticeable input lag in IDEs, slow build times, and opaque compiler error messages that are difficult to debug when an invalid argument is passed deep inside a curried chain.
