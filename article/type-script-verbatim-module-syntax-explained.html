TypeScript verbatimModuleSyntax Explained

The verbatimModuleSyntax compiler flag in TypeScript governs how import and export statements are emitted into JavaScript by enforcing strict, syntax-based module emission. Instead of analyzing whether an imported symbol resolves to a type or a runtime value to determine if an import should be dropped, TypeScript relies purely on the syntax used in the code. This article explains what verbatimModuleSyntax enforces, how it changes module emission, and how to write code that complies with it.

The Core Rule: Purely Syntactic Emission

Traditionally, TypeScript uses semantic analysis to elide (remove) imports. If an imported identifier is only used as a type, TypeScript quietly strips it from the emitted JavaScript output.

When verbatimModuleSyntax is enabled, TypeScript stops guessing your intent based on usage. Module emission is governed strictly by the written syntax:

  1. Imports with the type modifier are completely removed. Any statement using import type or individual specifiers using { type X } will never appear in the emitted JavaScript.
  2. Imports without the type modifier are preserved verbatim. Any import statement that does not explicitly use the type modifier is emitted directly into JavaScript, regardless of whether the imported symbol is actually an interface, type alias, or class.
  3. Using a type in a non-type import causes a compile-time error. If you import an identifier without the type keyword and that identifier only exists as a type, TypeScript throws a compilation error to prevent emitting broken runtime imports.

Impact on Module Syntax

Under verbatimModuleSyntax, the code you write maps directly to the emitted output:

Type-Only Imports

// Source
import type { User } from "./models";
import { type Post, renderPost } from "./posts";

// Emitted JavaScript
import { renderPost } from "./posts";

User is dropped entirely because the whole statement is marked as a type import. In the second statement, type Post is stripped, but renderPost is preserved.

Erroneous Type Imports

// Source
import { User } from "./models"; // Error if User is only a type!

Under default TypeScript settings, this statement would be deleted from the output if User was an interface. Under verbatimModuleSyntax, TypeScript flags this as an error. If left uncorrected, it would emit import { User } from "./models"; into the runtime code, potentially causing a runtime reference error.

Side-Effect Imports

// Source & Emitted JavaScript
import "./setup";

Side-effect imports are always preserved, as they do not bind any names.

CommonJS and ESM Interoperability

The flag also impacts how CommonJS modules are handled under modern module resolution settings. To emit CommonJS interop code correctly:

  • Use standard ESM import and export syntax for ECMAScript modules.
  • Use import foo = require("./foo") and export = foo syntax when specifically targeting CommonJS semantics.

Why verbatimModuleSyntax Is Used

Introduced in TypeScript 5.0, verbatimModuleSyntax supersedes the older --importsNotUsedAsValues and --preserveValueImports flags. It provides three primary benefits:

  • Predictable Output: Developers can tell exactly what JavaScript will be emitted simply by looking at the source file, without needing to inspect external type definitions.
  • Transpiler Compatibility: External build tools like Babel, esbuild, and SWC process single files without type checking. Because verbatimModuleSyntax relies entirely on syntax, these tools emit the exact same module code as the TypeScript compiler (tsc).
  • Runtime Safety: It prevents situations where bundlers or Node.js crash because a type was accidentally emitted as a runtime import, or vice versa, where an import intended for side effects was accidentally removed because its value was never directly referenced.
