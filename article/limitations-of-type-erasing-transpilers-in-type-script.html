Limitations of Type-Erasing Transpilers in TypeScript

Type-erasing transpilers such as Babel, esbuild, and SWC dramatically accelerate JavaScript build pipelines by stripping TypeScript type annotations without performing type checks. However, relying solely on type erasure introduces distinct architectural and functional drawbacks. This article details the primary limitations developers encounter when using single-file type-erasing tools instead of the official TypeScript compiler (tsc), covering syntax restrictions, missing build-time validation, and tooling trade-offs.

Single-File Transpilation Constraints

Type-erasing transpilers generally operate on one file at a time. Because they do not resolve references across multiple files or load the entire project graph, they cannot determine whether an imported identifier represents a runtime value or a compile-time type. This architecture imposes strict limitations on how code must be written:

  • Const Enums: In standard TypeScript, const enum members are completely inlined at compile time based on their definitions in other files. Single-file transpilers cannot resolve these cross-file definitions, causing build failures or requiring the compiler to emit them as standard runtime objects, which violates intended optimizations.
  • Ambiguous Type Re-exports: If a module imports an identifier from another file and re-exports it, a single-file transpiler cannot know whether it should be emitted into the final JavaScript output. Without explicit export type syntax, the transpiler may emit a reference to a nonexistent runtime value, causing runtime ReferenceError crashes.
  • Namespace Merging: TypeScript allows declarations of classes, functions, and namespaces with the same name across multiple files to merge. Single-file transpilers cannot merge symbols defined across module boundaries.

To avoid runtime bugs caused by these issues, projects must enable the isolatedModules flag in tsconfig.json, which restricts the use of language features that require whole-program understanding.

Absence of Build-Time Type Safety

The speed of tools like SWC and esbuild stems from bypassing the type-checking phase entirely. As a result:

  • Silent Type Errors: Code containing critical type violations will compile successfully without warnings. A typo in a property name or an incompatible function argument will make it directly into production bundles unless caught by unit tests or an external validation step.
  • Dual-Pipeline Requirement: Teams must still run tsc --noEmit in their continuous integration (CI) environments or background editor processes to ensure type correctness. This introduces tooling fragmentation and negates some of the convenience gained by faster local compilation.

Inability to Generate Declaration Files

Type-erasing transpilers cannot generate .d.ts declaration files. Creating declaration files requires traversing the full type graph to compute inferred return types, public interfaces, and class shapes.

For library authors, this means a type-erasing compiler cannot serve as an all-in-one build solution. Authors must still invoke tsc with --emitDeclarationOnly to publish accurate typings alongside their compiled JavaScript bundles.

Limited Metadata and Decorator Support

Certain TypeScript configurations depend on runtime reflection:

  • emitDecoratorMetadata: Frameworks like NestJS, TypeORM, and Angular rely on TypeScript emitting runtime type metadata for constructor injection and property definitions. Because this requires evaluating the type system to determine property types, type-erasing tools historically cannot generate this metadata accurately or require specialized plugins with known edge-case failures.
  • Legacy vs. TC39 Decorators: Variations in how experimental decorators and modern TC39 Stage 3 decorators are compiled can lead to discrepancies between tsc output and type-erasing transpiler output, occasionally altering runtime behavior.
