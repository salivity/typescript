How TypeScript Incremental Builds Work

TypeScript's incremental compiler flag significantly reduces build times by persisting information about the project graph from the last compilation to disk. When enabled, TypeScript analyzes file modifications since the previous build and only recompiles the files that have changed, along with their direct and indirect dependents. This article explains how the incremental flag functions under the hood, the role of the generated build information file, and how the compiler uses this metadata to optimize subsequent builds.

The Role of the .tsbuildinfo File

When you enable "incremental": true in your tsconfig.json, the TypeScript compiler (tsc) generates a cache file with the extension .tsbuildinfo. By default, this file is placed in your output directory alongside your compiled code, but you can customize its location using the tsBuildInfoFile configuration option.

The .tsbuildinfo file contains serialized metadata about the build, including:

  • File Hashes: Cryptographic hashes or timestamps of every source file, declaration file, and external module included in the compilation.
  • The Dependency Graph: A directed graph mapping which modules import, export, or depend on other modules.
  • Compiler Options: The configuration settings used during the compilation.
  • Emit Signatures: Checksums and signature information for generated outputs (such as .d.ts declaration files) to determine whether a change impacts downstream consumers.

The Rebuild Process Step-by-Step

When you run a compilation with the incremental flag enabled, TypeScript executes the following process to determine what needs to be compiled:

1. Reading the Cache

The compiler searches for the .tsbuildinfo file. If the file does not exist, TypeScript performs a full compilation from scratch and writes the .tsbuildinfo file upon completion. If the file exists, TypeScript reads the stored state into memory.

2. Change Detection

TypeScript computes the current hashes of all source files in the project and compares them against the stored hashes in the .tsbuildinfo file. If a file's hash is identical, the compiler knows the file has not changed.

3. Graph Invalidation

If the compiler detects changed files, it traverses the stored dependency graph. It marks the modified files as "dirty" and inspects their dependents:

  • Private Changes: If a change inside a file does not alter its public API (its exported types or shape), only that specific file needs to be re-emitted.
  • Shape Changes: If a change alters exported types, functions, or interfaces, TypeScript marks all modules importing that file as dirty, propagating the check up the dependency chain.

4. Type Checking and Emitting

TypeScript skips type-checking and code generation for files that are clean and unaffected by any changes. It only runs the full type-checking pipeline and writes output files (.js, .d.ts, and source maps) for the dirty files.

5. Updating the Cache

Once compilation finishes, the compiler updates the .tsbuildinfo file with the new file hashes, updated graph nodes, and emit signatures, preparing the project for the next incremental cycle.

Incremental Builds vs. Watch Mode

While both --watch and --incremental optimize compilation time, they serve distinct purposes:

  • Watch Mode (--watch): Keeps the compiler process alive in memory. It tracks file system events and maintains the project graph in RAM. However, once the process exits, all state is lost.
  • Incremental Flag (--incremental): Persists the compiler state to a file on disk. This allows non-watch invocations (such as standard build scripts, CI/CD pipelines, or editor restarts) to benefit from the work done in earlier compilations.

Combining both flags (tsc --incremental --watch) provides the fastest local development experience, as the compiler can bootstrap instantly using the on-disk cache instead of performing a cold start.

Using Incremental Builds in CI/CD

To leverage incremental compilation in automated environments:

  1. Persist the Cache: Configure your CI system to cache the .tsbuildinfo file across runs.
  2. Preserve Output Artifacts: Ensure that the generated build outputs (dist or build folders) are also cached, as TypeScript will avoid re-emitting files only if the existing outputs are present on disk.
  3. Invalidate on Config Changes: If you modify tsconfig.json or update dependencies in package.json, ensure the cache is purged to prevent stale resolution artifacts.
