Why TypeScript Allows Returning Values in Void Functions

This article explains why TypeScript permits functions assigned to a void return type, such as VoidFunction, to return a value without producing a compilation error. While this behavior often surprises developers, it is an intentional design choice rooted in callback substitutability and practical JavaScript interoperability. Understanding how TypeScript treats void in function type signatures versus direct implementations clarifies why this happens and how it keeps standard JavaScript idioms ergonomic.

The Difference Between Declarations and Function Types

To understand this behavior, you must distinguish between a direct function declaration and a function assigned to a type alias or interface.

When you declare a function with an explicit void return type, TypeScript strictly enforces that nothing is returned:

// Compiler Error: Type 'number' is not assignable to type 'void'.
function directFunction(): void {
  return 42;
}

However, when working with function types like VoidFunction (defined as () => void), TypeScript permits the implementation to return a value:

type VoidFunction = () => void;

// No error
const callback: VoidFunction = () => 42;

The Principle of Substitutability

TypeScript's type system relies on substitutability. When a type definition specifies a return type of void, it signifies that the caller will ignore the return value, not that the function is forbidden from returning one.

A function returning a value fulfills the contract of a function whose return value is ignored. The caller guarantees it will not consume or rely on any returned data:

const run = (fn: VoidFunction) => {
  fn(); // The caller does nothing with the result
};

run(() => "ignored value"); // Safe to execute

If TypeScript prohibited returning a value here, it would reject valid implementations where the returned value causes no runtime side effects for the caller.

Practical JavaScript Compatibility

The primary motivation for this design is seamless integration with standard JavaScript APIs. Many built-in array and collection methods return values, even when executed purely for side effects.

Consider Array.prototype.push, which returns the new length of the array:

const source = [1, 2, 3];
const target: number[] = [];

// forEach expects: (value: number) => void
source.forEach(item => target.push(item));

In the example above, target.push(item) evaluates to a number. Because the callback in forEach expects a return type of void, a strict ban on returning values would cause this code to fail compilation. Developers would be forced to write verbose blocks:

// Necessary if void strictly forbade returning values:
source.forEach(item => {
  target.push(item);
});

By allowing void callback signatures to accept values, TypeScript preserves standard shorthand arrow function syntax.

Type Safety Is Still Preserved

Although the function can return a value internally, TypeScript prevents the caller from using that value. The return value is typed as void, stopping downstream code from treating it as anything else:

type VoidFunction = () => void;

const getValue: VoidFunction = () => 100;

const result = getValue(); // Type of 'result' is void

// Compiler Error: Operator '+' cannot be applied to types 'void' and 'number'.
console.log(result + 1);

The compiler guarantees safety at the call site by blocking access to the returned data, ensuring the implementation details do not leak into consumer code.
