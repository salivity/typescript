Wildcard Module Declarations in TypeScript

Wildcard module declarations in TypeScript allow developers to import non-code assets and dynamically structured modules without triggering type-checker errors. This article explains how wildcard declarations work, why they are essential for modern bundlers like Webpack and Vite, and how to define them to properly type assets such as images, stylesheets, and custom loader paths.

Understanding the Problem

TypeScript is designed to resolve imports pointing to .ts, .tsx, .d.ts, or .js files. When working with modern frontend tooling, however, projects frequently import non-code assets directly into application logic:

import logo from "./assets/logo.svg";
import styles from "./styles.module.css";

By default, the TypeScript compiler (tsc) attempts to resolve these paths as standard modules and throws the error: TS2307: Cannot find module './assets/logo.svg' or its corresponding type declarations.

Because these files are transformed by bundlers at build time rather than by TypeScript itself, TypeScript needs an ambient definition explaining what these non-standard imports evaluate to.

What is a Wildcard Module Declaration?

A wildcard module declaration uses an asterisk (*) in an ambient module path definition (declare module) to match any import string matching a specified pattern. Instead of declaring a module for every individual asset file, a single declaration applies to all files that share a common extension or prefix.

Basic Syntax for Static Assets

To define a wildcard module, create an ambient declaration file (for example, declarations.d.ts or env.d.ts) and use the declare module syntax:

declare module "*.svg" {
  const content: string;
  export default content;
}

declare module "*.png" {
  const value: string;
  export default value;
}

With these declarations in place, any import ending in .svg or .png is recognized as a valid module where the default export is typed as a string.

Typing CSS Modules

Wildcard declarations can also define structured object types. For CSS Modules, class names are mapped to strings at runtime:

declare module "*.module.css" {
  const classes: { readonly [key: string]: string };
  export default classes;
}

This ensures that referencing properties on imported CSS module objects provides type safety and avoids any types:

import styles from "./Button.module.css";

const buttonClass = styles.primary; // Type: string

Prefix and Custom Loader Wildcards

Wildcards are not restricted to file extensions. They can match prefixes, which is useful when integrating with bundler plugins, virtual modules, or custom module loaders:

// Matching virtual modules (common in Vite)
declare module "virtual:*" {
  const data: Record<string, unknown>;
  export default data;
}

// Matching dynamic protocol-like loaders
declare module "raw-loader!*" {
  const content: string;
  export default content;
}

TypeScript requires the wildcard character * to be at either the start or the end of the module string pattern.

Configuring the Project

For TypeScript to recognize wildcard module declarations, ensure the file containing the declarations is included in the project's tsconfig.json:

{
  "compilerOptions": {
    "target": "ESNext",
    "module": "ESNext",
    "moduleResolution": "Bundler"
  },
  "include": [
    "src/**/*",
    "declarations.d.ts"
  ]
}

Wildcard module declarations bridge the gap between TypeScript's strict static analysis and the flexible module loading patterns introduced by modern web bundlers.
