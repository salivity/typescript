useDefineForClassFields and Inheritance in TypeScript

The useDefineForClassFields compiler flag in TypeScript switches class field emission from legacy assignment semantics to standard ECMAScript definition semantics. When enabled, class property initializers use Object.defineProperty instead of standard assignment (this.field = value). This change fundamentally alters inheritance behavior, specifically regarding how derived class properties interact with base class getters, setters, and initialized properties.

Assignment Semantics vs. Definition Semantics

To understand the impact on inheritance, it is essential to distinguish between the two emission modes:

  • When false (Legacy TypeScript): Fields are emitted as assignments (this.x = value;). Assignment follows the prototype chain, triggering any existing setter defined in a parent class.
  • When true (ECMAScript Standard): Fields are emitted using Object.defineProperty(this, "x", { value, writable: true, enumerable: true, configurable: true }). This explicitly creates an "own" property directly on the current instance, bypassing prototype setters entirely.

Overriding Getters and Setters in Base Classes

The most common behavioral divergence occurs when a derived class declares a property that matches an accessor (getter/setter) on a parent class.

Consider this structure:

class Base {
  set data(value: string) {
    console.log("Base setter called with:", value);
  }
}

class Derived extends Base {
  data = "hello";
}

Behavior with useDefineForClassFields: false

During the instantiation of Derived, super() runs, followed by this.data = "hello". Because it uses assignment, JavaScript traverses the prototype chain, finds the data setter on Base.prototype, and executes it. The console outputs "Base setter called with: hello".

Behavior with useDefineForClassFields: true

Object.defineProperty creates the data property directly on the Derived instance. It does not traverse the prototype chain, meaning the data setter on Base is never executed. Instead, the instance gains an own property called data that completely shadows the getter/setter pair on the base class.

Overwriting Base Properties with Uninitialized Fields

Another major shift affects class fields declared without explicit initializers.

class Parent {
  value = 10;
}

class Child extends Parent {
  value: number;
}

Behavior with useDefineForClassFields: false

TypeScript strips out type-only declarations during compilation. Because value in Child has no initializer, no JavaScript code is generated for it in the child class. The instance retains value = 10 set by the Parent constructor.

Behavior with useDefineForClassFields: true

Per the ECMAScript specification, any declared class field without an explicit initializer is initialized to undefined. The emitted code for Child defines value as void 0.

When new Child() runs:

  1. super() executes, setting this.value = 10.
  2. The Child initializer executes, defining value on the instance as undefined.
  3. The parent class's value is unintentionally overwritten.

To retain the parent value without adding a runtime initializer in modern TypeScript, use the declare keyword:

class Child extends Parent {
  declare value: number; // Emits no runtime JavaScript
}

Constructor Execution Order and TDZ

Because ECMAScript field definitions occur strictly after the base constructor returns, derived class property initializers evaluate in a distinct step:

  1. Base class fields are initialized using Define.
  2. Base class constructor body executes.
  3. Derived class fields are initialized using Define.
  4. Derived class constructor body executes.

If a base class constructor calls a virtual method that accesses a property declared in the derived class, legacy assignment would sometimes allow the method to observe the property if it was bound early. Under definition semantics, the derived field does not exist on the instance during the base constructor execution; attempting to access it will yield undefined or cause runtime initialization errors.
