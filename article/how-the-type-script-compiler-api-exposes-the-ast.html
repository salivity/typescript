How the TypeScript Compiler API Exposes the AST

The TypeScript Compiler API parses source code into an Abstract Syntax Tree (AST), exposing it through a tree-like hierarchy of specialized node objects rooted in a SourceFile. By leveraging parsing functions, visiting utilities, and syntax discriminators provided by the typescript package, developers can programmatically inspect, traverse, and manipulate every syntactic token, declaration, and statement in a TypeScript or JavaScript file.

Parsing Code into a SourceFile

The entry point to the AST is the SourceFile node, which represents the entire parsed file. You can generate a SourceFile without setting up a full compilation pipeline by using the ts.createSourceFile utility:

import * as ts from "typescript";

const sourceCode = `const greeting: string = "Hello, world!";`;
const sourceFile = ts.createSourceFile(
  "example.ts",
  sourceCode,
  ts.ScriptTarget.Latest,
  /* setParentNodes */ true
);

For multi-file projects requiring semantic analysis or type information, the AST is obtained through a ts.Program:

const program = ts.createProgram(["example.ts"], {});
const sourceFile = program.getSourceFile("example.ts");

The Structure of an AST Node

Every element within the AST implements the ts.Node interface. The SourceFile acts as the root node, and its children represent top-level statements, which branch further into expressions, declarations, and literals.

Each Node exposes foundational properties:

  • kind: A member of the ts.SyntaxKind enum identifying what the node represents (e.g., VariableStatement, FunctionDeclaration, Identifier).
  • pos and end: Character offsets indicating where the node starts and ends in the raw source text.
  • parent: A reference to the node's parent (populated when setParentNodes is enabled).

To retrieve the original source code corresponding to any node, use node.getText(sourceFile).

Traversing the AST

The API provides two primary mechanisms to walk the tree:

1. ts.forEachChild

ts.forEachChild visits the immediate children of a given node, making it ideal for linear, read-only traversals:

function traverse(node: ts.Node) {
  console.log(ts.SyntaxKind[node.kind]);
  ts.forEachChild(node, traverse);
}

traverse(sourceFile);

2. AST Visitors (ts.visitEachChild and ts.visitNode)

When transforming nodes or building custom AST transformations, the visitor API allows deep traversal while returning modified or replacement nodes:

const transformer: ts.TransformerFactory<ts.SourceFile> = (context) => {
  return (rootNode) => {
    function visit(node: ts.Node): ts.Node {
      // Return a modified node or continue traversing
      return ts.visitEachChild(node, visit, context);
    }
    return ts.visitNode(rootNode, visit) as ts.SourceFile;
  };
};

Type Guards and Syntax Kinds

Because the AST uses a tagged union pattern based on node.kind, the API exposes built-in type guard functions (prefixed with is) that narrow a generic ts.Node to its specific subclass:

ts.forEachChild(sourceFile, (node) => {
  if (ts.isVariableStatement(node)) {
    // node is narrowed to ts.VariableStatement
    const declarations = node.declarationList.declarations;
    declarations.forEach((decl) => {
      if (ts.isIdentifier(decl.name)) {
        console.log(`Variable name: ${decl.name.text}`);
      }
    });
  }
});

Connecting the AST to Semantics

While the AST captures structural syntax, the Compiler API binds these syntax nodes to semantic data through a TypeChecker. By calling program.getTypeChecker(), you can bridge syntax nodes to symbols and types:

  • checker.getSymbolAtLocation(node): Resolves an identifier AST node to its ts.Symbol definition.
  • checker.getTypeAtLocation(node): Resolves the computed ts.Type of an expression node.

This separation keeps the AST lightweight and strictly focused on representing the source code structure, while allowing rich semantic querying when needed.
