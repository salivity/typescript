TypeScript Method Chaining with Polymorphic This Types

This article explores how TypeScript uses polymorphic this types to preserve derived class types during method chaining. When designing fluent APIs with class inheritance, returning a base class type directly breaks the chain for subclass-specific methods. By leveraging the polymorphic this return type, TypeScript dynamically resolves the returned instance to the specific subtype at the call site, enabling seamless, type-safe inheritance across chained methods.

The Problem with Traditional Method Chaining

In object-oriented programming, method chaining (or fluent interfaces) typically relies on methods returning the current instance via return this. However, when implementing inheritance, explicitly typing the return value as the base class causes issues.

Consider a base builder class:

class RequestBuilder {
  protected headers: Record<string, string> = {};

  setHeader(key: string, value: string): RequestBuilder {
    this.headers[key] = value;
    return this;
  }
}

class AuthRequestBuilder extends RequestBuilder {
  protected token: string = "";

  setToken(token: string): AuthRequestBuilder {
    this.token = token;
    return this;
  }
}

If you instantiate AuthRequestBuilder and call the inherited setHeader() method first, the return type statically evaluates to RequestBuilder. Consequently, TypeScript will not allow you to call setToken() next:

// Error: Property 'setToken' does not exist on type 'RequestBuilder'
new AuthRequestBuilder()
  .setHeader("Content-Type", "application/json")
  .setToken("secret-token");

How Polymorphic this Solves the Issue

TypeScript introduces the polymorphic this type to represent a subtype of the containing class rather than the class itself. When used as a return type annotation, this refers dynamically to the actual type of the instance invoking the method.

Updating the base class to use this as the return type resolves the hierarchy issue:

class RequestBuilder {
  protected headers: Record<string, string> = {};

  // Note the return type annotation: 'this'
  setHeader(key: string, value: string): this {
    this.headers[key] = value;
    return this;
  }
}

class AuthRequestBuilder extends RequestBuilder {
  protected token: string = "";

  setToken(token: string): this {
    this.token = token;
    return this;
  }
}

Now, the compiler recognizes the concrete type executing the chain:

// Works correctly
const request = new AuthRequestBuilder()
  .setHeader("Content-Type", "application/json") // Returns AuthRequestBuilder
  .setToken("secret-token");                     // Returns AuthRequestBuilder

How the Compiler Evaluates Polymorphic this

Under the hood, TypeScript treats this in return positions as an implicit generic parameter bounded by the containing class: <T extends RequestBuilder>(this: T): T.

When setHeader() is invoked on an instance of AuthRequestBuilder:

  1. TypeScript evaluates the calling context (new AuthRequestBuilder()).
  2. It substitutes the polymorphic this annotation with the specific caller type (AuthRequestBuilder).
  3. The method returns AuthRequestBuilder instead of degrading to RequestBuilder.

This mechanism allows developers to build deeply nested, modular class hierarchies without needing verbose generic parameters on every class declaration. Derived classes can continuously introduce new methods while inheriting fluent behaviors from ancestor classes without losing type specificity.
