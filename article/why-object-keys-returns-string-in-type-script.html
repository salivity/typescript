Why Object.keys Returns string[] in TypeScript

In TypeScript, Object.keys returns string[] rather than (keyof T)[] because of how TypeScript's structural type system interacts with JavaScript at runtime. While narrowing the return type to (keyof T)[] feels intuitive, doing so would compromise type safety whenever objects contain extra properties, inherit enumerable prototype keys, or change dynamically. This article explains the technical reasons behind this design choice and demonstrates how to safely type object keys when strictness is required.

1. Structural Typing and Excess Properties

TypeScript uses a structural type system rather than a nominal one. Under structural typing, a type is defined by its shape, meaning a value is compatible with an interface as long as it satisfies the required shape—even if it includes additional properties.

Consider this scenario:

interface User {
  id: number;
  name: string;
}

const admin = {
  id: 1,
  name: "Alex",
  role: "superadmin" // Excess property
};

const user: User = admin; // Valid assignment due to structural subtyping

If Object.keys(user) returned (keyof User)[], TypeScript would promise that every element in the resulting array is strictly "id" | "name". At runtime, however, Object.keys(user) produces ["id", "name", "role"]. If the compiler assumed only "id" | "name" were present, downstream code relying on this guarantee could behave unexpectedly or introduce subtle runtime bugs.

2. Prototype Pollution and Enumerable Properties

Object.keys returns an array of a given object's own enumerable property names. However, JavaScript objects can inherit enumerable properties from their prototype chain, or external libraries might augment built-in prototypes. Because TypeScript cannot predict runtime alterations to an object or its prototype chain, assigning a strict compile-time union like (keyof T)[] would represent an unsound guarantee.

3. Subtyping and the Soundness Trade-off

The TypeScript design team prioritized type soundness over developer convenience in this case. In JavaScript, an object typed as T is strictly guaranteed to have at least the properties of T, but almost never only the properties of T. Therefore, the only guaranteed safe type for any generic object's keys at runtime is string.

Safe Workarounds

When you control the object lifecycle and are certain that no extra properties exist, you can enforce stricter typings using custom helper functions or type assertions.

Using a Type Assertion

const person = { name: "Sam", age: 30 };
const keys = Object.keys(person) as (keyof typeof person)[];

Creating a Generic Helper Function

To avoid repeating type assertions, define a reusable utility function:

function getKeys<T extends object>(obj: T): (keyof T)[] {
  return Object.keys(obj) as (keyof T)[];
}

const config = { host: "localhost", port: 8080 };
const configKeys = getKeys(config); // Type is ("host" | "port")[]

By keeping the default return type as string[], TypeScript prevents incorrect assumptions in open type hierarchies while still allowing developers to opt into stricter types when appropriate.
