How to Configure Bare-Metal TypeScript with noLib

This article provides a direct guide to configuring a bare-metal embedded environment using TypeScript with the noLib compiler option. It details how stripping the default standard library isolates the compiler from browser or Node.js assumptions, how to supply custom type definitions for minimal runtime environments, and how to structure hardware-level access for execution on microcontrollers via lightweight embedded JavaScript engines or ahead-of-time (AOT) compilers.

Understanding noLib in Bare-Metal Contexts

The noLib setting instructs the TypeScript compiler (tsc) to omit the default standard library declarations (such as lib.d.ts). By default, TypeScript assumes standard runtime environments that include globals like window, document, or Node.js process handles, along with heavy standard JavaScript built-ins.

In a bare-metal environment, memory constraints and execution targets (such as QuickJS, JerryScript, or Duktape running on an ARM Cortex-M or ESP32) necessitate a strict, deterministic runtime. Enabling noLib ensures that code cannot reference unsupported standard APIs, allowing developers to enforce zero-overhead type constraints directly at compile time.

Step 1: Configuring tsconfig.json

Create a dedicated tsconfig.json that disables standard library inclusion and produces lean JavaScript output without dynamic module overhead.

{
  "compilerOptions": {
    "noLib": true,
    "target": "ES5",
    "module": "none",
    "strict": true,
    "isolatedModules": true,
    "noEmitHelpers": true,
    "skipLibCheck": false,
    "types": []
  },
  "include": ["src/**/*"]
}
  • noLib: true: Removes all default declarations.
  • target: "ES5": Ensures compatibility with minimal embedded interpreters that lack full ES6+ features.
  • module: "none": Prevents CommonJS or ES module wrappers, keeping the output as a flat, direct script.
  • noEmitHelpers: true: Stops tsc from inserting dynamic polyfill helpers for features like inheritance or spread operators.

Step 2: Providing a Minimal Type Definition (core.d.ts)

Because noLib disables even fundamental JavaScript types, the compiler cannot type-check basic primitives like numbers, strings, or booleans without manual declarations. Create a minimal definition file (e.g., src/core.d.ts):

// Core primitive mappings required by the TypeScript compiler
interface Boolean {}
interface Number {}
interface String {}
interface Object {}
interface Function {}
interface Array<T> {}
interface RegExp {}
interface IArguments {}

// Essential bare-metal memory representation
type uint8 = number;
type uint32 = number;
type pointer = number;

This minimal stub provides only the symbols strictly necessary for compiler mechanics without introducing garbage collection, string manipulation prototypes, or standard math libraries.

Step 3: Defining Hardware Interfaces and MMIO

Bare-metal programming interacts directly with peripheral registers through Memory-Mapped I/O (MMIO). Define hardware access interfaces and ambient primitives inside the custom declaration files to model these interactions safely:

// src/hardware.d.ts
declare namespace Hardware {
  function read32(address: pointer): uint32;
  function write32(address: pointer, value: uint32): void;
}

declare const GPIO_BASE: pointer;
declare const GPIO_OUT_OFFSET: pointer;

These declarations map to underlying C/C++ foreign function interfaces (FFIs) provided by the host embedded interpreter, or to direct intrinsic operations if compiling ahead-of-time.

Step 4: Writing Hardware Logic

With the core constraints established, application code can now implement deterministic low-level routines:

// src/main.ts
const LED_PIN_MASK: uint32 = 1 << 5;

function toggleLed(): void {
  const current = Hardware.read32(GPIO_BASE + GPIO_OUT_OFFSET);
  Hardware.write32(GPIO_BASE + GPIO_OUT_OFFSET, current ^ LED_PIN_MASK);
}

function main(): void {
  while (true) {
    toggleLed();
  }
}

main();

Step 5: Compilation and Execution

Compile the source using the local TypeScript compiler:

npx tsc

The resulting JavaScript file contains flat, low-overhead code without runtime wrappers. This output can be flashed directly onto a target running an embedded runtime or processed by an AOT toolchain to produce an executable binary for the microcontroller.
