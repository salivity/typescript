Custom Polyfills with TypeScript noEmitHelpers

The TypeScript compiler uses internal helper functions to downlevel modern JavaScript features for older ECMAScript targets, which can lead to redundancy or suboptimal implementations in certain environments. By enabling the noEmitHelpers compiler flag, TypeScript strips out these generated helper functions from the compiled JavaScript output entirely. This mechanism allows developers to supply their own custom, globally available polyfills and helper implementations, giving them complete control over runtime behavior, performance optimizations, and bundle structure.

How TypeScript Downleveling Works

When targeting older ECMAScript versions (such as ES5), TypeScript must transform modern syntax—including decorators, rest parameters, class inheritance, and async/await—into compatible constructs. To do this, the compiler generates boilerplate runtime helpers, such as:

  • __extends for class inheritance
  • __assign for object spread properties
  • __awaiter and __generator for asynchronous functions
  • __rest for destructuring assignment

By default, the compiler inlines these functions into every file that uses the corresponding syntax. While the importHelpers flag solves code duplication by importing them from the tslib package, it still relies strictly on the official TypeScript team's implementations.

The Role of noEmitHelpers

The noEmitHelpers flag changes this behavior fundamentally. When you set "noEmitHelpers": true in your tsconfig.json, the compiler continues to rewrite modern syntax into helper call expressions, but it completely omits the definitions of those helpers from the emitted files.

For example, compiling an object spread expression will still produce code that calls __assign(...), but the declaration of __assign will not exist anywhere in the generated output.

Supplying Custom Helper Polyfills

Because the generated code references these functions as undeclared identifiers, the runtime environment will throw a ReferenceError unless you provide them globally. This allows you to inject custom polyfills prior to running your compiled code.

To use custom helpers:

  1. Enable the flag in tsconfig.json:

    {
  "compilerOptions": {
    "target": "es5",
    "noEmitHelpers": true
  }
}

  2. Define custom polyfills in the global scope: Create a dedicated entry script or polyfill module that attaches your custom functions to the global object (window in the browser or global in Node.js):

    // custom-helpers.js
var __assign = Object.assign || function (target) {
  for (var i = 1; i < arguments.length; i++) {
    var source = arguments[i];
    for (var key in source) {
      if (Object.prototype.hasOwnProperty.call(source, key)) {
        target[key] = source[key];
      }
    }
  }
  return target;
};

  3. Load the helpers first: Ensure the custom polyfill script executes before any compiled application code runs.

Practical Use Cases for Custom Helpers

  • Performance Optimization: Replace generic fallback logic (like manual loop iterations) with platform-specific or native C++ bindings available in specific runtime engines.
  • Logging and Observability: Wrap execution helpers like __awaiter to automatically track, log, or profile asynchronous operation lifecycles across an entire application.
  • Restricted Environments: Target custom micro-runtimes or embedded devices that lack standard browser APIs and need specialized execution logic for memory conservation.
