How TypeScript emitBOM Affects Output File Encoding

The emitBOM compiler option in TypeScript controls whether generated output files include a Byte Order Mark (BOM) at the beginning of the file. By default, TypeScript outputs clean, standard UTF-8 text files without a BOM. Enabling this flag instructs the compiler to prepend the UTF-8 BOM byte sequence (0xEF, 0xBB, 0xBF) to every emitted JavaScript file, source map, and declaration file, which directly alters how downstream tools, operating systems, and text editors interpret the encoding of your output files.

What is a Byte Order Mark (BOM)?

A Byte Order Mark is a specific Unicode character code (U+FEFF) placed at the very start of a text stream. While originally intended in UTF-16 and UTF-32 to indicate whether bytes are ordered in big-endian or little-endian format, in UTF-8, byte order is fixed. Therefore, a UTF-8 BOM does not indicate endianness; instead, it serves exclusively as an explicit signature marking the file's encoding as UTF-8.

Default Behavior: emitBOM: false

When emitBOM is omitted or explicitly set to false in your tsconfig.json:

  • The TypeScript compiler writes output files in standard UTF-8 encoding without any signature bytes.
  • This is the recommended modern standard across Unix, Linux, Node.js, and web environments.
  • Web servers and modern runtimes treat the output as clean ASCII-compatible UTF-8 text.

Enabled Behavior: emitBOM: true

When you enable the option in your tsconfig.json:

{
  "compilerOptions": {
    "emitBOM": true
  }
}

The compiler adds the three-byte UTF-8 signature (0xEF, 0xBB, 0xBF) to the start of all emitted .js, .jsx, .d.ts, and .js.map files.

Why and When to Use emitBOM

The primary reason to enable emitBOM is compatibility with legacy Windows-based software and runtimes:

  • Legacy Windows Applications: Older Windows applications, legacy editors, and Windows PowerShell 5.1 often default to reading non-BOM files using the system's local ANSI code page (such as Windows-1252), causing non-ASCII characters to become garbled (mojibake). The BOM forces these programs to correctly interpret the file as UTF-8.
  • Compilation and Packaging Pipelines: Certain older enterprise compilers or resource packaging tools expect all Unicode assets to explicitly declare their encoding through a BOM.

Potential Drawbacks of Enabling emitBOM

While emitBOM solves encoding detection issues on legacy Windows tools, it can introduce issues in modern development workflows:

  • Unix/Linux Scripts: In environments that treat scripts as executable (e.g., using a #!/usr/bin/env node shebang), a leading BOM will corrupt the shebang line and prevent execution.
  • String Concatenation and Bundlers: Certain build tools or naive file concatenators may not strip the BOM, leading to invisible characters appearing in the middle of bundled scripts.
  • JSON and Data Parsers: Strict parsers may throw syntax errors if a BOM is encountered at the start of a generated data or map file.

Unless your deployment environment or build pipeline specifically requires a BOM for UTF-8 identification, emitBOM should remain disabled.
