Why Parameter Decorators Cannot Modify Values in TypeScript

Parameter decorators in TypeScript are a powerful language feature, yet developers frequently encounter the limitation that they cannot directly intercept or mutate method arguments. This article explores the architectural reasons behind this restriction, focusing on TypeScript's decorator evaluation lifecycle, the ignored return value of parameter decorators, and how metadata observation differs from runtime execution. It also outlines the standard pattern used to achieve parameter modification by pairing parameter decorators with method decorators.

1. Execution Timing: Definition Time vs. Invocation Time

The primary reason parameter decorators cannot modify argument values is that decorators execute when a class is declared, not when a method is called.

When the JavaScript runtime evaluates a class definition:

  • Decorator functions run once to set up the class structure.
  • At this point, the method has not been invoked, meaning runtime arguments simply do not exist.
  • Because there is no active invocation or call stack to intercept, there are no concrete values for the parameter decorator to inspect or mutate.

2. The Return Value is Ignored by Design

In TypeScript's decorator implementation (both experimental and ECMAScript stages), different decorators possess different capabilities based on what the runtime does with their return values:

  • Method Decorators can return a new PropertyDescriptor, allowing you to replace the method implementation and intercept incoming calls.
  • Class Decorators can return a new constructor function to replace the class.
  • Parameter Decorators have their return values completely ignored by the runtime.

A parameter decorator function receives three arguments:

  1. target: The prototype of the class (for an instance member) or the constructor function (for a static member).
  2. propertyKey: The name of the member (string or symbol).
  3. parameterIndex: The ordinal index of the parameter in the function’s argument list.

Because the decorator signature enforces that any returned value is discarded, the decorator cannot supply a replacement value, a default wrapper, or an interceptor on its own.

3. The Intended Purpose: Metadata Storage

Parameter decorators are designed strictly for observation and metadata registration. Their sole capability is to record information about a specific parameter at a specific index.

Using metadata libraries such as reflect-metadata, a parameter decorator attaches custom flags, validation rules, or dependency injection tokens to the class prototype under the target method's key. This metadata remains dormant until another mechanism acts upon it.

4. The Solution: Combining Parameter and Method Decorators

To modify, transform, or validate a parameter at runtime, you must pair the parameter decorator with a method decorator.

  1. Parameter Decorator: Registers the index of the parameter and the required transformation or validation rule using metadata reflection.
  2. Method Decorator: Replaces the original method's value in the PropertyDescriptor with a wrapper function.
  3. Runtime Execution: When the wrapped method is invoked, it retrieves the metadata for its parameters, reads the arguments array via arguments or rest parameters (...args), modifies the value at the designated index, and passes the updated arguments to the original method.

Parameter decorators cannot modify values in isolation because they lack both the execution context of a method call and the runtime mechanism to override argument bindings. Modifying runtime parameters requires wrapping the function itself via a method decorator.
