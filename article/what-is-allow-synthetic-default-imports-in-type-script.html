What Is allowSyntheticDefaultImports in TypeScript?

The allowSyntheticDefaultImports compiler option in TypeScript enables type-checking support for default imports from modules that do not explicitly define a default export. This article breaks down why this flag exists, the specific problem it addresses when importing CommonJS modules, its limitations regarding runtime output, and how it compares to the related esModuleInterop setting.

The Problem: CommonJS vs. ECMAScript Modules

In ECMAScript Modules (ESM), default exports and named exports are strictly differentiated. To import a default value, the target module must explicitly specify an export default.

However, many older or legacy packages use CommonJS, where exports are assigned directly to module.exports or exports:

// A typical CommonJS module (e.g., 'example-lib')
module.exports = {
  doSomething: () => {}
};

Under strict TypeScript checking, attempting to import this library using the standard ES module default import syntax causes a compiler error:

import exampleLib from "example-lib";
// Error: Module '"example-lib"' has no default export.

To satisfy TypeScript without additional configuration, developers historically had to use the namespace import syntax:

import * as exampleLib from "example-lib";

What allowSyntheticDefaultImports Achieves

When you set "allowSyntheticDefaultImports": true in your tsconfig.json, TypeScript relaxes this specific type-checking rule.

The flag creates a "synthetic" (virtual) default export for any module whose exports can be viewed as an object. This allows you to write:

import React from "react";
import express from "express";

Instead of requiring:

import * as React from "react";
import * as express from "express";

The compiler will treat the entire exported namespace as if it were the default export, eliminating the has no default export error during compilation.

The Crucial Catch: Type Checking Only

The most important aspect of allowSyntheticDefaultImports is that it does not modify emitted JavaScript. It is strictly a type-checking convenience.

If TypeScript compiles your code to CommonJS or native ESM, it will not inject any runtime helpers to ensure the default import actually works. If your runtime environment or bundler does not automatically handle synthetic default imports, your code may crash at runtime with errors such as TypeError: exampleLib is not a function or TypeError: Cannot read properties of undefined.

This flag is safe to use on its own only if:

  1. You use a tool like Babel, Webpack, or Vite that automatically handles interoperability between CommonJS and ES modules.
  2. The runtime environment already provides an interoperability layer.

Difference Between allowSyntheticDefaultImports and esModuleInterop

To solve both the type-checking and the runtime execution issues, TypeScript introduced the esModuleInterop flag.

  • allowSyntheticDefaultImports: Changes only TypeScript's type analysis. It emits standard imports without adding helper code.
  • esModuleInterop: Changes type analysis and emits runtime helper functions (__importDefault and __importStar) to ensure default imports work seamlessly across CommonJS modules at runtime.

Enabling esModuleInterop automatically turns on allowSyntheticDefaultImports. In modern TypeScript projects, enabling "esModuleInterop": true is generally recommended over using allowSyntheticDefaultImports alone, as it guarantees safety at both compile time and runtime.
