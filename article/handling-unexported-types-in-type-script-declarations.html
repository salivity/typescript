Handling Unexported Types in TypeScript Declarations

When compiling projects with declaration emit enabled, TypeScript must generate .d.ts files that fully describe a library's public API surface without breaking consumer code. When an exported function, class, or variable depends on an un-exported type, the compiler must resolve how to represent that dependency in the generated output. This article explains how TypeScript handles these un-exported dependencies, the common errors it triggers, the fallback mechanisms it employs, and how modern compiler features address the problem.

The Core Challenge of Un-exported Types

When TypeScript generates .d.ts files using the declaration compiler flag, it writes the public interface of your application or library so downstream consumers can type-check against it. If an exported API references an internal type that is not exported, TypeScript cannot simply write that type name into the declaration file; doing so would result in a declaration file referencing a symbol that downstream consumers cannot resolve.

For example, consider an exported function returning an internal interface:

interface InternalConfig {
  retries: number;
}

export function createConfig(): InternalConfig {
  return { retries: 3 };
}

Because createConfig is exported but InternalConfig is not, TypeScript must evaluate whether it can safely emit the declaration or if it must halt compilation with an error.

Compiler Errors: TS4023 and TS2742

In many scenarios where an un-exported type cannot be safely resolved or referenced, TypeScript fails the build with one of two primary compiler errors:

  1. TS4023: "Exported variable '[name]' has or is using name '[type]' from external module '[path]' but cannot be named."
    This occurs when an exported symbol relies on a type from an external package or another file that has not been explicitly re-exported.

  2. TS2742: "The inferred type of '[name]' cannot be named without a reference to '[path]'."
    This happens frequently in monorepos or multi-package projects where an inferred return type references a dependency not directly referenced or exported in the consuming project's entry point.

When these errors trigger, the compiler refuses to emit declarations to prevent publishing broken .d.ts files that consumers cannot parse.

Structural Inlining

If the un-exported dependency is a simple object type, type alias, or interface defined in the same file, TypeScript often circumvents the naming restriction by inlining the structure directly into the emitted .d.ts file.

Using the earlier createConfig example, TypeScript will bypass the un-exported name and emit:

export declare function createConfig(): {
  retries: number;
};

By expanding the shape structurally, TypeScript eliminates the reference to the private symbol entirely. However, structural inlining has limitations: it does not work cleanly with recursive types, private class members, nominal types, or interfaces that depend on complex inheritance chains.

Dynamic import() Type Emission

When an un-exported type resides in another file or an external package, TypeScript cannot always inline the structure. Instead, the compiler generates an inline dynamic import type directly within the .d.ts output:

export declare function fetchSettings(): import("./internal").Settings;

This mechanism allows the emitted declaration to reference the correct type definition without requiring the author to manually export the symbol from the public module boundary. Downstream tools and IDEs use this path to resolve the shape behind the scenes.

Isolated Declarations (--isolatedDeclarations)

Prior to TypeScript 5.5, the compiler performed extensive type inference across files to resolve and inline these hidden dependencies, which caused significant performance overhead and unpredictable declaration files.

With the introduction of the --isolatedDeclarations flag, TypeScript alters how it handles these scenarios by requiring developers to be explicit:

  • Functions and exports that reference un-exported or complex inferred types must have explicit type annotations.
  • If a type must appear in a public signature, it must be exported.

Under isolated declaration mode, the compiler refuses to guess or silently inline hidden types, ensuring that all dependencies required by declaration files are explicitly tracked, exported, and cleanly generated.
