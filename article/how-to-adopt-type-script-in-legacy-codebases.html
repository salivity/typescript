How to Adopt TypeScript in Legacy Codebases

Migrating a massive legacy JavaScript codebase to TypeScript can feel overwhelming, but a gradual, iterative approach makes the transition manageable and safe. This guide outlines proven strategies for incrementally introducing TypeScript without halting feature development, breaking production builds, or overwhelming engineering teams. By establishing the right compiler settings, leveraging hybrid tooling, prioritizing core modules, and systematically tightening type safety, organizations can modernize their codebases smoothly and reliably.

1. Configure a Permissive TypeScript Environment

The first step is introducing a tsconfig.json file configured to accommodate existing JavaScript alongside TypeScript. Setting allowJs: true instructs the TypeScript compiler (tsc) to process .js files without compiling errors, while noEmit: true allows TypeScript to act strictly as a linter if you are using tools like Babel or Webpack for the actual build.

Keep initial strictness flags off:

  • Set strict: false
  • Set noImplicitAny: false

This establishes the baseline infrastructure without generating thousands of blocking compile-time errors on day one.

2. Integrate Type Checking into CI/CD

Integrate TypeScript verification into your continuous integration pipeline early. Add a dedicated script (e.g., npm run type-check) that runs tsc --noEmit.

Initially, run this check only against changed files or configured directories, or ensure that it passes with your permissive configuration. Making type checking a prerequisite for merging ensures that no new type regressions are introduced as the migration progresses.

3. Use JSDoc for Zero-Build Type Checking

Before converting .js files to .ts, teams can start typing code immediately using standard JSDoc comments. When combined with the // @ts-check directive at the top of a JavaScript file, the TypeScript compiler checks the file using JSDoc type annotations.

This strategy requires zero file renaming, preserves Git history cleanly, and familiarizes the team with TypeScript’s type system while remaining entirely within standard JavaScript syntax.

4. Prioritize High-Impact Boundaries First

Avoid random file conversions. Instead, target high-traffic, foundational layers that yield the highest return on investment:

  • Shared Utilities and Helpers: These are imported across the entire application. Typing them provides immediate downstream autocomplete and type safety for other developers.
  • API Contracts and Data Models: Define types and interfaces for backend responses and global state stores. Catching runtime data mismatches at compile time prevents widespread frontend bugs.
  • New Features and Modules: Mandate that all net-new files must be written in TypeScript (.ts or .tsx).

5. Implement the "Boy Scout Rule" for Existing Files

Enforce a policy where developers convert existing JavaScript files to TypeScript only when touching them for bug fixes or feature work.

When a developer modifies a legacy module:

  1. Rename the file from .js to .ts (or .jsx to .tsx).
  2. Fix any immediate syntax and structural issues.
  3. Apply pragmatic typing to the touched functions.
  4. Keep moving forward without attempting to refactor the entire module's architecture.

Over time, the most frequently modified—and therefore most critical—parts of the codebase naturally become fully typed.

6. Use the any Type and @ts-expect-error Pragmatically

Dogmatic adherence to strict typing can stall a gradual migration. When converting complex legacy code, it is acceptable to use the any type or explicit type assertions (as unknown as TargetType) to keep momentum.

For intentional workarounds or third-party library issues, use // @ts-expect-error with an explanatory comment instead of // @ts-ignore. This ensures that if the underlying issue is resolved later, the compiler prompts developers to remove the obsolete suppression directive.

7. Incrementally Increase Compiler Strictness

Once a significant portion of the codebase is converted and developers are comfortable with TypeScript, begin enabling strict compiler checks incrementally:

  1. Enable noImplicitReturns and noFallthroughCasesInSwitch.
  2. Enable noImplicitAny module by module, or across the whole project once coverage is high.
  3. Enable strictNullChecks to eliminate common runtime errors like "cannot read property of undefined."
  4. Finally, enable strict: true.

Taking a tiered approach prevents developer fatigue and steadily elevates overall code quality without disrupting regular release cycles.
