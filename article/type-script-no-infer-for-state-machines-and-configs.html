TypeScript NoInfer for State Machines and Configs

TypeScript 5.4 introduced the NoInfer<T> intrinsic utility type, providing developers with explicit control over how generic types are inferred across function parameters. In complex patterns such as finite state machines and configuration objects, TypeScript's default behavior often infers types from secondary locations, leading to unwanted type widening or missed compilation errors. By wrapping specific generic usages in NoInfer<T>, you instruct the compiler to resolve the generic type solely from primary candidate sites, ensuring that dependent properties act strictly as consumers rather than contributors to the inferred type.

The Inference Problem in Configuration Objects

By default, when a generic type parameter T is referenced in multiple parameters or object properties, TypeScript collects type candidates from every occurrence and merges them into a union.

Consider a configuration function where a list of allowed values should determine the type:

function createConfig<T extends string>(config: {
  allowed: T[];
  default: T;
}) {
  return config;
}

// Undesired behavior:
const config = createConfig({
  allowed: ["read", "write"],
  default: "admin", // No error! 'T' is inferred as "read" | "write" | "admin"
});

Instead of validating that default belongs to the allowed array, TypeScript uses "admin" as an inference candidate for T. As a result, T silently widens to "read" | "write" | "admin", defeating the purpose of the configuration constraint.

Solving Configuration Inference with NoInfer

Using NoInfer<T> prevents TypeScript from using the marked position to infer the generic parameter:

function createConfig<T extends string>(config: {
  allowed: T[];
  default: NoInfer<T>;
}) {
  return config;
}

const config = createConfig({
  allowed: ["read", "write"],
  default: "admin", // Type error: Type '"admin"' is not assignable to type '"read" | "write"'
});

Because default is annotated with NoInfer<T>, TypeScript determines T solely from allowed: ["read", "write"]. Once T is locked in, the compiler checks default against that established type.

Improving State Machine Inference

State machines depend on rigid state definitions where transitions and events must only target existing states. Without NoInfer, introducing a typo in a transition target can accidentally register that invalid target as a new, valid state in the machine's type definition.

type TransitionConfig<State extends string> = {
  initial: State;
  states: Record<State, { onNext?: NoInfer<State> }>;
};

function createMachine<State extends string>(config: TransitionConfig<State>) {
  return config;
}

const machine = createMachine({
  initial: "idle",
  states: {
    idle: { onNext: "loading" },
    loading: { onNext: "sucess" }, // Error: Type '"sucess"' is not assignable to type '"idle" | "loading"'
  },
});

In this implementation, the states object keys serve as the sole source of truth for State. Wrapping the onNext target in NoInfer<State> ensures that typos (such as "sucess" instead of "success") trigger a compile-time error immediately, rather than expanding the union of available states and causing runtime failures.

Advantages Over Legacy Workarounds

Prior to TypeScript 5.4, achieving this behavior required lower-level type gymnastics, such as using conditional type flattening:

type NoInferLegacy<T> = [T][T extends any ? 0 : never];

While functional, this approach was non-intuitive, slowed down compiler performance in large codebases, and reduced readability. NoInfer<T> is a native compiler intrinsic that:

  1. Clarifies intent: Explicitly communicates which inputs govern inference and which inputs consume it.
  2. Improves diagnostics: Generates clear, localized error messages at the exact site of the mismatch.
  3. Enhances performance: Eliminates the overhead of recursive conditional type calculations during the inference phase.
