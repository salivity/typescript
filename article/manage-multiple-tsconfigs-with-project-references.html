Manage Multiple tsconfigs with Project References

TypeScript project references allow developers to structure large codebases, monorepos, or multi-target applications into smaller, modular builds that compile independently. This article details the proper architecture for managing multiple tsconfig.json files using project references, focusing on the root solution pattern, necessary compiler flags, and build command execution to achieve faster compilation times and strict code boundaries.

The Solution-Style Architecture

The standard and most maintainable approach to managing multiple configurations is the "solution style" structure. This pattern divides configurations into three distinct roles:

  1. Shared Base (tsconfig.base.json): Holds universally applied compiler options (e.g., strict, target, moduleResolution).
  2. Project Configurations (packages/*/tsconfig.json or sub-configs): Individual configurations for each discrete module, package, or environment (such as src vs. test).
  3. Root Orchestrator (tsconfig.json): A high-level file containing references to all sub-projects without containing source files itself.

Directory Structure Example

my-project/
├── tsconfig.base.json
├── tsconfig.json
└── packages/
    ├── core/
    │   ├── src/
    │   └── tsconfig.json
    └── api/
        ├── src/
        └── tsconfig.json

Step 1: Define the Shared Base Configuration

Create a tsconfig.base.json file at the root level to prevent duplicating compiler settings.

{
  "compilerOptions": {
    "target": "ES2022",
    "module": "NodeNext",
    "moduleResolution": "NodeNext",
    "strict": true,
    "skipLibCheck": true,
    "forceConsistentCasingInFileNames": true
  }
}

Step 2: Configure Child Projects

Every child project referenced by another project must enable the composite setting. Setting "composite": true enforces that the project can be built incrementally, generates declaration files (.d.ts), and enables the TypeScript compiler to track build dependencies.

packages/core/tsconfig.json (Dependency)

{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "composite": true,
    "declaration": true,
    "declarationMap": true,
    "rootDir": "src",
    "outDir": "dist"
  },
  "include": ["src"]
}

packages/api/tsconfig.json (Consumer)

If api depends on core, add a reference pointing to the core configuration directory or file:

{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "composite": true,
    "declaration": true,
    "declarationMap": true,
    "rootDir": "src",
    "outDir": "dist"
  },
  "references": [
    { "path": "../core" }
  ],
  "include": ["src"]
}

Step 3: Configure the Root Solution File

The root tsconfig.json connects all independent configurations. It should not compile files directly; instead, set "files": [] and register every project under "references".

{
  "files": [],
  "references": [
    { "path": "./packages/core" },
    { "path": "./packages/api" }
  ]
}

Setting "files": [] prevents the root build from compiling loose files, while the list of references informs IDEs and build tools about the relationship between all modules in the repository.

Step 4: Compiling with Build Mode

Standard compilation via tsc ignores project references. To build a multi-tsconfig setup properly, you must use TypeScript's build mode by using the --build (or -b) flag.

# Build all referenced projects in dependency order
tsc --build

# Perform a clean build
tsc --build --clean

# Watch all projects simultaneously
tsc --build --watch

Build mode automatically determines the dependency graph, builds dependencies first (in this case, core before api), skips projects whose outputs are up to date via .tsbuildinfo files, and re-compiles only what has changed.

Key Rules for Project References

  • Always Enable composite: Any project listed in a references array must have "composite": true.
  • Consume Built Types: When importing from a referenced package, ensure your module resolution points to the built declaration files or that package's entry point rather than importing raw .ts files across project boundaries.
  • Separate Tests from Production: Use references to isolate test suites. Create a tsconfig.test.json that references tsconfig.src.json to keep heavy test types and dependencies out of your production compilation pipeline.
