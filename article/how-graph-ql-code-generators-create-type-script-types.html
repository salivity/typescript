How GraphQL Code Generators Create TypeScript Types

GraphQL code generators automate type safety by transforming GraphQL schemas and query documents into native TypeScript definitions. This article explains the technical pipeline behind this transformation: parsing GraphQL Schema Definition Language (SDL) and client operations into Abstract Syntax Trees (ASTs), validating and matching operations against the schema, mapping GraphQL types to TypeScript counterparts, and emitting precise, operation-specific TypeScript interfaces.

1. Ingestion and AST Parsing

The process begins by reading two sets of inputs: the GraphQL schema (provided via an introspection JSON file or SDL) and client-side operations (queries, mutations, subscriptions, and fragments extracted from .graphql files or inline template literals).

The code generator uses the core graphql-js parser to convert this raw text into an Abstract Syntax Tree (AST). The AST is a structured JSON representation of the syntax, breaking down objects, scalar definitions, directives, fields, and arguments into distinct nodes.

2. Validation and Normalization

Once the ASTs are created, the generator validates the client operations against the target schema:

  • Fragment Inlining and Resolution: Named fragments are resolved and matched to their target types.
  • Semantic Analysis: The generator verifies that requested fields exist on the queried types, arguments match defined inputs, and variables conform to expected types.
  • Directive Processing: Custom client or server directives (such as @client or @skip) are processed to alter type generation rules accordingly.

3. Type Mapping (Schema Level)

The generator establishes a mapping layer that translates GraphQL primitives to TypeScript equivalents:

  • Scalars: Standard scalars are converted directly (String to string, Int and Float to number, Boolean to boolean, and ID to string). Custom scalars are mapped via configuration (e.g., mapping a DateTime scalar to a TypeScript string or Date).
  • Nullability Handling: In GraphQL, fields are nullable by default unless marked with an exclamation point (!). The generator mirrors this by appending | null or optional modifiers (?) to TypeScript properties unless a field is explicitly defined as non-nullable.
  • Enums: GraphQL enums are converted into TypeScript string unions or native TypeScript enum declarations.
  • Input Objects: Mutation input types are converted into standard TypeScript interfaces representing request payloads.

4. Selection Set Projection (Operation Level)

A major challenge in GraphQL code generation is that client queries rarely fetch entire schema entities; they select specific sub-fields. Creating types simply mirroring the server-side models leads to inaccurate typings on the client.

To handle this, the generator performs a projection:

  1. It traverses the operation AST's SelectionSet.
  2. It walks through the corresponding path in the schema AST.
  3. It constructs a narrow, bespoke TypeScript type representing only the requested fields for that specific query.
  4. For polymorphic responses (Unions and Interfaces), it creates TypeScript discriminated union types based on the __typename field.

5. Code Emission

In the final step, the generator serializes the in-memory TypeScript representations into code files (typically .ts or .d.ts). Using string templates or AST printers (such as the TypeScript Compiler API), the generator writes out:

  • Base Schema Types: Global definitions for all types, inputs, and enums defined in the API.
  • Operation Types: Strongly typed definitions for both the input variables (Exact<{ ... }>) and the query response data ({ __typename: 'Query', ... }).
  • Framework Artifacts (Optional): Pre-typed hooks or SDK functions (e.g., Apollo Client, TanStack Query, or URQL integrations) that bind the generated input and output types directly to execution functions.
