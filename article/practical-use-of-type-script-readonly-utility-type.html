Practical Use of TypeScript Readonly Utility Type

This article explores the practical applications of TypeScript's built-in Readonly<T> utility type in modern software development. You will learn how Readonly enforces immutability at compile time, prevents unintended side effects in functions, protects application state in frameworks like React and Redux, and safeguards configuration objects.

Understanding Readonly<T>

The Readonly<T> utility type constructs a new type with all properties of T set to readonly. This means that once an object is initialized with this type, its properties cannot be reassigned. The TypeScript compiler will throw an error if any assignment is attempted.

interface User {
  id: string;
  name: string;
}

const user: Readonly<User> = {
  id: "u123",
  name: "Alice"
};

// Error: Cannot assign to 'name' because it is a read-only property.
user.name = "Bob";

1. Preventing Unintended Mutations in Functions

In JavaScript, objects and arrays are passed by reference. If a function modifies an incoming object, that mutation affects the caller's scope, leading to subtle bugs. Using Readonly<T> on function parameters guarantees that the function treats arguments as strictly read-only.

interface CartItem {
  id: string;
  price: number;
}

function calculateTotal(items: Readonly<CartItem[]>): number {
  // items.push(...) // Error: Property 'push' does not exist on type 'readonly CartItem[]'
  return items.reduce((sum, item) => sum + item.price, 0);
}

2. State Management in UI Libraries

Frameworks like React, Redux, and Vue rely on immutable state to detect changes and trigger UI re-renders correctly. Directly mutating state violates this paradigm. Wrapping state interfaces with Readonly ensures that developers create new state objects rather than mutating existing ones.

interface AppState {
  theme: "light" | "dark";
  notificationsCount: number;
}

function reducer(state: Readonly<AppState>, action: { type: string }): AppState {
  switch (action.type) {
    case "TOGGLE_THEME":
      // state.theme = 'dark'; // Compile-time error
      return {
        ...state,
        theme: state.theme === "light" ? "dark" : "light"
      };
    default:
      return state;
  }
}

3. Protecting Configuration and Environment Objects

Application configurations, environment variables, and feature flags should remain static throughout an application's lifecycle. Typing these structures as Readonly prevents accidental runtime overwrites from other modules or third-party packages.

interface AppConfig {
  apiUrl: string;
  timeoutMs: number;
  enableDebug: boolean;
}

export const CONFIG: Readonly<AppConfig> = {
  apiUrl: "https://api.example.com",
  timeoutMs: 5000,
  enableDebug: false
};

4. Caveat: Shallow vs. Deep Immutability

The native Readonly<T> utility type is shallow. It only protects top-level properties from reassignment; nested objects remain mutable.

interface Profile {
  user: {
    name: string;
  };
}

const profile: Readonly<Profile> = {
  user: { name: "Charlie" }
};

// profile.user = { name: "David" }; // Error: Cannot assign to 'user'
profile.user.name = "David"; // Allowed: Nested properties are not readonly

For deeply nested structures, you must either apply Readonly recursively to nested interfaces or implement a custom DeepReadonly<T> mapped type.
