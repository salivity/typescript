TypeScript Web Worker Type Checking with tsconfig

This article explains how to enforce strict type checking in TypeScript for Web Workers by utilizing isolated, dedicated tsconfig files. By separating the execution context configurations, developers can eliminate global namespace collisions between the DOM and the worker environments, restrict inappropriate API access at compile time, and strongly type cross-thread communication using shared type contracts.

The Global Scope Conflict

In a browser environment, the main execution thread operates within the Window context, providing access to APIs like document, window, and direct DOM manipulation. Web Workers run in a distinct background thread governed by the DedicatedWorkerGlobalScope, where DOM access is restricted, and alternative APIs like importScripts and worker-specific postMessage implementations exist.

By default, adding both "DOM" and "WebWorker" to the "lib" array in a single tsconfig.json merges their global type definitions. This merge causes TypeScript to permit invalid code:

  • Calling window or document inside worker files compiles without errors, but fails at runtime.
  • Worker-specific globals like close() or the worker variant of postMessage() inadvertently become valid in main-thread files.

To enforce strict, accurate type checking, each environment must be scoped to its own type definitions via separate configuration files.

Configuring a Dedicated Worker tsconfig

To isolate the environments, create a dedicated configuration file specifically for worker files, commonly named tsconfig.worker.json.

{
  "compilerOptions": {
    "target": "ES2022",
    "lib": ["ES2022", "WebWorker"],
    "module": "ESNext",
    "moduleResolution": "bundler",
    "strict": true,
    "noEmit": true
  },
  "include": ["src/**/*.worker.ts", "src/workers/**/*.ts"]
}

Key compiler settings include:

  • lib: Exclusively contains "WebWorker" alongside the relevant ECMAScript standard (e.g., "ES2022"). The standard "DOM" library is deliberately omitted.
  • include: Explicitly targets worker entry points and worker-specific utilities.

Adjusting the Main Application tsconfig

The primary configuration (such as tsconfig.app.json or tsconfig.json) must exclude worker files and restrict its standard library inclusions strictly to the DOM:

{
  "compilerOptions": {
    "target": "ES2022",
    "lib": ["ES2022", "DOM", "DOM.Iterable"],
    "module": "ESNext",
    "moduleResolution": "bundler",
    "strict": true,
    "noEmit": true
  },
  "include": ["src/**/*"],
  "exclude": ["src/**/*.worker.ts", "src/workers/**/*.ts"]
}

By excluding the worker files from the main project and removing "WebWorker" from the main lib array, neither configuration pollutes the other's scope.

Enforcing Strict Message Contracts

While dedicated configuration files secure the global runtime environment, communication across threads via postMessage requires structured typing to avoid the any type fallback.

Define shared interfaces using discriminated unions in a separate shared file accessible to both configurations:

// src/types/worker-messages.ts
export type WorkerRequest = 
  | { type: 'PROCESS_IMAGE'; payload: { buffer: ArrayBuffer; width: number } }
  | { type: 'CANCEL' };

export type WorkerResponse = 
  | { type: 'SUCCESS'; result: Uint8ClampedArray }
  | { type: 'ERROR'; message: string };

In the worker file (src/image-processor.worker.ts), type the incoming and outgoing messages explicitly:

import type { WorkerRequest, WorkerResponse } from './types/worker-messages';

// Re-cast the global context to ensure strong typing
const ctx: DedicatedWorkerGlobalScope = self as any;

ctx.onmessage = (event: MessageEvent<WorkerRequest>) => {
  const message = event.data;

  switch (message.type) {
    case 'PROCESS_IMAGE':
      // message.payload is strictly typed
      const result = new Uint8ClampedArray();
      ctx.postMessage({ type: 'SUCCESS', result } satisfies WorkerResponse);
      break;
    case 'CANCEL':
      break;
  }
};

Connecting Configurations with Project References

To ensure continuous type verification across the entire project during build steps or CI/CD pipelines, use TypeScript's Project References. The root tsconfig.json coordinates the builds:

{
  "files": [],
  "references": [
    { "path": "./tsconfig.app.json" },
    { "path": "./tsconfig.worker.json" }
  ]
}

Both referenced configurations must enable "composite": true in their compilerOptions. Running tsc --build will validate both contexts simultaneously according to their unique type constraints without runtime namespace collision.
