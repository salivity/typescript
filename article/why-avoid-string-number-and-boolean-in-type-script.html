Why Avoid String, Number, and Boolean in TypeScript

In TypeScript, developers should consistently use lowercase types like string, number, and boolean instead of their uppercase counterparts String, Number, and Boolean. While these uppercase types may seem interchangeable at first glance, they refer to JavaScript's object wrappers rather than the primitive data types. Using wrapper types leads to subtle type-checking errors, unintended behavior, and unnecessary memory overhead, making the use of primitive lowercase types the standard best practice in modern TypeScript development.

Primitives vs. Object Wrapper Types

JavaScript differentiates between primitive values and wrapper objects. Primitive values—such as 'hello', 42, and true—are lightweight, immutable values stored directly in memory.

When you define a type using uppercase String, Number, or Boolean, you are targeting the special JavaScript object constructor wrapper (e.g., instances created via new String('hello')).

// Lowercase refers to the primitive value
const primitiveText: string = "hello";

// Uppercase refers to the wrapper object instance
const objectText: String = new String("hello");

JavaScript automatically "boxes" a primitive into an object temporarily when you access methods like .toUpperCase() or .toFixed(), and then discards the object immediately. Explicitly declaring variables as these object wrappers is almost never needed.

Assignability and Type Mismatches

One of the primary reasons to avoid uppercase types is the one-way type compatibility problem. TypeScript allows a primitive to be assigned to an object type, but an object type cannot be assigned to a primitive.

let primitiveString: string = "hello";
let objectString: String = new String("hello");

// This succeeds:
objectString = primitiveString;

// This fails with a type error:
primitiveString = objectString; 
// Error: Type 'String' is not assignable to type 'string'.

If an API or function expects a standard string, passing a variable typed as String will trigger a compile-time error. This discrepancy breaks interoperability across libraries and utility functions that correctly rely on primitives.

Truthiness and Comparison Hazards

Wrapper objects introduce unexpected runtime bugs when evaluated in conditional statements. In JavaScript, any object is truthy, even if it wraps a falsy value.

const falseWrapper: Boolean = new Boolean(false);

if (falseWrapper) {
  // This block executes because falseWrapper is an object!
  console.log("This will unexpectedly run.");
}

Similarly, reference equality (===) fails when comparing wrapper objects to primitive values, leading to silent logical errors during execution.

Official Guidelines and Linting Rules

TypeScript's official documentation explicitly advises against using Number, String, Boolean, Symbol, or Object. Popular static analysis tools like ESLint enforce this convention out of the box through rules such as @typescript-eslint/no-wrapper-object-types (formerly part of @typescript-eslint/ban-types).

Always use the lowercase primitive keywords—string, number, boolean, symbol, and bigint—to ensure type safety, avoid unexpected object behavior, and maintain consistency with the broader TypeScript ecosystem.
