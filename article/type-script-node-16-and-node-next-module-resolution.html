TypeScript Node16 and NodeNext Module Resolution

TypeScript's node16 and nodenext module resolution modes align TypeScript's compilation and lookup behaviors directly with Node.js's native dual CommonJS (CJS) and ECMAScript Modules (ESM) system. This article explains how these resolution modes operate, how they determine whether a file is treated as ESM or CommonJS, how relative imports and file extensions are handled, and how package entry points are resolved using modern package.json fields.

The Difference Between Node16 and NodeNext

In TypeScript, node16 freezes module resolution behavior to match the specifications established in Node.js v16. The nodenext setting serves as an evolving target that updates alongside future Node.js releases to reflect newer module behaviors. In practice, both currently share identical resolution mechanics, but nodenext ensures your configuration adopts modern Node.js module semantics as the runtime ecosystem updates.

Determining Module Format: ESM vs. CommonJS

Under node16 and nodenext, TypeScript does not assume your entire project is purely ESM or purely CommonJS. Instead, the format of each individual file is determined dynamically using two primary factors: file extensions and package.json configurations.

  1. Explicit File Extensions:
    • .mts files compile to .mjs and are always treated as ES modules.
    • .cts files compile to .cjs and are always treated as CommonJS modules.
    • .ts files compile to .js and inherit their format from the nearest parent package.json.
  2. The package.json "type" Field:
    • If the nearest enclosing package.json contains "type": "module", all .ts files in that scope are treated as ES modules.
    • If "type" is "commonjs" or omitted, all .ts files are treated as CommonJS.

The resolved module format dictates syntax allowances: top-level await and import/export statements are allowed in ESM, while require() and module.exports are restricted to CommonJS files unless dynamically imported.

Mandatory Relative Import Extensions

When writing relative imports in an ES module context under node16 or nodenext, TypeScript adheres strictly to the ECMAScript module specification implemented by Node.js. Node.js ESM does not perform directory lookups (like /index.js) or automatically append file extensions.

Because of this runtime requirement:

  • You must include the explicit output file extension in your import path.
  • Even when authoring a .ts file, you must write the import path using .js, .mjs, or .cjs.
// Importing './utils.ts' in an ESM context:
import { helper } from "./utils.js"; 

// Directory index imports require explicit filenames:
import { config } from "./config/index.js";

TypeScript uses the .js extension in the source code to locate the corresponding ./utils.ts or ./utils.d.ts file on disk during type checking, and it outputs the exact ./utils.js path to the compiled JavaScript.

Package Resolution: exports and imports

Under traditional node (Node10) resolution, TypeScript looked only at the "main" or "types" fields in a dependency’s package.json. With node16 and nodenext, TypeScript prioritizes the modern Node.js "exports" and "imports" fields.

The "exports" Field

The "exports" field in a dependency defines internal encapsulation and public entry points. If a library defines an "exports" field, TypeScript will prevent imports of any subpaths not explicitly listed.

When resolving imports, TypeScript matches conditions specified inside "exports". Under node16 and nodenext, resolution changes based on whether the consuming file is ESM or CJS:

  • An ESM file resolves against the "import" condition.
  • A CommonJS file resolves against the "require" condition.
  • Type definitions are located using the "types" condition.

For example, given this dependency configuration:

{
  "name": "example-lib",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js",
      "require": "./dist/index.cjs"
    },
    "./feature": {
      "types": "./dist/feature.d.ts",
      "import": "./dist/feature.js"
    }
  }
}
  • An import of example-lib inside an ES module maps to ./dist/index.js and checks types via ./dist/index.d.ts.
  • An attempt to import example-lib/dist/internal.js fails at compile time because it is not exposed in the "exports" map.

The "imports" Field (Subpath Imports)

TypeScript also honors internal package aliases declared in the "imports" field of your project's own package.json. These entries must begin with a # symbol and allow internal modules to reference paths without relative traversal:

{
  "imports": {
    "#database": {
      "types": "./src/db/index.d.ts",
      "default": "./dist/db/index.js"
    }
  }
}

A file can reference import db from "#database";, and TypeScript will correctly resolve the types and module location based on the active conditions.
