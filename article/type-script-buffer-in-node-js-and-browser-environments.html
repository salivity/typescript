TypeScript Buffer in Node.js and Browser Environments

Managing binary data across both Node.js and browser environments in TypeScript presents unique challenges because the Buffer class is a Node.js runtime global rather than a standard web API. This article explains how TypeScript handles Buffer typings, the common pitfalls of mixing Node and browser runtimes, and the best practices for writing cross-platform, type-safe binary code using universal primitives, targeted configurations, and polyfills.

The Underlying Mismatch

In Node.js, Buffer is built into the runtime to handle raw binary data and inherits directly from the ECMAScript Uint8Array specification. Modern browsers implement standard typed arrays—such as ArrayBuffer, Uint8Array, and DataView—but do not include a native global Buffer object.

Because Buffer extends Uint8Array, any code expecting a Uint8Array can safely receive a Buffer instance. However, the reverse is not true. If code relies on Node-specific Buffer methods (like .toString('hex') or Buffer.from()), running that same code in a browser without an abstraction layer results in a runtime ReferenceError: Buffer is not defined.

How TypeScript Compiles Buffer Types

TypeScript relies on ambient declaration files (.d.ts) to understand the types available in an environment. When a project includes @types/node in its package.json, TypeScript automatically includes these declarations globally unless configured otherwise.

This creates a common false sense of security:

  1. False Positives in Browser Code: If @types/node is present, TypeScript allows the use of Buffer across all files, even those targeting the client. The code compiles without errors, but fails in the browser at runtime.
  2. Type Incompatibilities: While Buffer extends Uint8Array, certain type signatures between different versions of @types/node and standard lib.dom.d.ts / lib.es2015.iterable.d.ts can produce subtle type discrepancies during compilation, especially when dealing with iterators or shared buffers.

Strategies for Isomorphic TypeScript

To safely write binary handling logic that works in both Node.js and browser environments, use one of the following approaches:

1. Standardize on Uint8Array

The most robust, modern approach is to design all cross-platform interfaces to accept and return standard Uint8Array types instead of Buffer.

function processData(data: Uint8Array): Uint8Array {
  // Use standard TypedArray methods supported in all modern environments
  const copy = new Uint8Array(data.length);
  copy.set(data);
  return copy;
}

Since Buffer extends Uint8Array, Node-specific callers can pass a Buffer without casting, and browser callers can pass a native Uint8Array.

2. Segregate Environments with tsconfig.json

To prevent TypeScript from allowing Node globals in browser code, explicitly define the types array in your tsconfig.json files and separate targets using TypeScript Project References.

For browser code (tsconfig.browser.json):

{
  "compilerOptions": {
    "lib": ["DOM", "ES2022"],
    "types": [] 
  }
}

Setting "types": [] prevents TypeScript from automatically loading all @types/* packages from node_modules, ensuring that references to Buffer produce a compile-time error.

For Node.js code (tsconfig.node.json):

{
  "compilerOptions": {
    "types": ["node"]
  }
}

3. Explicit Imports and Polyfills

If your application requires the complete Buffer API in the browser, you must use a polyfill such as the buffer package from npm. Avoid relying on global variables; import the type and implementation explicitly:

import { Buffer } from "buffer";

export function encodeStringToHex(input: string): string {
  return Buffer.from(input).toString("hex");
}

Modern module bundlers like Vite and Webpack 5 do not automatically inject Node.js polyfills. When using explicit imports, configure your bundler to alias buffer to the polyfill package to ensure runtime compatibility across browsers.
