How TypeScript Merges Namespaces and Classes

Declaration merging in TypeScript allows developers to combine multiple declarations sharing the same identifier into a single definition. When merging namespaces and classes, TypeScript avoids naming collisions by categorizing identifiers into separate declaration spaces—Types, Values, and Namespaces—and systematically mapping exported namespace members onto the class constructor object as static properties. This article explains the internal mechanics TypeScript uses to handle these merges cleanly and how the compiler prevents identifier conflicts.

The Three Declaration Spaces

To prevent conflicts, TypeScript maintains three distinct internal entity groups:

  1. Namespace Space: Contains names resolved using dotted notation (e.g., A.B).
  2. Type Space: Contains compile-time types used for annotations, interfaces, and type aliases.
  3. Value Space: Contains JavaScript runtime values such as variables, functions, and objects.

A class declaration introduces two entities: a Type representing the instance of the class, and a Value representing the constructor function.

A namespace declaration introduces a Namespace and a Value representing an object holding exported members.

Because the class and the namespace contribute different parts to the symbol table, their core identities do not collide. Instead, TypeScript executes a value-to-value merge.

Mapping Namespace Members to Static Properties

When a namespace merges with a class of the exact same name, TypeScript attaches the namespace's exported members directly to the class constructor function. This effectively makes the namespace exports act as static members of the class.

class Album {
  label: string;

  constructor(label: string) {
    this.label = label;
  }
}

namespace Album {
  export class AlbumLabel {
    format: string = "Vinyl";
  }

  export function createAlbum(label: string): Album {
    return new Album(label);
  }
}

In the compiled JavaScript, the Album namespace executes after the Album class constructor is defined, attaching AlbumLabel and createAlbum to the Album object:

Album.AlbumLabel = ...;
Album.createAlbum = ...;

This structural separation ensures that instance properties (which live on Album.prototype or instance instances) never collide with exported namespace members, which reside strictly on the constructor function object.

Compile-Time Collision Checks

TypeScript prevents runtime overwrite issues by enforcing strict validation rules during compilation:

1. Duplicate Static Identifier Detection

If a class already defines a static property or method, a merged namespace cannot export a member with the same name. Attempting to do so triggers a compile-time error:

class Widget {
  static version = 1.0;
}

namespace Widget {
  // Error: Duplicate identifier 'version'.
  export const version = 2.0; 
}

2. Declaration Order Constraints

The class declaration must appear before the namespace declaration in the source code. This requirement ensures that the constructor function is instantiated before the namespace code attempts to assign properties to it, preventing the namespace from accidentally wiping out or shadowing the constructor.

3. Non-Exported Privacy Isolation

Any variable, function, or type inside the namespace that is not explicitly marked with the export keyword remains private to the namespace scope. Unexported members are encapsulated within a closure and cannot collide with the class or other declarations outside that closure.
