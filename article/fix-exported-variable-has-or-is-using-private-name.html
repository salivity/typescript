Fix: Exported Variable Has or Is Using Private Name

The TypeScript error "Exported variable has or is using private name" occurs when an exported variable, function, or class exposes a type that is not exported from the same module. This article explains why the TypeScript compiler flags this issue during declaration file generation and provides direct, actionable solutions to fix it in your codebase.

What Causes the Error?

The primary cause of this error is TypeScript's requirement to generate declaration files (.d.ts) when the declaration compiler option is set to true in tsconfig.json.

When you export a variable, TypeScript needs to define that variable's type signature in the generated .d.ts file so external consumers know how to interact with it. If the variable's type is inferred from or explicitly references a local type, interface, or class that lacks an export modifier, the compiler cannot generate a valid public declaration. Because the referenced type is "private" (local to that file), TypeScript throws the error to prevent emitting broken type declarations.

Example of the Error

Consider the following scenario:

// Not exported (private to this module)
interface DatabaseConfig {
  host: string;
  port: number;
}

const defaultConfig: DatabaseConfig = {
  host: "localhost",
  port: 5432,
};

// Error: Exported variable 'config' has or is using private name 'DatabaseConfig'.
export const config = defaultConfig;

In this case, config is inferred to have the type DatabaseConfig. Because DatabaseConfig is not exported, TypeScript cannot write the type definition for config into the .d.ts file.

How to Fix the Error

There are two primary methods to resolve this issue depending on whether the underlying type should be part of your public API.

Solution 1: Export the Underlying Type (Recommended)

The most common and robust solution is to add the export keyword to the interface, type alias, or class that the exported variable depends on.

// Add 'export' here
export interface DatabaseConfig {
  host: string;
  port: number;
}

const defaultConfig: DatabaseConfig = {
  host: "localhost",
  port: 5432,
};

export const config = defaultConfig; // No error

Exporting the type allows TypeScript to reference it cleanly in generated .d.ts files and lets consumers of your code use the type definitions safely.

Solution 2: Explicitly Type the Variable with an Exported or Inline Type

If you do not want to expose the internal type by name, you can explicitly type the exported variable using a generic type, an existing public interface, or an inline type literal:

interface DatabaseConfig {
  host: string;
  port: number;
}

const defaultConfig: DatabaseConfig = {
  host: "localhost",
  port: 5432,
};

// Explicit inline typing eliminates the reference to 'DatabaseConfig'
export const config: { host: string; port: number } = defaultConfig;

This prevents TypeScript from having to look up and reference the unexported DatabaseConfig identifier during declaration emission.

Solution 3: Disable Declaration File Generation

If your project is a standalone application (such as a backend service or bundled frontend app) rather than a distributed library, you likely do not need .d.ts files. You can disable declaration generation in your tsconfig.json:

{
  "compilerOptions": {
    "declaration": false
  }
}

Disabling this setting stops TypeScript from creating .d.ts files, which suppresses the error entirely. However, if you are building an npm package or shared library, you should keep declaration: true and use Solution 1.
