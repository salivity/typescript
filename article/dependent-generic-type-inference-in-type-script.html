Dependent Generic Type Inference in TypeScript

This article explores how the TypeScript compiler resolves generic function calls when multiple type parameters depend on one another. It covers the compiler's dependency graph construction, topological resolution of generic parameters, inference priority mechanisms, the handling of circular constraints, and techniques like NoInfer to prevent unwanted inference cascades.

Dependency Graph and Topological Ordering

When a generic function declares multiple type parameters where one parameter references another (for example, <T, K extends keyof T>), the TypeScript compiler does not infer all type variables simultaneously in isolation. Instead, it constructs a dependency graph of type parameters based on their constraints:

function getProperty<T, K extends keyof T>(obj: T, key: K): T[K] {
    return obj[key];
}

In this signature, K explicitly depends on T. The compiler topologically sorts the generic parameters according to this dependency graph:

  1. Root Parameters First: Type parameters that do not depend on other unresolved parameters (like T) are scheduled for initial inference.
  2. Dependent Parameters Second: Parameters whose constraints depend on upstream variables (like K) have their inference deferred until their prerequisite types are determined or have candidates collected.

Candidate Collection and Candidate Merging

During call site evaluation, TypeScript checks each runtime argument against its corresponding parameter type to collect "inference candidates" for each generic variable:

  1. Independent Collection: For an invocation like getProperty({ id: 1, name: "Alice" }, "name"), TypeScript collects candidates for T from the first argument ({ id: number, name: string }).
  2. Constraint Substitution: Once candidate types for T are found, TypeScript merges them to form a preliminary type for T. It then substitutes this resolved T into K's constraint, transforming K extends keyof T into K extends "id" | "name".
  3. Validation and Refinement: TypeScript inspects the second argument ("name") to collect candidates for K, verifying that "name" satisfies the substituted constraint "id" | "name".

If an argument provides candidates for multiple dependent parameters simultaneously, the compiler gathers candidates in parallel but resolves them in dependency order.

Inference Priority and Contextual Typing

Inference dependencies are also shaped by the source of the type information. TypeScript assigns different priorities to inference sites:

  • Argument Types (High Priority): Directly passed values provide primary inference candidates.
  • Contextual Types (Deferred Priority): If an argument is a function expression or callback whose parameter types depend on a generic argument (e.g., (item: T) => U), TypeScript defers the contextual typing of that callback until T is fixed by other arguments.
  • Return Type Targets (Lowest Priority): When a generic type only appears in the return type, it is inferred from the calling context (the variable receiving the result).

When dependencies conflict—for example, if argument 1 suggests T is string and argument 2 suggests T is number via a dependent type—TypeScript attempts to find a common supertype (union or subtype reduction). If no compatible type exists, it issues a type mismatch error.

Mutual and Circular Dependencies

When generic parameters reference each other cyclically (e.g., <T extends U, U extends T>), a strict topological ordering is impossible. TypeScript handles these scenarios through constraint baselines and widening:

  • The compiler identifies the cycle and breaks the evaluation loop by substituting the declared upper bounds (the base constraints).
  • If a parameter lacks an explicit constraint, it falls back to unknown.
  • Inference fails or defaults to the widest valid constraint if concrete candidates from arguments cannot break the mutual cycle.

Guiding Inference with NoInfer

Because dependent generics can cause TypeScript to infer candidates from arguments where inference is unintended, TypeScript 5.4 introduced the NoInfer<T> intrinsic utility type.

By wrapping a dependent generic in NoInfer<T>, you instruct the compiler to satisfy the parameter using already-inferred candidates rather than allowing that specific position to contribute new candidates:

function configure<T, K extends keyof T>(
    target: T,
    defaultKey: NoInfer<K>
): void {
    // ...
}

In this pattern, K must be derived strictly from target or explicit type specification, preventing the defaultKey argument from widening K outside the bounds of T.
