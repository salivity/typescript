ts-ignore vs ts-expect-error in TypeScript

TypeScript provides two primary directives to silence compiler diagnostics: // @ts-ignore and // @ts-expect-error. While both comments suppress compilation errors on the immediate following line, they handle error absence differently. The @ts-ignore directive silences errors unconditionally, whereas @ts-expect-error demands that a type error actually exists; if the line has no error, the compiler throws an unused directive error. This distinction makes @ts-expect-error a strictly safer mechanism for long-term codebase maintenance.

Understanding @ts-ignore

The // @ts-ignore comment was introduced early in TypeScript's lifecycle. Placing it before a line of code instructs the compiler to ignore any type-checking errors that occur on that specific line.

// @ts-ignore
const result: number = "This is a string";

The primary flaw of @ts-ignore is its silence when code changes. If a developer later refactors the variable to accept a string, or if an upstream library updates its types to match the usage, @ts-ignore remains dormant in the codebase. It does not alert developers that the comment is no longer necessary, often leading to stale, dead suppressions cluttering the source code.

Understanding @ts-expect-error

Introduced in TypeScript 3.9, // @ts-expect-error acts as an assertion that the following line contains a genuine compilation error.

// @ts-expect-error
const result: number = "This is a string";

If the subsequent line produces a type error, the compiler suppresses it and builds successfully. However, if the line contains valid TypeScript code that produces no error, the compiler raises an error:

error TS2578: Unused '@ts-expect-error' directive.

This self-checking behavior prevents suppressions from outliving their necessity. When a refactor or dependency update resolves the underlying issue, the compiler immediately notifies you to remove the directive.

Key Differences

Feature // @ts-ignore // @ts-expect-error
Error Suppression Suppresses the next line's error Suppresses the next line's error
Behavior When No Error Exists Silent (does nothing) Throws compiler error TS2578
Refactoring Safety Low (can mask valid code or stale comments) High (alerts when the suppression is obsolete)
Primary Use Case Legacy migrations across TS versions Intentional temporary fixes, type testing

When to Use Each Directive

Use @ts-expect-error by Default

In modern TypeScript codebases, @ts-expect-error is the recommended choice whenever an intentional error suppression is needed. It is particularly useful for:

  • Testing Types: Verifying that a function rejects invalid inputs during unit tests.
  • Temporary Workarounds: Silencing incomplete external type definitions while ensuring you are notified once the definitions are fixed.
  • Refactoring Safeguards: Ensuring that temporary suppressions do not become permanent blind spots in the build pipeline.

When @ts-ignore is Still Relevant

The use of @ts-ignore is generally discouraged, but it remains useful in specific edge cases:

  • Multi-Version TypeScript Support: When maintaining a library that must build across different TypeScript versions where a line produces an error in version 4.x but not in 5.x. An @ts-expect-error directive would fail the build on the newer version, whereas @ts-ignore will pass on both.
  • Rapid Prototyping: Scaffolding large sections of incomplete code where strict compiler feedback is temporarily unwanted.
