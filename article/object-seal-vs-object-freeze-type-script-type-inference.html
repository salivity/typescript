Object.seal vs Object.freeze TypeScript Type Inference

In JavaScript, Object.seal() and Object.freeze() provide runtime immutability safeguards, but TypeScript treats them fundamentally differently during static type inference. While Object.freeze() transforms an object type into an immutable representation by applying the Readonly<T> utility type to top-level properties, Object.seal() returns the object's original type T unchanged. Understanding this distinction is essential for writing accurate, type-safe TypeScript applications when controlling object mutability.

Type Signature of Object.seal()

In TypeScript’s standard library definitions (lib.es5.d.ts), Object.seal() is declared as follows:

seal<T>(o: T): T;

Because Object.seal() prevents properties from being added or deleted at runtime but still permits the modification of existing writable properties, TypeScript does not modify the structure or modifiers of the incoming type T.

If you pass an object with mutable properties into Object.seal(), TypeScript still infers those properties as mutable:

const user = Object.seal({ name: "Alice", age: 30 });
// Inferred Type: { name: string; age: number; }

user.age = 31; // Allowed by TypeScript and permitted at runtime

TypeScript cannot statically enforce the prevention of property additions or deletions on generic object shapes, so the returned type remains identical to the input type.

Type Signature of Object.freeze()

In contrast, Object.freeze() marks existing properties as non-writable at runtime in addition to preventing property addition and removal. TypeScript reflects this change in its type system using the Readonly<T> mapped type:

freeze<T>(f: T): Readonly<T>;

When an object is passed to Object.freeze(), TypeScript appends the readonly modifier to all top-level properties:

const user = Object.freeze({ name: "Alice", age: 30 });
// Inferred Type: { readonly name: string; readonly age: number; }

user.age = 31; 
// Compile error: Cannot assign to 'age' because it is a read-only property.

By inferring Readonly<T>, the TypeScript compiler catches unauthorized mutations during development, matching the runtime constraint imposed by the JavaScript engine.

Key Differences in Type Checking

Feature Object.seal() Inference Object.freeze() Inference
Return Type T Readonly<T>
Property Reassignment Allowed by compiler Blocked by compiler (readonly)
Object Extension Runtime error only Blocked by compiler and runtime
Type Mutation Preserves existing modifiers Adds readonly modifier

Shallow Inference Behavior

Neither method performs deep inference by default. Both Object.seal() and Object.freeze() act shallowly at runtime, and TypeScript's standard library mirrors this behavior.

Nested objects passed through Object.freeze() will have their top-level keys marked as readonly, but nested child objects will retain their original mutable types unless they are individually frozen or cast using a const assertion (as const).
