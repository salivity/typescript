TypeScript allowArbitraryExtensions in Bundling Pipelines

The allowArbitraryExtensions compiler option, introduced in TypeScript 5.0, enables TypeScript to type-check imports of non-JavaScript and non-TypeScript assets—such as CSS, SVG, WebAssembly, and HTML files—without sacrificing strict per-file type safety. When modern bundling pipelines like Vite, Webpack, or esbuild handle these assets at build time, allowArbitraryExtensions allows developers to provide dedicated, file-specific declaration files for every imported asset instead of relying on generic ambient definitions.

The Bundler Asset Import Problem

Modern bundlers allow JavaScript and TypeScript files to import non-script assets directly:

import styles from "./Button.module.css";
import icon from "./logo.svg";

Historically, TypeScript did not recognize arbitrary file extensions as import specifiers. To silence compiler errors, developers typically defined global wildcard declarations:

declare module "*.module.css" {
  const classes: { [key: string]: string };
  export default classes;
}

While this prevents compiler errors, it introduces significant drawbacks. Wildcard ambient declarations cannot provide specific typings for individual files. A typo in a CSS class name like styles.btnPrmary passes compilation, even if Button.module.css does not contain that class.

How allowArbitraryExtensions Solves the Problem

When "allowArbitraryExtensions": true is enabled in tsconfig.json, TypeScript changes how it resolves imports containing non-standard file extensions.

Instead of rejecting the file extension or matching it exclusively against a generic wildcard declaration, the compiler looks for a declaration file that appends .d.<extension>.ts to the base filename.

For example, when resolving:

import styles from "./Button.module.css";

TypeScript searches for a corresponding declaration file located at:

./Button.module.d.css.ts

Inside Button.module.d.css.ts, you can provide exact typings for that specific file:

declare const styles: {
  btnPrimary: string;
  btnSecondary: string;
};
export default styles;

If you attempt to access an undefined class name, TypeScript flags it as a compile-time error.

Integration with Build and Bundling Tools

The allowArbitraryExtensions flag directly complements the automated generation tools often embedded in bundler pipelines.

  1. Automated Typings for Assets: Tools like typed-css-modules or custom build plugins can watch asset files (like CSS Modules, GraphQL queries, or translation JSON) and automatically generate their corresponding .d.<ext>.ts declaration files next to them.
  2. Bundler Resolution Compatibility: This option is typically paired with "moduleResolution": "bundler" (or "node16"/"nodenext"). It informs TypeScript that an external tool will handle the final bundling and module execution, while TypeScript's sole responsibility is checking the types.
  3. No Emit Obligation: TypeScript does not attempt to compile or emit code for files with arbitrary extensions. It only checks the usage against the .d.<ext>.ts definition, delegating asset transformation and bundling entirely to the bundler.

Configuration Requirements

To use arbitrary extensions in a project, update the tsconfig.json compiler options:

{
  "compilerOptions": {
    "moduleResolution": "bundler",
    "allowArbitraryExtensions": true,
    "noEmit": true
  }
}

By bridging the gap between bundler-specific import syntax and strict static analysis, allowArbitraryExtensions gives bundling pipelines full type safety across heterogeneous file types.
