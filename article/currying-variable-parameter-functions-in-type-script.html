Currying Variable Parameter Functions in TypeScript

This article explores how TypeScript's type system models curried functions with variable parameter lengths using recursive conditional types and variadic tuple types. By breaking down function argument lists into structured tuples, TypeScript can dynamically infer parameters, preserve strict type safety across partial applications, and continuously compute subsequent function signatures until all arguments are satisfied.

The Mechanics: Variadic Tuples and Recursive Types

Currying converts a function with multiple parameters into a sequence of functions, each taking a subset of those parameters. To model this generically in TypeScript for any function arity, the type system relies on two main features introduced in TypeScript 4.0 and 4.1:

  1. Variadic Tuple Types: Allows representing argument lists as tuple types that can be decomposed using rest elements (...infer Rest).
  2. Recursive Conditional Types: Enables type-level loops that peel off parameters one by one (or in chunks) until no parameters remain.

Defining a Strict Unary Curry

A strict curried function takes exactly one parameter at a time. The type definition extracts the first element of a parameter tuple, constructs a function signature accepting that parameter, and recursively calls itself with the remaining elements.

type Curry<TArgs extends any[], TReturn> = 
  TArgs extends [infer First, ...infer Rest]
    ? (arg: First) => Curry<Rest, TReturn>
    : TReturn;

// Helper to extract parameters and return types
type CurriedFunction<F> = 
  F extends (...args: infer P) => infer R 
    ? Curry<P, R> 
    : never;

When applied to a function like (a: string, b: number, c: boolean) => void, CurriedFunction recursively unfolds into:

(arg: string) => (arg: number) => (arg: boolean) => void

Supporting Variable Chunk Sizes (Partial Currying)

In real-world implementations like Lodash or Ramda, curried functions allow callers to provide multiple arguments at once. To model variable-length argument slices, TypeScript must determine whether the provided arguments fully satisfy or only partially satisfy the expected parameter tuple.

type VariadicCurry<TArgs extends any[], TReturn> = {
  <TProvided extends any[]>(
    ...args: TProvided
  ): TArgs extends [...TProvided, ...infer TRest]
    ? TRest extends []
      ? TReturn
      : VariadicCurry<TRest, TReturn>
    : never;
};

This type works by matching the tuple of provided arguments (TProvided) as a prefix of the target arguments (TArgs).

  • If TProvided consumes all of TArgs, TRest is empty ([]), and the evaluation resolves to TReturn.
  • If elements remain in TRest, the return value is another VariadicCurry function waiting for the remaining tuple.

Handling Arbitrary Subsets and Overloads

A more permissive and idiomatic approach generates the full set of valid call signatures for any combination of arguments. This can be achieved by using conditional types that accept any prefix of the argument tuple:

type CurryVariadic<Args extends any[], Return> = 
  Args extends []
    ? () => Return
    : <Provided extends any[]>(
        ...args: Provided
      ) => Args extends [...Provided, ...infer Rest]
        ? Rest extends []
          ? Return
          : CurryVariadic<Rest, Return>
        : Provided extends []
          ? CurryVariadic<Args, Return>
          : never;

Type System Constraints

While TypeScript cleanly handles finite, fixed-length parameter tuples, modeling currying introduces specific constraints:

  • Recursion Limits: TypeScript enforces a maximum recursion depth on conditional types (typically around 50 iterations), though standard function parameter counts rarely exceed this limit.
  • Rest Parameters: Functions that already contain trailing rest parameters (e.g., (...nums: number[]) => void) represent unbounded tuples. Peeling parameters off unbounded tuples requires custom handling, as TypeScript cannot determine when the tuple terminates.
  • Optional Arguments: Optional parameters (a?: number) resolve to union types (number | undefined), which can complicate prefix matching unless explicitly handled using tuple transformations that strip optionality.
