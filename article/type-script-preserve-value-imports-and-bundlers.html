TypeScript preserveValueImports and Bundlers

This article provides an overview of TypeScript's preserveValueImports compiler option, explaining its core functionality, the problem it solves regarding import elision, and how it directly interacts with modern bundlers and build tools. You will learn why TypeScript removes certain imports by default, how this option prevents unwanted side effects in module bundling, and how it has evolved with newer TypeScript configurations.

What Is preserveValueImports?

Introduced in TypeScript 4.5, preserveValueImports is a compiler flag designed to prevent the TypeScript compiler (tsc) from automatically stripping out imported values that appear to be used only as types.

By default, TypeScript performs a process called "type elision." If you import an identifier and only reference it in type positions—such as type annotations, interfaces, or generic parameters—TypeScript assumes the import is not needed at runtime and removes it from the emitted JavaScript.

However, in certain scenarios, an imported identifier might be required at runtime even if the TypeScript type checker does not detect its usage. When preserveValueImports is set to true, TypeScript guarantees that any import written using regular import syntax (import { X } from "module") will remain in the emitted output. The only imports that will be removed are those explicitly declared using the type modifier (e.g., import type { X } from "module").

The Problem with Default Import Elision

Consider the following example:

import { Component } from "./components";

function render(item: Component) {
    // Component is only used as a type annotation here
}

Under default settings, TypeScript eliminates import { Component } from "./components"; from the generated JavaScript because it sees no runtime evaluation of Component.

This elision behavior creates problems in multiple modern development workflows:

  1. Side-Effect Management: Some modules rely on the side effects triggered when imported. If TypeScript removes the import because it was only referenced as a type, those runtime side effects are lost.
  2. Custom Compilers and Macro Systems: Frameworks like Vue, Svelte, or Angular often transform templates separately from the TypeScript compiler. A component might be used in a template markup rather than the <script> block. If TypeScript strips the import first, the runtime or secondary compiler fails to locate the reference.

How preserveValueImports Interacts with Bundlers

Modern bundlers like Webpack, Vite, Rollup, and esbuild often rely on isolated compilation. When single-file transpilers (like Babel, SWC, or esbuild) compile a file, they do so without access to the broader type graph across the entire project.

1. Compatibility with isolatedModules

Single-file transpilers cannot always deduce whether an import is an interface, a type alias, or a class. When using preserveValueImports alongside isolatedModules, developers are forced to be explicit:

  • If you want an import preserved for the bundler to process, write a standard import:

    import { Action } from "./actions";

  • If an import is strictly a compile-time type, write an explicit type import:

    import type { Action } from "./actions";

This clear separation ensures that single-file bundler transpilers do not make incorrect assumptions, avoiding runtime errors such as ReferenceError: X is not defined.

2. Bundler Tree-Shaking and Dead Code Elimination

When preserveValueImports keeps value imports intact in the generated code, modern bundlers can handle tree-shaking accurately. Rather than relying on TypeScript's conservative guesses, the bundler inspects the entire dependency tree and evaluates whether the imported symbol is truly used, whether the imported module has side effects (via package.json's "sideEffects" property), and what can safely be dropped from the final bundle.

Evolution in Modern TypeScript: verbatimModuleSyntax

In TypeScript 5.0, preserveValueImports and its counterpart importsNotUsedAsValues were deprecated in favor of a unified option: verbatimModuleSyntax.

While preserveValueImports established the rule that regular imports should be kept, verbatimModuleSyntax simplifies and solidifies the contract: any import or export written without the type modifier remains completely untouched in the output, while anything marked with type is erased.

For legacy codebases or projects targeting TypeScript 4.5 through 4.9, preserveValueImports remains the key configuration for ensuring that TypeScript and bundlers interpret module bindings consistently.
