TypeScript Line Endings in Cross-Platform Teams

Managing line endings across cross-platform development teams can lead to dirty Git diffs, inconsistent build artifacts, and unexpected compiler output when engineers alternate between Windows (CRLF) and Unix-based environments like macOS and Linux (LF). TypeScript resolves these discrepancies by decoupling source code parsing from code generation through its built-in newLine compiler option, while relying on companion tooling like Git attributes and formatters to normalize the source files themselves. This guide explains the exact mechanisms TypeScript uses to manage line endings and the best practices required to ensure consistency across your team.

The Source Code Parsing Mechanism

The TypeScript compiler (tsc) handles differing line endings automatically during the lexical analysis and parsing phases. The internal scanner recognizes carriage return (\r), line feed (\n), and carriage return followed by line feed (\r\n) as identical line-break tokens.

Because the compiler normalizes these characters into standard tokens in the Abstract Syntax Tree (AST), code written with CRLF on a Windows machine will parse and type-check identically on a Linux Continuous Integration (CI) runner using LF. Differing line endings in raw TypeScript source files will not cause syntax errors or semantic type issues.

The newLine Compiler Option

While TypeScript parses any standard line break seamlessly, the emitted JavaScript, source maps, and declaration files (.d.ts) must pick a specific line-ending format. By default, tsc emits files using the operating system's native line ending: CRLF on Windows and LF on macOS and Linux. In a cross-platform team, this behavior creates uncommitted changes or divergent build artifacts simply because two developers compiled the same code on different machines.

To enforce deterministic output regardless of the host operating system, TypeScript provides the newLine configuration in tsconfig.json:

{
  "compilerOptions": {
    "newLine": "lf"
  }
}

The valid settings are:

  • "lf": Forces all generated files to end with line feeds (\n), matching Unix standards. This is the recommended setting for modern web development and CI/CD pipelines.
  • "crlf": Forces all generated files to use carriage return plus line feed (\r\n), matching legacy Windows standards.

Setting this explicitly ensures that builds generated locally on Windows match the outputs generated by Linux-based automated build environments bit-for-bit.

Integrating with Git via .gitattributes

The newLine option only controls the output of the compilation process; it does not alter the line endings of the source .ts files on disk. If a Windows developer checks in a file with CRLF, and a Mac developer checks in a change with LF, version control histories become polluted with entire-file diffs.

To prevent this, teams should configure a .gitattributes file in the repository root. This takes precedence over individual developer configurations like core.autocrlf:

* text=auto eol=lf
*.ts text eol=lf
*.tsx text eol=lf
*.json text eol=lf

This configuration forces Git to normalize all TypeScript files to LF upon commit and guarantees that checkouts onto any platform retain LF line endings.

Complementary Tooling: ESLint and Prettier

To catch line-ending discrepancies before compilation or commit:

  1. Prettier: Setting "endOfLine": "lf" in your .prettierrc ensures all developers format files using the same characters across IDEs.
  2. ESLint: The linebreak-style rule can be set to ["error", "unix"] to flag any accidental CRLF insertions directly in developer text editors.

By combining the TypeScript newLine compiler option with a strict .gitattributes policy and automated formatting, cross-platform teams eliminate line-ending conflicts across both source code and emitted build outputs.
