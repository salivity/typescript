Can a TypeScript Decorator Return a New Constructor?

Yes, a class decorator in TypeScript can return a new constructor function or class to replace the original target class. This article explores how class decorator replacement works, demonstrating implementations for both modern standard decorators (TypeScript 5.0+) and legacy experimental decorators, while addressing the type-checking implications of swapping constructors at runtime.

How Constructor Replacement Works

When a class decorator returns a new constructor function or a new class, TypeScript and JavaScript runtime engines replace the original constructor with the returned one. Any subsequent instantiation using the new keyword will execute the new constructor instead of the original one.

Typically, the replacement class extends the original target class to preserve existing prototype methods and properties while adding or overriding behavior.

Modern Stage 3 Decorators (TypeScript 5.0+)

Starting with TypeScript 5.0, decorators align with the official ECMAScript Stage 3 proposal. Under this standard, a class decorator receives the original class as its first parameter and a context object as its second parameter. If the decorator returns a new class or constructor, it substitutes the target class.

function LoggedClass<T extends new (...args: any[]) => any>(
  target: T,
  context: ClassDecoratorContext
) {
  return class extends target {
    constructor(...args: any[]) {
      console.log(`Creating an instance of ${context.name || "AnonymousClass"}`);
      super(...args);
    }
  };
}

@LoggedClass
class User {
  constructor(public name: string) {}
}

const user = new User("Alice"); 
// Console output: "Creating an instance of User"

In modern decorators, the returned constructor can modify instantiation behavior, inspect or log constructor parameters, or inject additional runtime properties.

Legacy Experimental Decorators

In earlier TypeScript implementations using the "experimentalDecorators": true flag in tsconfig.json, constructor replacement works similarly by returning a subclass constructor:

function Timestamped<T extends { new (...args: any[]): {} }>(constructor: T) {
  return class extends constructor {
    createdAt = new Date();
  };
}

@Timestamped
class Document {
  constructor(public title: string) {}
}

const doc = new Document("Invoice");
console.log((doc as any).createdAt); // Outputs current Date

TypeScript Type-Checking Limitations

While runtime replacement works seamlessly in both modern and experimental decorator specifications, TypeScript's static type checker has an important limitation:

  1. Static Shape Invariance: Decorators cannot change the static compile-time type signature of a class. If the new constructor adds new properties or methods (like createdAt in the example above), TypeScript will not recognize these new members on instances unless you explicitly cast the instance or apply a class wrapper function instead of a decorator.
  2. Signature Compatibility: The returned constructor must be construct-compatible with the original class. It must accept constructor arguments compatible with the decorated class's constructor arguments.

A TypeScript class decorator can fully replace the target class constructor at runtime, which is an effective pattern for cross-cutting concerns like logging, dependency injection, and instance virtualization.
