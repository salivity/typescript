How tRPC Infers Types Without Code Generation

tRPC provides end-to-end type safety between the server and the client without requiring a code generation build step like GraphQL or OpenAPI. It accomplishes this feat entirely through TypeScript's native type system by combining type-only imports, automatic type inference via typeof, and runtime JavaScript Proxies. This architecture allows developers to define API procedures on the backend and have their input and output types immediately reflect on the frontend during compilation, all without leaking sensitive server implementation logic into the client bundle.

1. Type-Only Imports and Zero Runtime Leakage

The foundation of tRPC's design is TypeScript's type-only import syntax (import type). In a standard tRPC setup, the backend defines an appRouter containing all procedures and queries. The server then exports only the type definition of that router:

export type AppRouter = typeof appRouter;

On the frontend, the client imports this type:

import type { AppRouter } from '../server/router';

Because TypeScript erases all type declarations during compilation, the client bundle contains zero bytes of backend code, database drivers, or server-side secrets. The client only consumes the metadata of the router's interface.

2. Inferring Procedures via the typeof Operator

Instead of requiring developers to manually write TypeScript interfaces for every request and response, tRPC infers them automatically.

When you define a procedure using an input validator (such as Zod, Yup, or Valibot):

t.procedure
  .input(z.object({ id: z.string() }))
  .query(async ({ input }) => {
    return { id: input.id, name: 'Alice' };
  });

TypeScript evaluates the input schema and the return value of the query function. The resulting typeof appRouter contains a complex nested object type representing every route, its required input shape, and its inferred return type.

3. Deep Type Transformation with Mapped Types

Once the client receives the AppRouter type, the tRPC client library utilizes TypeScript's advanced type features—including mapped types, conditional types, and recursive utility types—to transform the server definition into a typed client interface.

Internally, tRPC maps over the AppRouter structure:

  • It inspects whether a procedure is a query, mutation, or subscription.
  • It extracts the input and output types associated with each procedure using the infer keyword in conditional types.
  • It translates these definitions into client-side methods (e.g., .useQuery(), .query(), .mutateAsync()) where the arguments match the backend's validation schema and the resolved promise matches the backend's return type.

If the backend changes a returned database column or alters a validation rule, the inferred type changes instantly in the TypeScript language server without needing to trigger a separate compilation or watcher process.

4. Dynamic Runtime Resolution via ES6 Proxies

Because no actual JavaScript code is generated to match the router structure, the client needs a way to call arbitrary procedure paths dynamically at runtime. tRPC achieves this using ES6 Proxy objects.

When you invoke a procedure such as:

trpc.user.getById.useQuery({ id: '123' });

No concrete user or getById functions exist in the client JavaScript bundle. Instead, a dynamic Proxy intercepts each property access, accumulating the path segments (['user', 'getById']). When a method call is finally executed, the proxy translates the path and parameters into a standard HTTP request to the corresponding server endpoint.

By decoupling runtime routing using Proxies and mapping server routes through TypeScript's native type inference, tRPC delivers full-stack type safety with zero code generation overhead.
