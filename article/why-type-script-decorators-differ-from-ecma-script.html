Why TypeScript Decorators Differ from ECMAScript

Early TypeScript decorators differ from standard ECMAScript decorators primarily because TypeScript implemented an experimental version based on an early 2015 TC39 proposal to meet urgent framework demands, whereas the official standard underwent nearly a decade of redesign. The divergence centers around differing API signatures, object mutation models, parameter decoration capabilities, and metadata reflection mechanisms.

The Historical Divergence

In 2014, the Angular team was building Angular 2 and initially planned to create a custom language called AtScript to support annotations. To avoid language fragmentation, the TypeScript team collaborated with Angular to implement decorators natively into TypeScript 1.5 in 2015.

At the time, decorators were only a Stage 1 proposal in TC39 (the ECMAScript standards committee), authored by Yehuda Katz. Because TypeScript needed the feature immediately, it implemented this early draft behind the --experimentalDecorators flag.

Over the subsequent years, the TC39 committee substantially overhauled the specification. Concerns regarding performance, interaction with class fields, prototype mutation, and security caused the proposal to be rewritten multiple times before finally reaching Stage 3 in 2022. By the time TC39 standardized decorators (which TypeScript formally adopted in version 5.0), the design had moved in an entirely different direction.

Mutation vs. Replacement

The original experimental TypeScript implementation relies on in-place mutation. Method and property decorators directly modify the underlying JavaScript property descriptors or class prototypes:

  • Experimental TypeScript: Receives the class prototype (or constructor for static members), the property key, and the property descriptor (target, propertyKey, descriptor). Developers alter properties by directly modifying this descriptor.
  • Standard ECMAScript: Employs a pure, functional replacement model. Decorators receive the target element's value and a context object (value, context). Rather than mutating objects in place, the decorator optionally returns a new function or value that replaces the original target.

The Context Object

Standard ECMAScript introduced a unified second argument: the decorator context object. In experimental TypeScript, decorators had to determine context based on the number and type of arguments passed to them, which varied widely between classes, methods, accessors, and properties.

The ECMAScript standard standardizes this via context, which provides:

  • kind: Identifies the decorated element ("class", "method", "getter", "setter", "field", or "accessor").
  • name: The name of the decorated element.
  • static: A boolean indicating if the member is static.
  • private: A boolean indicating if the member is a private field or method (#field).
  • access: Methods (get, set) to read and write the member.
  • addInitializer: A hook allowing decorators to run initialization code during instance construction.

Parameter Decorators

A major functional difference is the presence of parameter decorators.

Early TypeScript added support for decorating function and method parameters, an essential feature for dependency injection engines used in Angular and NestJS.

The Stage 3 ECMAScript decorator standard explicitly excluded parameter decorators to keep the initial specification focused and manageable. As a result, standard ECMAScript decorators cannot be applied to function or method arguments without relying on future, separate TC39 proposals.

Metadata Reflection

Early TypeScript decorators were tightly coupled with the reflect-metadata library and the compiler flag --emitDecoratorMetadata. This system automatically serialized TypeScript compile-time types (such as parameter types and return types) into runtime metadata.

Standard ECMAScript decorators decouple metadata from runtime type reflection. Instead of relying on a global Reflect polyfill and compile-time type emission, ECMAScript introduced a dedicated Symbol.metadata proposal. This provides a standard storage mechanism on the class constructor for metadata, but it does not automatically serialize static TypeScript types into the runtime environment.
