How TypeScript Types Reflect.get and Reflect.set

This article explores how TypeScript types the built-in ECMAScript Reflect.get and Reflect.set methods in its standard library declarations. It examines the actual TypeScript signatures for both functions, explains why the compiler opts for loose any types rather than strict generic mappings by default, and demonstrates how to implement strictly typed wrappers when compiler safety is required.

Standard Library Type Definitions

In TypeScript's standard library (lib.es2015.reflect.d.ts), Reflect.get and Reflect.set are intentionally typed with flexible, non-generic signatures.

The official definition for Reflect.get is:

function get(target: object, propertyKey: PropertyKey, receiver?: any): any;

The official definition for Reflect.set is:

function set(target: object, propertyKey: PropertyKey, value: any, receiver?: any): boolean;

In these signatures:

  • target is constrained simply to object.
  • propertyKey accepts PropertyKey, which is a global type alias for string | number | symbol.
  • For Reflect.get, the return type is any.
  • For Reflect.set, the value argument is typed as any, and the method returns a boolean indicating whether property assignment succeeded.

Why TypeScript Uses any Instead of Generics

TypeScript's standard object property access (target[key]) uses generic lookup types (T[K]) to enforce that the key exists on the object and that the returned value matches the property's type. However, the design team intentionally chose not to make Reflect.get and Reflect.set generic for several structural reasons:

1. Dynamic Metaprogramming and Proxies

The Reflect API is primarily intended for metaprogramming, runtime reflection, and forwarding operations inside Proxy traps. Inside a Proxy handler, properties may be virtual or generated dynamically at runtime without existing on the underlying target interface. Stricter types would cause false-positive type errors in these dynamic contexts.

2. Receiver Polymorphism

Both Reflect.get and Reflect.set accept an optional receiver argument. When accessing a property backed by a getter or setter, the receiver replaces the this context for that getter/setter execution. This means the returned value or expected input value might depend entirely on the receiver's type rather than the target's declared type, making precise static typing impossible at compile time.

3. Non-Existent Keys

In vanilla JavaScript, calling Reflect.get(target, "missingKey") does not throw a runtime error; it returns undefined. If TypeScript typed the return value strictly as T[K], it would prevent checking for properties that might not exist on the type definition.

Enforcing Strict Types

When you need type safety for reflection methods outside of Proxy handlers, you can create strongly typed generic helper wrappers or use TypeScript module augmentation.

A type-safe wrapper for Reflect.get:

function strictGet<T extends object, K extends keyof T>(
  target: T,
  propertyKey: K,
  receiver?: unknown
): T[K] {
  return Reflect.get(target, propertyKey, receiver);
}

const user = { id: 1, name: "Alice" };

const id = strictGet(user, "id"); // Typed as number
// strictGet(user, "email"); // Compiler Error: Argument of type '"email"' is not assignable to parameter of type '"id" | "name"'.

A type-safe wrapper for Reflect.set:

function strictSet<T extends object, K extends keyof T>(
  target: T,
  propertyKey: K,
  value: T[K],
  receiver?: unknown
): boolean {
  return Reflect.set(target, propertyKey, value, receiver);
}

const settings = { theme: "dark", notifications: true };

strictSet(settings, "theme", "light"); // Valid
// strictSet(settings, "theme", 123); // Compiler Error: Type 'number' is not assignable to type 'string'.

By default, TypeScript sacrifices type safety in Reflect.get and Reflect.set to preserve runtime flexibility for JavaScript metaprogramming patterns, requiring developers to provide explicit types or custom generic abstractions when stronger guarantees are needed.
