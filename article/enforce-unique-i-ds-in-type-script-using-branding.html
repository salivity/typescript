Enforce Unique IDs in TypeScript Using Branding

This article demonstrates how to use branded types in TypeScript to enforce compile-time safety for unique identifiers. By implementing a lightweight nominal typing pattern, developers can prevent common bugs where structurally identical primitives, such as strings or numbers representing different entity IDs, are accidentally interchanged throughout an application codebase.

The Problem with Primitive IDs

TypeScript uses a structural type system. If two types share the same shape, TypeScript treats them as mutually assignable. When entities rely on plain primitives (like string or number) for their IDs, the compiler cannot distinguish between them:

type UserId = string;
type OrderId = string;

function cancelOrder(userId: UserId, orderId: OrderId) {
  // ...
}

const userId: UserId = "usr_123";
const orderId: OrderId = "ord_456";

// Accidentally swapping arguments causes no compile-time error
cancelOrder(orderId, userId);

Implementing Branded Types

To force TypeScript to treat identical primitive structures as distinct types, you can append a unique "brand" to the type. This is typically done using an intersection with an object containing a unique symbol or tag property that does not exist at runtime.

Here is a generic helper for creating branded types:

declare const brand: unique symbol;

export type Brand<T, TBrand extends string> = T & {
  readonly [brand]: TBrand;
};

Using this utility, declare distinct ID types:

export type UserId = Brand<string, "UserId">;
export type OrderId = Brand<string, "OrderId">;
export type ProductId = Brand<string, "ProductId">;

Because the [brand] symbol is unique to the branded definition, neither raw strings nor IDs with different brand tags can satisfy the type without explicit assignment.

Constructing and Casting Branded IDs

Because branded types are a compile-time construct, runtime values must be cast using constructor functions or type assertion guards.

export function createUserId(id: string): UserId {
  // Optional: Add runtime validation (e.g., regex, UUID checks)
  return id as UserId;
}

export function createOrderId(id: string): OrderId {
  return id as OrderId;
}

Compile-Time Enforcement in Practice

Once IDs are branded, TypeScript rejects mixed arguments and invalid assignments:

function cancelOrder(userId: UserId, orderId: OrderId) {
  // Logic here
}

const user = createUserId("usr_123");
const order = createOrderId("ord_456");

// Correct usage
cancelOrder(user, order);

// Compile-time error:
// Argument of type 'UserId' is not assignable to parameter of type 'OrderId'.
cancelOrder(order, user);

// Compile-time error:
// Argument of type 'string' is not assignable to parameter of type 'UserId'.
cancelOrder("usr_123", order);

Key Benefits

  1. Zero Runtime Overhead: Branding is entirely erased during compilation; it leaves no runtime footprint or performance penalty.
  2. Refactoring Safety: Renaming or rearranging function parameters immediately surfaces all mismatched arguments across the project.
  3. Domain Clarity: Function signatures become self-documenting by requiring explicit ID types instead of generic primitives.
