TypeScript ESM Module Resolution with .js Extensions

In TypeScript projects targeting ECMAScript Modules (ESM), writing imports with explicit .js extensions is a standard requirement that often confuses developers working in .ts files. This article explains why TypeScript mandates the .js extension in import specifiers, how the compiler maps these paths back to your TypeScript source files during type checking, and how the output is resolved at runtime.

Why ESM Requires Explicit Extensions

Native ECMAScript Modules in Node.js do not perform automatic file extension resolution or directory index searching by default. To load a local module natively, Node.js requires a complete relative URL or path, which includes the file extension (for example, ./utils.js).

A core TypeScript design principle is that the compiler does not rewrite module specifiers during the build process. If you write an import targeting ./utils, TypeScript will not rewrite it to ./utils.js upon emit. Consequently, to produce valid runtime JavaScript that modern Node.js ESM can execute, the original source code in your .ts files must explicitly import ./utils.js.

How TypeScript Resolves .js to .ts

When configuring TypeScript with modern module settings—specifically setting "moduleResolution": "Node16" or "NodeNext" in tsconfig.json—the TypeScript compiler employs an extension substitution algorithm.

When the compiler encounters an import specifier such as:

import { helper } from "./utils.js";

TypeScript executes the following lookup process:

  1. Extension Substitution: TypeScript inspects the path and notes the .js extension. It does not look strictly for a physical utils.js file in the source directory. Instead, it substitutes the .js extension with relevant TypeScript extensions.
  2. Source Candidate Lookup: The compiler checks the file system for source files in the same location in the following priority order:
    • ./utils.ts
    • ./utils.tsx
    • ./utils.d.ts
  3. Type Checking: If a matching TypeScript source file (such as ./utils.ts) is located, TypeScript uses it for type definitions, module interface validation, and compilation.
  4. Emit: When building the project, TypeScript compiles ./utils.ts into ./utils.js in the output directory and leaves the import path ./utils.js completely unchanged in the emitted JavaScript files.

Support for Additional Extensions

This substitution logic applies symmetrically to distinct module formats under the Node16/NodeNext resolution rules:

  • Specifiers ending in .mjs will resolve to ./file.mts or ./file.d.mts.
  • Specifiers ending in .cjs will resolve to ./file.cts or ./file.d.cts.
  • Specifiers ending in .js can also resolve to .jsx files when JSX processing is enabled.

Required Configuration

For this resolution mechanism to function correctly, your environment must be explicitly configured for native ESM:

  1. package.json: Set "type": "module" to tell Node.js and TypeScript that .js and .ts files should be treated as ES modules.

  2. tsconfig.json: Configure the module settings to modern Node resolution:

    {
  "compilerOptions": {
    "module": "NodeNext",
    "moduleResolution": "NodeNext",
    "target": "ES2022"
  }
}

By aligning the import syntax with the expected runtime output, TypeScript ensures that emitted JavaScript executes natively without the need for post-processing or bundler intervention.
