TypeScript Bivariance: Methods vs Property Functions

In TypeScript, parameter variance rules differ significantly between method syntax and function property syntax when the --strictFunctionTypes compiler flag is enabled. While function property declarations enforce strict contravariant parameter checking, method declarations deliberately retain bivariant parameter checking. This article explores how this variance behavior operates in both declarations, why TypeScript maintains this distinction, and how to choose the right approach for type safety.

Understanding Function Parameter Variance

When comparing two function types, variance determines whether one function can be safely assigned to another based on their parameter types.

  • Contravariance requires that a callback or function parameter accept a type that is equal to or broader (a supertype) than the expected parameter type.
  • Bivariance allows a parameter to be either a supertype (contravariant) or a subtype (covariant), effectively loosening type safety by permitting narrower types to be passed where broader types are expected.

Method Declarations and Bivariance

Method syntax is defined directly within an interface, class, or object type using standard method signature notation:

interface AnimalComparer {
  compare(a: Animal): number;
}

Even when --strictFunctionTypes is enabled, methods declared with this shorthand syntax are checked bivariantly. This means a method expecting a narrower derived type can be assigned to a method expecting a broader base type, and vice versa.

class Animal { name!: string; }
class Dog extends Animal { bark() {} }

interface MethodContainer {
  handle(animal: Animal): void;
}

let dogHandler = {
  handle(dog: Dog): void {
    dog.bark();
  }
};

// Allowed due to method bivariance, despite potential runtime errors:
let container: MethodContainer = dogHandler;

// Runtime failure: passing an Animal that lacks the bark() method
container.handle(new Animal());

Property Function Declarations and Contravariance

Function property syntax defines a function as a property holding a function type signature:

interface AnimalComparer {
  compare: (a: Animal) => number;
}

Under --strictFunctionTypes, property functions enforce strict contravariant parameter checking. The compiler rejects assignments where the incoming function parameter is more specific than the target definition requires.

interface PropertyContainer {
  handle: (animal: Animal) => void;
}

let strictDogHandler = {
  handle: (dog: Dog) => {
    dog.bark();
  }
};

// TypeScript Error: Type '(dog: Dog) => void' is not assignable to type '(animal: Animal) => void'.
// Property 'bark' is missing in type 'Animal' but required in type 'Dog'.
let strictContainer: PropertyContainer = strictDogHandler;

Why the Distinction Exists

TypeScript intentionally preserves bivariant checking for method declarations to accommodate common JavaScript patterns, most notably with built-in mutable structures like arrays.

In JavaScript, Array<Derived> is routinely treated as a subtype of Array<Base>. If methods like push(item: T) were strictly contravariant, Dog[] could not be assigned to Animal[], because Dog[].push accepts only Dog, while Animal[].push accepts any Animal. By keeping method declarations bivariant, TypeScript allows array covariance to function smoothly at the cost of strict runtime safety.

Best Practices for Type Safety

To maximize type safety and prevent runtime errors caused by bivariant assignments:

  1. Use Property Signatures for Callbacks: When writing interfaces that accept handlers, event listeners, or callbacks, always declare them as function properties (callback: (data: T) => void) rather than methods (callback(data: T): void).
  2. Reserve Method Signatures for True Methods: Use method shorthand syntax primarily when modeling object-oriented APIs, classes, or structures where method override flexibility is required and the structural risks are understood.
