Structural Typing vs Nominal Typing in TypeScript

In domain-driven design with TypeScript, understanding type mechanics is critical for building resilient software architectures. This article explores the core differences between TypeScript’s default structural typing system, the concept of nominal typing, and how structural equality applies to domain entities and value objects. By comparing how the compiler validates shapes versus how domain models enforce explicit business rules, you will learn how to prevent domain errors and implement nominal safety patterns within a structurally typed language.

Structural Typing in TypeScript

TypeScript utilizes a structural type system, commonly referred to as "duck typing." In a structural system, two types are considered compatible if they share the same shape (the same properties and method signatures), regardless of how or where they are defined.

type UserId = string;
type OrderId = string;

function cancelOrder(id: OrderId) {
  // logic to cancel order
}

const userId: UserId = "user_123";
cancelOrder(userId); // Valid in TypeScript, but an error in domain logic

From a compiler perspective, both UserId and OrderId resolve to string. The structural type system allows this substitution because the underlying representations are identical. While this flexibility simplifies component composition and JavaScript interoperability, it introduces risks in domain modeling where distinct business concepts must remain isolated.

Nominal Typing Explained

Nominal typing determines type equivalence based strictly on explicit declarations and unique type names, rather than the internal shape of the data. Languages like Java, C#, and Rust are primarily nominal.

In a nominal system:

  • Two types with identical properties are strictly incompatible unless an explicit relationship (like inheritance or interface implementation) is declared.
  • Passing a UserId to a function expecting an OrderId produces a compile-time error, even if both internally wrap a primitive string.

Nominal typing maps naturally to domain-driven design because it treats business identifiers and concepts as distinct entities that cannot be accidentally transposed.

Structural Equality vs. Structural Typing

It is important to distinguish structural typing from structural equality:

  • Structural Typing is a static compile-time mechanism determining whether type A can be assigned to type B based on property contracts.
  • Structural Equality is a runtime comparison rule, typical of Value Objects in Domain-Driven Design (DDD). Two instances are equal if their internal values are identical, regardless of whether they share the same memory reference.

By default, JavaScript and TypeScript evaluate objects using reference equality (===). To enforce structural equality in a domain model, you must explicitly implement comparison methods (such as an .equals() method) on your Value Objects.

class Money {
  constructor(public readonly amount: number, public readonly currency: string) {}

  equals(other: Money): boolean {
    return this.amount === other.amount && this.currency === other.currency;
  }
}

Simulating Nominal Typing in TypeScript (Branded Types)

Because TypeScript is structurally typed, domain modelers simulate nominal typing using a technique called "branding" or "tagging." By attaching a unique phantom property to a type, you force the compiler to treat identical structures as distinct nominal types.

type Brand<K, T> = K & { readonly __brand: T };

type UserId = Brand<string, "UserId">;
type OrderId = Brand<string, "OrderId">;

function createUserId(id: string): UserId {
  return id as UserId;
}

function createOrderId(id: string): OrderId {
  return id as OrderId;
}

function cancelOrder(id: OrderId) {
  // Cancel logic
}

const user = createUserId("usr_abc");
const order = createOrderId("ord_xyz");

cancelOrder(order); // Valid
cancelOrder(user);  // Error: Type '"UserId"' is not assignable to type '"OrderId"'

Branding introduces zero runtime overhead while enforcing strict nominal boundaries during static analysis.

Key Differences Summary

Feature Structural Typing Nominal Typing
Equivalence Basis Shape, property names, and property types Explicit type name and declaration
TypeScript Support Native, default language behavior Simulated via branded/tagged types
Domain Use Case Data Transfer Objects (DTOs), generic utilities Domain Identifiers, Value Objects, Entities
Safety Level High flexibility, lower domain isolation Strict boundaries, prevents primitive obsession

Application in Domain Modeling

When modeling business domains in TypeScript:

  1. Use Structural Typing for DTOs and Contracts: External payloads, API responses, and simple data interfaces benefit from structural compatibility.
  2. Use Branded Nominal Types for Identifiers: Prevent primitive obsession by branding primary keys, IDs, and raw measurements.
  3. Use Structural Equality for Value Objects: Ensure immutable objects with no conceptual identity evaluate equality based on their properties rather than object references.
