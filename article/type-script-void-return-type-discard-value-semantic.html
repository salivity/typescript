TypeScript Void Return Type Discard-Value Semantic

This article explains the discard-value semantic of the void return type in TypeScript, detailing how and why TypeScript allows functions that return values to satisfy void-returning callback types. You will learn the mechanical differences between declaring a function directly with a void return type versus using a void return type in callback signatures, how this behavior facilitates idiomatic JavaScript patterns, and how it contrasts with the strict undefined return type.

What is the Discard-Value Semantic?

In TypeScript, when a function type specifies a return type of void (such as () => void), it indicates that the caller will not inspect or rely on the return value of that function. This is known as the discard-value semantic. It does not mean the function must return undefined; rather, it signifies that whatever value the function returns will be ignored and treated as unusable by the caller.

type VoidCallback = () => void;

// Valid: The function returns a number, but the caller discards it
const runCallback: VoidCallback = () => {
  return 42; 
};

// Error: Type 'void' is not assignable to type 'number'
// TypeScript prevents the caller from using the returned value
const result: number = runCallback();

Function Declarations vs. Callback Types

The discard-value semantic applies strictly to context-dependent function types, such as callback signatures or interface method declarations. It behaves differently when directly annotating a literal function declaration.

Literal Function Declarations

When a function declaration or expression is explicitly annotated with a : void return type at its definition site, TypeScript enforces that it must not return a value (other than undefined or an empty return statement).

// Error: Type 'number' is not assignable to type 'void'
function directFunction(): void {
  return 100;
}

Contextual and Callback Signatures

When void appears in a function type definition, any function returning any type can be assigned to it:

interface Processor {
  process: () => void;
}

const p: Processor = {
  // Completely valid despite returning a boolean
  process: () => true, 
};

Why TypeScript Uses Discard-Value Semantics

This design choice allows TypeScript to remain compatible with standard JavaScript idioms, particularly high-order array methods and event handling.

Consider Array.prototype.forEach. The TypeScript definition for forEach expects a callback returning void:

forEach(callbackfn: (value: T, index: number, array: T[]) => void, thisArg?: any): void;

In JavaScript, it is common to use shorthand arrow functions with methods that happen to return a value:

const numbers = [1, 2, 3];
const targetArray: number[] = [];

// Array.prototype.push returns the new length of the array (a number)
numbers.forEach(num => targetArray.push(num));

If void meant "must return nothing," the code above would produce a type error because targetArray.push() returns a number. Because () => void uses discard-value semantics, TypeScript permits this code while still ensuring that nothing inside forEach attempts to use the value returned by push.

Difference Between void and undefined

If you genuinely want to restrict a callback to returning nothing or specifically undefined, you must explicitly annotate the return type as undefined rather than void.

  • () => void: Accepts a function returning any type, but marks the resulting value as unobservable (void).
  • () => undefined: Strictly requires that the function returns literal undefined or executes a bare return.
type StrictCallback = () => undefined;

// Error: Type 'number' is not assignable to type 'undefined'
const invalid: StrictCallback = () => 42; 

// Valid
const valid: StrictCallback = () => undefined;

Understanding this semantic prevents confusion when functions returning concrete data seamlessly satisfy interfaces and callbacks typed with void.
