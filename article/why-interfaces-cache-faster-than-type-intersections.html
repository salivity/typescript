Why Interfaces Cache Faster Than Type Intersections

This article explores the architectural differences in how the TypeScript compiler processes object shapes, focusing on why interface declarations achieve superior caching performance compared to intersection types (&). While interfaces register a single, persistent shape identity within the compiler’s internal type checker, type intersections force the engine to dynamically evaluate, merge, and check constituent properties for compatibility. Understanding these mechanics reveals why large codebases benefit significantly from preferring interfaces for object modeling to optimize build times and compiler throughput.

Canonical Identity vs. Dynamic Synthesis

The primary reason interfaces cache faster is how they are registered in the compiler’s symbol table. An interface declaration creates a single canonical type identity associated directly with a persistent symbol. When the compiler encounters an interface like interface User { id: string }, it constructs a single flat object type and stores it under that symbol's unique ID. Subsequent references simply fetch this already-constructed type object from the cache.

In contrast, intersection types (such as type User = Base & { id: string }) are synthetic, structural operations. An intersection is not an atomic declaration; it is an operation combining two or more distinct types. Even when assigned to a type alias, the alias points to an intersection node rather than a pre-flattened object shape. The compiler must retain the individual components of the intersection to evaluate relationships, which prevents immediate, flat caching at the point of declaration.

Flat Shape Evaluation and Conflict Resolution

When interfaces extend one another via the extends keyword, TypeScript enforces strict property consistency during declaration. If two interfaces declare a property with the same name, their types must be identical or directly assignable; otherwise, the compiler raises an immediate error. This rule allows the compiler to produce a clean, flat property map once.

Intersection types handle property conflicts dynamically:

  • If type A has { prop: string } and type B has { prop: number }, A & B computes { prop: string & number }, which resolves to { prop: never }.
  • If properties are methods or function signatures, intersections construct overloaded functions.

Because the compiler must evaluate property-by-property intersections across every branch of an intersection tree, it expends CPU cycles computing intersections on demand. These computed properties must be checked whenever the type is examined, creating significant computational overhead compared to an interface's pre-flattened property list.

Relationship Caching in Type Checking

During type checking, the compiler spends the majority of its time evaluating assignability using internal routines like isTypeAssignableTo. To stay performant, TypeScript maintains an internal relationship cache that stores pairs of source and target type IDs that have already been evaluated.

  • Interfaces: Because each interface has a fixed, stable type ID, the result of checking whether InterfaceA is assignable to InterfaceB can be stored in the relationship cache immediately. The next time the compiler checks this pair, it performs an \(O(1)\) dictionary lookup.
  • Intersections: Intersections often generate anonymous compound types during instantiation, especially when combined with generics. These compound types may not have stable global IDs, leading to cache misses. When a cache miss occurs, the compiler must recursively decompose the intersection and test every constituent member against the target type.

Deeply Nested and Recursive Structures

The performance gap widens drastically as type hierarchies grow deeper. When an intersection contains other intersections (for example, A & B & C & D), TypeScript must evaluate the entire tree structurally to determine member visibility and compatibility. This process scales quadratically or exponentially in complex scenarios, particularly when evaluating unions distributed across intersections.

Interfaces flatten their inheritance trees up front. An interface that extends multiple base interfaces compiles into a single unified member table. By eliminating the need to traverse multi-layered abstract syntax tree (AST) nodes during type comparison, interfaces reduce the memory footprint and CPU cycles required by the compiler's caching pipeline.
