Typing Redux Actions and Reducers in TypeScript

Typing Redux state management in TypeScript can range from verbose boilerplate to elegant, fully inferred architectures. This article covers the primary strategies for cleanly typing Redux actions and reducers, contrasting the modern standard—Redux Toolkit—with traditional vanilla Redux patterns, such as discriminated unions and action creator inference, ensuring strong type safety with minimal manual maintenance.

1. The Modern Standard: Redux Toolkit (RTK)

The cleanest and officially recommended strategy for typing Redux code is Redux Toolkit. RTK's createSlice API automatically generates action creators and action types based on the reducers you provide, drastically reducing redundant type declarations.

import { createSlice, PayloadAction } from '@reduxjs/toolkit';

interface UserState {
  name: string;
  age: number;
}

const initialState: UserState = {
  name: '',
  age: 0,
};

const userSlice = createSlice({
  name: 'user',
  initialState,
  reducers: {
    setName: (state, action: PayloadAction<string>) => {
      state.name = action.payload;
    },
    setAge: (state, action: PayloadAction<number>) => {
      state.age = action.payload;
    },
    reset: () => initialState,
  },
});

export const { setName, setAge, reset } = userSlice.actions;
export default userSlice.reducer;

With createSlice, the state type is defined once in initialState, and individual payloads are typed directly using PayloadAction<T>. Redux Toolkit then automatically infers the correct types for all generated action creators.

2. Discriminated Unions for Vanilla Redux

If you are working with legacy or vanilla Redux without RTK, the cleanest approach is to use discriminated unions. By typing the type property of an action with string literal types, TypeScript narrows the specific action type inside a reducer's switch statement.

// Action constants
const SET_NAME = 'user/SET_NAME';
const SET_AGE = 'user/SET_AGE';

// Action interfaces
interface SetNameAction {
  type: typeof SET_NAME;
  payload: string;
}

interface SetAgeAction {
  type: typeof SET_AGE;
  payload: number;
}

// Discriminated union
type UserActionTypes = SetNameAction | SetAgeAction;

// Reducer with type narrowing
function userReducer(state = initialState, action: UserActionTypes): UserState {
  switch (action.type) {
    case SET_NAME:
      // action.payload is typed as string
      return { ...state, name: action.payload };
    case SET_AGE:
      // action.payload is typed as number
      return { ...state, age: action.payload };
    default:
      return state;
  }
}

3. Action Creator Type Inference (ReturnType)

Writing explicit action interfaces alongside action creator functions can lead to duplicate type declarations. You can streamline vanilla Redux by writing action creators with as const assertions and inferring the action types using TypeScript's ReturnType.

export const setName = (name: string) => ({
  type: 'user/SET_NAME' as const,
  payload: name,
});

export const setAge = (age: number) => ({
  type: 'user/SET_AGE' as const,
  payload: age,
});

// Infer action types automatically
type UserActions = ReturnType<typeof setName> | ReturnType<typeof setAge>;

Using as const preserves the literal string types, allowing TypeScript to construct the discriminated union automatically without manually writing separate action interfaces.

4. Deriving RootState and AppDispatch

Regardless of the action strategy you use, typing your store's root state and dispatch function should always rely on inference rather than manual declaration. This ensures your types automatically stay up to date as your store grows.

import { configureStore } from '@reduxjs/toolkit';
import rootReducer from './rootReducer';

export const store = configureStore({
  reducer: rootReducer,
});

// Clean type derivation
export type RootState = ReturnType<typeof store.getState>;
export type AppDispatch = typeof store.dispatch;

By pairing these inferred store types with custom typed hooks (useAppDispatch and useAppSelector), you eliminate the need to import RootState across your component tree, completing a clean, end-to-end typed Redux workflow.
