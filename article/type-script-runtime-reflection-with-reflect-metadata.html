TypeScript Runtime Reflection With Reflect Metadata

TypeScript normally erases all type information during compilation, making types unavailable at runtime. However, by enabling the emitDecoratorMetadata compiler flag and importing the reflect-metadata polyfill, developers can preserve and access design-time types when using decorators. This article explains how the TypeScript compiler serializes types into runtime metadata, how reflect-metadata provides an API to read and write that data, and how these tools work together to power advanced patterns like Dependency Injection and validation.

The Challenge: Type Erasure

TypeScript is a purely compile-time type system. When source code compiles to JavaScript, interfaces, type aliases, and type annotations are completely stripped away. Under normal circumstances, inspecting a variable, function parameter, or class property at runtime yields standard JavaScript primitives or generic Object instances, with no reference to the original TypeScript types.

How emitDecoratorMetadata Works

The emitDecoratorMetadata flag is a setting in tsconfig.json that modifies the code generator. When set to true alongside experimentalDecorators: true, TypeScript inspects elements annotated with decorators and emits helper calls that serialize their type information directly into the JavaScript output.

Whenever a decorator is applied to a class, method, property, or accessor, the compiler automatically generates calls to a helper function named __metadata. It injects three primary metadata keys:

  • design:type: Emitted for properties and accessors, representing the property's data type.
  • design:paramtypes: Emitted for constructors and methods, representing an array of parameter types.
  • design:returntype: Emitted for methods and accessors, representing the return type.

For example, consider this TypeScript snippet:

function Injectable(): ClassDecorator {
  return (target) => target;
}

class UserService {}

@Injectable()
class UserController {
  constructor(private userService: UserService) {}
}

When compiled with emitDecoratorMetadata, TypeScript generates output similar to this:

var __metadata = (this && this.__metadata) || function (k, v) {
    if (typeof Reflect === "object" && typeof Reflect.metadata === "function") return Reflect.metadata(k, v);
};

UserController = __decorate([
    Injectable(),
    __metadata("design:paramtypes", [UserService])
], UserController);

TypeScript serializes the UserService reference directly into the decorator call stack under the design:paramtypes key.

The Role of reflect-metadata

The __metadata helper emitted by TypeScript assumes the existence of a global Reflect.metadata method. However, this method is part of a proposed ECMAScript reflection standard that is not yet natively supported in JavaScript engines.

This is where the reflect-metadata package becomes necessary. It acts as a runtime polyfill that:

  1. Defines the Reflect metadata API (Reflect.defineMetadata, Reflect.getMetadata, Reflect.hasMetadata, etc.).
  2. Provides the underlying in-memory storage (typically mapped to targets using WeakMap) where metadata key-value pairs are kept.
  3. Allows frameworks and libraries to retrieve the types that the compiler generated.

To make this functionality work, reflect-metadata must be imported once at the entry point of the application before any decorated code executes:

import 'reflect-metadata';

Reading Types at Runtime

Once metadata is emitted and stored, developers can read it at runtime using the Reflect.getMetadata function. This enables runtime frameworks (such as NestJS, TypeORM, or custom dependency injection containers) to inspect classes dynamically.

Reading the constructor parameter types of the previous example looks like this:

import 'reflect-metadata';

const paramTypes = Reflect.getMetadata('design:paramtypes', UserController);
console.log(paramTypes); // [ [class UserService] ]

The consumer receives an array containing the actual constructor reference for UserService, which can then be instantiated and injected automatically.

Limitations of Decorator Metadata

While this mechanism bridges the gap between compile-time and runtime, it has inherent constraints:

  • Decorators are Mandatory: TypeScript only emits metadata for elements that have at least one decorator attached. Undecorated classes or functions do not receive metadata.
  • Complex Types Degenerate: Because runtime reflection requires concrete JavaScript values, TypeScript types that do not exist at runtime (such as interfaces, type aliases, or complex union types) cannot be serialized. In these cases, TypeScript falls back to emitting Object or undefined.
  • Circular Dependencies: If two classes depend on each other through constructor parameters, runtime metadata evaluation may encounter undefined references during module loading.
