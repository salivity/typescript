How TypeScript Resolves package.json Exports Maps

This article explains how TypeScript locates and resolves type definitions using the modern Node.js package.json "exports" map. It covers the compiler options required to enable this behavior, the precedence rules TypeScript follows for conditional mappings, the role of the "types" condition, and how package encapsulation affects imports.

Enabling Exports Support in tsconfig.json

By default, legacy resolution modes (such as "moduleResolution": "node") ignore the "exports" field entirely and look only at the traditional "types" or "typings" root fields and file-system paths.

To make TypeScript respect the "exports" map, you must configure modern resolution in your tsconfig.json:

{
  "compilerOptions": {
    "moduleResolution": "node16" // or "nodenext", or "bundler"
  }
}
  • node16 / nodenext: Mimics Node.js ECMAScript Module (ESM) resolution strictly, enforcing file extensions and condition rules based on whether the consuming file is ESM or CommonJS.
  • bundler: Emulates modern bundlers (like Vite, Webpack 5, or esbuild), allowing extensionless imports while still honoring the "exports" map.

How Resolution Traverses the Exports Map

When an import like import { feature } from "my-library/subpath" is encountered, TypeScript performs the following steps:

  1. Locate the Package: TypeScript finds node_modules/my-library/package.json.
  2. Identify Target Subpath: It matches /subpath against keys in the "exports" object (e.g., "./subpath" or matching wildcard patterns like "./*").
  3. Evaluate Conditions: TypeScript checks the conditions defined for that subpath to find the matching declaration file.

The Role of Conditional Exports

The "exports" field allows different targets depending on how the package is consumed. A typical setup looks like this:

{
  "name": "my-library",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs"
    },
    "./utils": {
      "types": "./dist/utils.d.ts",
      "default": "./dist/utils.js"
    }
  }
}

Order Matters

TypeScript evaluates keys in the order they appear in the JSON object. The "types" condition must always appear before runtime conditions like "import", "require", or "default". If a runtime condition precedes "types", TypeScript may resolve directly to the JavaScript file instead of looking for the corresponding declaration file.

Format-Specific Declarations

When supporting dual-module packages (CJS and ESM) under "moduleResolution": "node16", TypeScript distinguishes between CommonJS typings and ESM typings:

{
  "exports": {
    ".": {
      "import": {
        "types": "./dist/esm/index.d.mts",
        "default": "./dist/esm/index.mjs"
      },
      "require": {
        "types": "./dist/cjs/index.d.cts",
        "default": "./dist/cjs/index.cjs"
      }
    }
  }
}
  • If imported from an ESM file, TypeScript selects the import branch and requires .d.mts or types with ESM semantics.
  • If imported from a CommonJS file, TypeScript selects the require branch and loads .d.cts or types with CommonJS semantics.

Pattern Matching and Wildcards

Wildcards allow mapping multiple subpaths dynamically without listing every file manually:

{
  "exports": {
    "./features/*": {
      "types": "./dist/features/*.d.ts",
      "default": "./dist/features/*.js"
    }
  }
}

When resolving my-library/features/auth, TypeScript substitutes the wildcard * with auth and loads ./dist/features/auth.d.ts.

Package Encapsulation

The "exports" map enforces strict internal encapsulation. If an "exports" field exists in a package's package.json, any internal file not explicitly declared in that map cannot be imported.

For example, attempting to import a file directly:

import { helper } from "my-library/dist/internal/helper.js";

TypeScript will raise an error (Cannot find module...) if ./dist/internal/helper.js is not exposed in the "exports" map, preventing consumers from depending on private implementation details.
