Why Use ts-expect-error Instead of ts-ignore

While both // @ts-ignore and // @ts-expect-error tell the TypeScript compiler to suppress a type error on the following line, modern TypeScript development heavily favors @ts-expect-error. The primary reason is safety: @ts-expect-error will trigger a compiler error if the suppressed code actually becomes type-safe, preventing dead suppressions and silent code degradation. This article explains the technical differences between these two directives, why relying on @ts-ignore introduces long-term maintenance issues, and how @ts-expect-error creates cleaner, more resilient codebases.

The Blind Spot of @ts-ignore

When introduced, // @ts-ignore gave developers a way to bypass strict type checking for edge cases, third-party library bugs, or rapid prototyping. However, @ts-ignore is an unconditional suppression. It silences any diagnostic on the following line, regardless of whether a diagnostic exists.

This behavior causes significant technical debt:

  • Stale Suppressions: If you refactor a function or upgrade an external dependency that fixes the original type error, the // @ts-ignore comment remains in the codebase unnoticed.
  • Masking New Bugs: If the underlying code changes in a way that introduces a completely different, critical error, @ts-ignore will still suppress it. You lose all type protection on that line permanently unless manually audited.

How @ts-expect-error Fixes the Problem

Introduced in TypeScript 3.9, // @ts-expect-error acts as an assertion that a compilation error must occur on the subsequent line.

If an error is present, TypeScript suppresses it just like @ts-ignore. However, if the code on the next line produces no type error, the compiler raises an error:

Unused '@ts-expect-error' directive.

By failing when no error exists, @ts-expect-error forces developers to remove suppressions that are no longer necessary, keeping the codebase clean automatically.

Key Advantages in Modern Development

1. Safer Dependency and TypeScript Upgrades

When upgrading your TypeScript version or third-party type definitions, bugs are frequently patched. With @ts-ignore, you will never know which workarounds are obsolete. With @ts-expect-error, the compiler immediately flags every workaround that has been resolved, allowing you to delete the directives and restore standard type checking.

2. Reliable Negative Type Testing

In library development and shared utilities, testing what a type rejects is just as important as testing what it accepts. Developers use @ts-expect-error in test suites to assert that invalid arguments trigger compiler failures:

// Testing that invalid types cannot be passed
// @ts-expect-error
calculateTotal("invalid_string_argument");

If a future change accidentally loosens the types to accept strings, the test will fail during compilation because the expected error did not occur.

3. Clearer Intent and Accountability

Writing @ts-expect-error communicates clear intent to other developers: "We know this code is technically invalid according to TypeScript, and we deliberately expect an error here." When paired with an explanation comment, it acts as a proactive, self-validating contract.

When Is @ts-ignore Still Acceptable?

The only standard scenario where // @ts-ignore remains useful is in codebases that must be compiled across multiple distinct versions of TypeScript simultaneously (such as distributed open-source packages). In that context, an error might occur in TypeScript 4.8 but be fixed in TypeScript 5.2. Using @ts-expect-error would break the build on the newer version because the error is gone, whereas @ts-ignore will allow both versions to compile without failure.

Outside of multi-compiler support, modern projects should completely replace // @ts-ignore with // @ts-expect-error. You can enforce this standard in your project using the ESLint rule @typescript-eslint/prefer-ts-expect-error.
