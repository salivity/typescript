How TypeScript Uses LSP to Communicate with IDEs

This article explores how the TypeScript language service interfaces with modern integrated development environments (IDEs) through the Language Server Protocol (LSP). While TypeScript natively uses a standalone tool called tsserver, modern developer tools utilize an LSP wrapper to translate standardized editor requests—such as autocompletion, type checking, and jump-to-definition—into the proprietary format TypeScript understands, creating a seamless, cross-editor development experience.

The Architecture: tsserver vs. LSP

TypeScript was created before the Language Server Protocol existed. As a result, the TypeScript core team maintains tsserver, a standalone process that provides language features using TypeScript’s own custom JSON-based messaging protocol.

To bridge tsserver with editors that strictly adhere to the Language Server Protocol (such as Neovim, Emacs, Sublime Text, or Eclipse Theia), the community relies on an adapter, most commonly typescript-language-server. This adapter acts as a proxy:

  1. LSP Client (The IDE): Speaks standard LSP.
  2. LSP Server (The Adapter): Receives LSP requests and converts them into tsserver commands.
  3. Core Engine (tsserver): Executes the compiler logic, semantic analysis, and type checking, then returns responses to the adapter.
[ IDE / Editor ] <--- (LSP over JSON-RPC) ---> [ typescript-language-server ] <--- (tsserver protocol) ---> [ tsserver ]

(Note: Visual Studio Code contains its own built-in integration layer to talk directly to tsserver, but it follows the exact same architectural principles.)

The Transport Layer: JSON-RPC

Communication between the IDE and the language server is asynchronous and relies on the JSON-RPC 2.0 protocol. The transmission typically happens over standard input and output (stdio), though sockets or Node.js IPC channels can also be used.

Each message contains a header specifying the content length followed by a JSON payload:

Content-Length: 118

{"jsonrpc":"2.0","id":1,"method":"textDocument/completion","params":{"textDocument":{"uri":"file:///app.ts"},"position":{"line":5,"character":12}}}

Messages fall into two main categories:

  • Requests and Responses: Paired messages using an id field. The client asks for information (e.g., hover information or completions), and the server replies.
  • Notifications: One-way messages without an id. These are used for events like file modifications or diagnostic reports.

Key Communication Phases

1. Initialization and Handshake

When an IDE opens a TypeScript workspace, it starts the language server child process and sends an initialize request. This payload specifies the client's capabilities (e.g., whether it supports snippet completions or markdown hover documentation). The server responds with its own server capabilities, letting the editor know which language features it supports.

2. Document Synchronization

Because disk I/O is too slow for real-time code analysis, the IDE keeps the language server updated with in-memory changes:

  • textDocument/didOpen: Notifies the server that a file is active.
  • textDocument/didChange: Sends incremental or full-text updates as the user types.

The adapter receives these events, updates its internal virtual file tree, and notifies tsserver so the compiler can re-evaluate types and abstract syntax trees (AST).

3. Language Feature Queries

When a user triggers an action (like requesting autocomplete), the flow operates synchronously from the user's perspective:

  1. The IDE sends textDocument/completion with the file URI and cursor coordinates.
  2. The LSP wrapper converts this into a tsserver quickinfo or completions command.
  3. tsserver inspects the AST at the given position and calculates valid tokens.
  4. The wrapper formats these tokens into standard LSP CompletionItem[] objects.
  5. The IDE renders the autocomplete pop-up.

4. Diagnostics and Error Reporting

Type errors and syntax warnings do not wait for user interaction. When code changes, tsserver triggers a background validation cycle. The language server collects these errors and pushes a textDocument/publishDiagnostics notification to the IDE, allowing the editor to highlight syntax errors and populate the "Problems" panel instantly.
