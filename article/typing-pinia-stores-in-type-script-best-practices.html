Typing Pinia Stores in TypeScript: Best Practices

Properly typing Pinia stores in Vue 3 ensures complete type safety, accurate auto-completion, and fewer runtime errors across your application. This guide outlines the essential best practices for using TypeScript with Pinia, covering the choice between Setup and Option stores, explicit state typing, getter inference, asynchronous action typing, and safely destructuring store properties without breaking reactivity.

1. Prefer Setup Stores for Better Type Inference

Pinia supports both Option Stores and Setup Stores. Setup Stores (defined with a function syntax similar to the Vue Composition API) provide superior TypeScript support out of the box. They eliminate the complexities of typing this and make relying on native TypeScript inference much more seamless.

import { defineStore } from 'pinia';
import { ref, computed } from 'vue';

interface User {
  id: string;
  name: string;
  role: 'admin' | 'user';
}

export const useUserStore = defineStore('user', () => {
  const currentUser = ref<User | null>(null);
  const isAuthenticated = computed(() => currentUser.value !== null);

  function setUser(user: User) {
    currentUser.value = user;
  }

  return { currentUser, isAuthenticated, setUser };
});

2. Define Explicit Interfaces for State

Avoid relying entirely on default values for type inference, especially when initial state values can be null, empty arrays, or complex nested objects. Define dedicated interfaces for your domain models and pass them as generics to ref() or declare them in your state interface.

export interface Product {
  id: number;
  title: string;
  price: number;
}

// In Setup Store
const products = ref<Product[]>([]);
const selectedProduct = ref<Product | null>(null);

If you are using Option Stores, use the return type of the state function or cast the initial value:

interface State {
  products: Product[];
  selectedProduct: Product | null;
}

export const useProductStore = defineStore('product', {
  state: (): State => ({
    products: [],
    selectedProduct: null,
  }),
});

3. Explicitly Type Getter Return Values in Option Stores

When using Option Stores, TypeScript can struggle with circular type inference if a getter accesses another getter through this. To resolve this, always annotate the return type of getters explicitly.

export const useCartStore = defineStore('cart', {
  state: () => ({
    items: [] as Product[],
  }),
  getters: {
    // Explicit return type avoids circular type references
    totalCount(): number {
      return this.items.length;
    },
    hasItems(): boolean {
      return this.totalCount > 0;
    },
  },
});

4. Strongly Type Action Arguments and Promises

Actions handle business logic and API requests. Always type action arguments and ensure asynchronous actions return typed Promises. This allows components awaiting store actions to be fully aware of the resolved outcome.

export const useAuthStore = defineStore('auth', () => {
  const token = ref<string | null>(null);

  async function login(credentials: { email: string; password: string }): Promise<boolean> {
    try {
      const response = await api.post<{ token: string }>('/login', credentials);
      token.value = response.data.token;
      return true;
    } catch {
      return false;
    }
  }

  return { token, login };
});

5. Preserve Types When Destructuring with storeToRefs

Destructuring state or getters directly from a Pinia store breaks reactivity and can cause subtle typing issues. Always use storeToRefs to extract state and getters while preserving both reactivity and TypeScript types. Actions do not require storeToRefs and should be destructured directly from the store.

import { storeToRefs } from 'pinia';
import { useUserStore } from '@/stores/user';

const userStore = useUserStore();

// currentUser and isAuthenticated retain their Ref types
const { currentUser, isAuthenticated } = storeToRefs(userStore);

// Actions are extracted directly
const { setUser } = userStore;

6. Manage Cross-Store Dependencies Cleanly

When one store depends on another, call the secondary store inside the action or getter where it is needed rather than at the top level of the file. This prevents circular dependency issues during TypeScript compilation and runtime initialization.

export const useOrderStore = defineStore('order', () => {
  async function placeOrder() {
    // Instantiate inside the function to avoid circular references
    const userStore = useUserStore();

    if (!userStore.isAuthenticated) {
      throw new Error('User must be authenticated');
    }

    await api.post('/orders', { userId: userStore.currentUser?.id });
  }

  return { placeOrder };
});
