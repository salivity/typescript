Why Unique Symbols Must Be Const in TypeScript

In TypeScript, the unique symbol type provides a way to treat symbols as distinct, nominal types rather than a general, broad symbol primitive. This article explains why TypeScript strictly requires unique symbol declarations to be bound to const variables or readonly static class properties. By examining reference immutability, compile-time identity tracking, and the mechanics of TypeScript's type checker, you will understand how these constraints maintain soundness and prevent identity drift in your code.

The Role of unique symbol

The standard symbol type in TypeScript represents any possible runtime symbol created via Symbol(). Because symbols are inherently unique at runtime, TypeScript introduced the unique symbol subtype to represent individual, literal symbol identities at compile time.

This type allows symbols to act as unique property keys, branded types, or nominal identifiers. For the type system to treat a symbol as a unique type, it must link that type to a specific, unchangeable identifier.

Preventing Reassignment and Type Drift

TypeScript binds a unique symbol type directly to the variable identifier that declares it. If TypeScript allowed you to declare a unique symbol with let or var, the variable could be reassigned later in the program:

// Disallowed by TypeScript:
let mySymbol: unique symbol = Symbol("key");
mySymbol = Symbol("anotherKey"); // Mutates the underlying identity

If reassignment were permitted, the variable would no longer reliably point to the exact same runtime symbol. Any code relying on typeof mySymbol as a type-level key or token would become unsound because the static type could no longer guarantee the identity of the underlying runtime value. Requiring const guarantees that the identifier always points to the exact same symbol reference created during initialization.

Reference Identity as a Type

In TypeScript, unique symbol types are nominal. Each declaration creates a new, mutually exclusive type that is not assignable to any other unique symbol:

const symbolA: unique symbol = Symbol("token");
const symbolB: unique symbol = Symbol("token");

// Error: Type 'typeof symbolB' is not assignable to type 'typeof symbolA'.
const symbolC: typeof symbolA = symbolB;

Because TypeScript's type checker tracks these types through the identifier itself (using typeof identifier), the identifier must remain an immutable reference. A mutable binding breaks the compiler’s ability to use the identifier as a stable type token.

Why readonly static is Allowed on Classes

TypeScript allows unique symbol properties on classes only when they are marked as both readonly and static:

class Registry {
  static readonly entryId: unique symbol = Symbol("entryId");
}

This exception follows the same logic as const:

  1. readonly ensures immutability: The property cannot be modified after class initialization, ensuring the reference never changes.
  2. static ensures single-instance identity: A static property belongs to the constructor function rather than class instances.

Instance properties cannot hold unique symbol types because every new instance of a class would either share the same type while pointing to different runtime symbols, or require a distinct type for every instantiated object. TypeScript cannot track per-instance symbol types dynamically at compile time. Binding the symbol to the static constructor guarantees a single, predictable location in memory.

Summary

TypeScript restricts unique symbol declarations to const variables and readonly static properties to enforce immutability. Because the static type checker relies directly on the variable's declaration to establish its nominal identity, the underlying reference must never change. This restriction guarantees that compile-time type distinctions remain completely aligned with runtime values.
