How NestJS and TypeORM Use TypeScript Decorators

This article explores how modern TypeScript frameworks, specifically NestJS and TypeORM, utilize experimental decorators and runtime metadata reflection to enable declarative programming. By combining TypeScript's experimentalDecorators and emitDecoratorMetadata compiler flags with the reflect-metadata polyfill, these frameworks extract design-time type information and custom metadata at runtime. This mechanism forms the foundation for automated dependency injection, declarative route handling, and object-relational database mapping without requiring redundant configuration.

The Core Mechanism: Decorators and reflect-metadata

TypeScript's decorator implementation is an experimental feature that allows annotating and modifying classes, methods, accessors, properties, and parameters at design time. When decorators are enabled alongside metadata emission, the TypeScript compiler automatically embeds type information directly into the compiled JavaScript.

To make this work, two flags must be enabled in tsconfig.json:

{
  "compilerOptions": {
    "experimentalDecorators": true,
    "emitDecoratorMetadata": true
  }
}

When emitDecoratorMetadata is active, the compiler uses the global Reflect object (provided by the reflect-metadata package) to serialize three specific metadata keys on decorated members:

  • design:type: The type of the property or field.
  • design:paramtypes: An array of types representing a method or constructor's arguments.
  • design:returntype: The return type of a method.

Frameworks then read this metadata at runtime via Reflect.getMetadata() to understand the structure and types of user-defined code.

How NestJS Utilizes Decorators and Reflection

NestJS relies heavily on decorators and reflection to implement its dependency injection (DI) container and HTTP routing architecture.

Dependency Injection with Constructor Reflection

In NestJS, marking a class with @Injectable() registers it with the IoC (Inversion of Control) container. When a service requires another dependency, it is declared in the constructor:

@Injectable()
export class UsersService {
  constructor(private readonly logger: LoggerService) {}
}

Because emitDecoratorMetadata is enabled, TypeScript emits the design:paramtypes for the UsersService constructor as [LoggerService]. At runtime, the NestJS DI container inspects these parameter types using:

const dependencies = Reflect.getMetadata('design:paramtypes', UsersService);

NestJS sees that LoggerService is required, resolves an instance of LoggerService from its container, and injects it when instantiating UsersService. This removes the need to manually specify dependencies using string tokens in standard cases.

Route and Controller Mapping

NestJS uses class and method decorators such as @Controller('users'), @Get(':id'), and @Post() to define routing logic. Under the hood, these decorators call Reflect.defineMetadata() to store path strings, HTTP methods, and parameter transformation rules directly on the class and method prototypes. During bootstrap, NestJS iterates over all registered controllers, extracts this metadata, and binds the appropriate endpoints to the underlying HTTP server (such as Express or Fastify).

How TypeORM Utilizes Decorators and Reflection

TypeORM is an Object-Relational Mapper that uses decorators to map TypeScript classes to database tables and class properties to table columns.

Automatic Schema and Column Inference

When defining an entity in TypeORM, the developer decorates fields using @Column():

@Entity()
export class User {
  @PrimaryGeneratedColumn()
  id: number;

  @Column()
  name: string;

  @Column()
  isActive: boolean;
}

Instead of requiring explicit database types for every column (e.g., @Column({ type: 'varchar' })), TypeORM reads the design:type metadata emitted by TypeScript:

const propertyType = Reflect.getMetadata('design:type', User.prototype, 'name');

In this case, propertyType returns the JavaScript String constructor. TypeORM matches String to the default database type (such as VARCHAR in PostgreSQL or MySQL), Number to INTEGER, and Boolean to BOOLEAN.

Relationship Mapping

Relational decorators like @ManyToOne(), @OneToMany(), and @ManyToMany() rely on reflection and function closures to build database foreign keys and join tables. Because TypeScript cannot infer complex relationship targets that may cause circular dependency issues at runtime, decorators often accept a function returning the target entity (e.g., @OneToMany(() => Photo, photo => photo.user)). The decorator stores these relationships in a centralized metadata storage object, which TypeORM compiles into SQL schema migrations and runtime join queries.

Summary of the Lifecycle

  1. Compilation: TypeScript detects decorated classes, properties, or constructors and emits Reflect.metadata() calls containing design:type and design:paramtypes.
  2. Initialization: As application files load, the reflect-metadata polyfill populates an in-memory metadata registry. Decorator functions execute and attach custom domain metadata (such as SQL constraints or HTTP paths).
  3. Bootstrap: NestJS or TypeORM scans the stored metadata to assemble the dependency graph, route trees, and database schemas dynamically.
