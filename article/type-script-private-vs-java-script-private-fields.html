TypeScript private vs JavaScript Private Fields

When managing encapsulation in modern web development, developers often choose between TypeScript's private keyword and native JavaScript private fields denoted by a # prefix. While both mechanisms aim to hide class internals, they operate at fundamentally different levels of the execution lifecycle. TypeScript's private keyword enforces accessibility only at compile time, whereas JavaScript's # syntax provides true runtime encapsulation backed directly by the JavaScript engine. Understanding these differences in runtime enforcement, transpilation output, and inheritance behavior is essential for choosing the right tool for your project.

Compile-Time vs. Runtime Enforcement

The primary distinction between the two approaches lies in when and how access restrictions are enforced.

TypeScript's private Keyword

The private modifier is an abstraction provided solely by TypeScript's type system:

  • Compile-Time Only: The restriction exists strictly while TypeScript is checking your code. If you attempt to access a private property from outside the class, the TypeScript compiler will throw an error.
  • No Runtime Protection: Once compiled into JavaScript, the private keyword is completely erased. The property becomes a standard, publicly accessible property on the resulting object. It can be inspected via Object.keys(), accessed using bracket notation (instance["secret"]), or bypassed using type assertion ((instance as any).secret).

JavaScript's Hash # Private Fields

Native private fields (introduced in ECMAScript 2022) are hard limits enforced by the JavaScript runtime:

  • Hard Runtime Encapsulation: Fields prefixed with # (such as #secret) cannot be accessed outside the class body under any circumstances.
  • No Bypassing: Attempting to access #secret outside the declaring class results in a syntax error (if attempted directly) or a runtime TypeError. They do not appear in Object.keys(), Object.getOwnPropertyNames(), or for...in loops, and cannot be accessed via bracket notation (instance["#secret"] will return undefined or look for a literal string key named "#secret").

Syntax and Declaration

class Example {
  // TypeScript private modifier
  private tsSecret: string = "TypeScript hidden";

  // JavaScript private field
  #jsSecret: string = "JavaScript hidden";

  readSecrets() {
    // Both are accessible within the class body
    console.log(this.tsSecret);
    console.log(this.#jsSecret);
  }
}

const example = new Example();

// TypeScript compile error, but succeeds at runtime:
// (example as any).tsSecret -> "TypeScript hidden"

// Runtime error:
// example.#jsSecret -> SyntaxError: Private field '#jsSecret' must be declared in an enclosing class

Subclassing and Name Collisions

Both mechanisms prevent subclasses from accessing parent-private state, but they handle collisions differently:

  • TypeScript private: A subclass cannot define a property with the same name as a private property in the parent class without generating a TypeScript error, because both map to the same property name on the final prototype/instance.
  • JavaScript # fields: Private identifiers are scoped strictly to the declaring class. A subclass can declare a #secret field without colliding with or overriding a parent class's #secret field. Each class manages its own distinct internal slot.

Transpilation and Performance

  • TypeScript private: Leaves zero runtime overhead when targeting modern JavaScript, as it simply emits standard property declarations or assignments.
  • JavaScript # fields: When targeting modern runtimes (ES2022+), engines use optimized internal slots. However, if you configure TypeScript to compile native private fields down to older targets (such as ES2015 or ES5), the compiler must generate helper structures using WeakMap or WeakSet. This downlevel compilation introduces both a memory and execution speed overhead.

When to Use Which

  • Use TypeScript's private when you want cleaner syntax, only need developer ergonomics to prevent accidental usage within a TypeScript codebase, or need to support older browser environments without the overhead of WeakMap polyfills.
  • Use JavaScript's # fields when building security-sensitive logic, developing public libraries where consumers might use plain JavaScript, or when absolute internal privacy must be guaranteed against reflection and runtime inspection.
