Debug Slow TypeScript Type-Checking Performance

As TypeScript codebases grow, complex conditional types, deep unions, and sprawling dependency graphs can cause compilation times to spike dramatically. The TypeScript compiler (tsc) includes specialized diagnostic flags to measure, trace, and debug these performance bottlenecks. By utilizing --extendedDiagnostics for high-level performance metrics, --generateTrace to capture granular execution logs, and trace analysis tools like @typescript/analyze-trace, developers can pinpoint exact files, types, and compiler operations that cause slow type-checking performance.

1. Measuring Baseline Performance with --extendedDiagnostics

Before analyzing individual types, determine whether the bottleneck is type-checking, parsing, or I/O. Running the compiler with --extendedDiagnostics outputs high-level performance counters for the entire build process.

tsc --noEmit --extendedDiagnostics

Key output metrics include:

  • Check time: The total time spent evaluating types. If this number represents the majority of the total compilation time, slow type-checking is the primary issue.
  • Types count: The total number of unique types created. An unusually high number relative to project size often indicates excessive type generation.
  • Instantiations: The number of generic type instantiations. Spikes here typically point to deep recursive types, complex conditional types, or large union/intersection operations.

2. Generating Granular Traces with --generateTrace

When check time or instantiations are disproportionately high, use the compiler's tracing feature to capture detailed operational timelines.

Run the compiler with the --generateTrace flag followed by a target directory:

tsc --noEmit --generateTrace ./tsc-trace

This command generates two critical files inside the specified directory:

  • trace.json: A standard Chromium-compatible event trace recording compiler operations, file reads, and type resolutions over time.
  • types.json: A lookup table mapping internal numeric type IDs from trace.json to their human-readable type representations.

3. Visualizing Trace Data

You can inspect trace.json directly using browser-based tracing viewers or command-line analysis tools:

  • Perfetto / Chrome Tracing: Navigate to perfetto.dev or chrome://tracing in a Chromium-based browser and load trace.json. The timeline visually highlights long-running tasks, such as checkSourceFile, checkVariableDeclaration, and individual type-checking calls.
  • Analyze Trace Utility: Microsoft provides the @typescript/analyze-trace CLI tool to automatically parse trace directories and identify hotspots.
npx @typescript/analyze-trace ./tsc-trace

This tool highlights the files, functions, and specific type definitions that consumed the most processing time and recursion depth.

4. Identifying and Resolving Bottlenecks

Once the trace data exposes the slow areas, look for the following common patterns:

  • Excessive Union and Intersection Combinations: Intersecting large union types can trigger combinatorial explosions (\(O(N \times M)\) comparisons). Refactor massive unions into explicit maps or simplify interfaces.
  • Missing Return Type Annotations: When complex functions or exported library APIs omit explicit return types, TypeScript must infer them across deep call chains. Adding explicit return type annotations acts as a firewall, preventing the compiler from re-evaluating deep dependencies.
  • Unbounded Recursive Types: Deeply nested generic types without aggressive base-case short-circuiting lead to runaway instantiation limits. Ensure conditional types terminate as early as possible.
  • Overly Broad Types in Third-Party Libraries: Traces often reveal that heavy type operations stem from node_modules. Pinpointing these allows teams to wrap third-party types or adjust tsconfig.json paths to skip unnecessary library checking via skipLibCheck: true.
