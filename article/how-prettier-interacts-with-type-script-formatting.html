How Prettier Interacts with TypeScript Formatting

Prettier interacts with TypeScript by serving as a dedicated, opinionated code formatter that completely decouples visual code style from TypeScript's type-checking and compilation processes. While TypeScript includes its own language service capable of basic formatting, Prettier supersedes these capabilities by parsing TypeScript code into an Abstract Syntax Tree (AST) and re-printing it according to strict, standardized layout rules. This article explains the technical division of labor between Prettier and TypeScript, how Prettier parses TypeScript-specific syntax, how to resolve conflicts with editor tooling and linters, and the best practices for integrating both tools.

Separation of Concerns: Formatting vs. Type Checking

TypeScript is primarily a type-checker and compiler. Although the TypeScript Language Service (tsserver) offers built-in formatting settings (such as semicolons, spacing, and brace placement), these features are secondary to its main purpose: verifying type safety and compiling TypeScript into JavaScript.

Prettier, by contrast, cares exclusively about visual layout. It does not evaluate types, resolve module paths, or check for runtime logic errors. When integrated into a project, Prettier takes complete ownership of styling decisions—such as line wrapping, indent levels, single vs. double quotes, and trailing commas—allowing the TypeScript compiler to focus purely on semantic correctness.

How Prettier Parses TypeScript

To format TypeScript, Prettier must understand TypeScript-specific language features, including interfaces, type aliases, generics, enums, and access modifiers.

Prettier achieves this by using dedicated AST parsers. Under the hood, Prettier can parse TypeScript using either Babel’s TypeScript plugin or the TypeScript compiler API itself. Because Prettier operates directly on the AST, it guarantees that formatting does not alter the underlying semantics of the code. It strips away all original formatting—including existing whitespace and arbitrary line breaks—and completely reprints the code based on a target line length (commonly 80 or 100 characters).

During this reprint, Prettier formats complex TypeScript structures automatically, such as breaking long intersection types, union types, and deeply nested generic parameters across multiple lines for improved readability.

Resolving Editor Conflicts

Most modern code editors, like Visual Studio Code, include a built-in TypeScript formatter powered by tsserver. If both the editor's TypeScript formatter and Prettier are active, they will fight over code layout on save.

To establish Prettier as the definitive formatting tool, the editor must be configured to delegate all TypeScript formatting exclusively to Prettier. In VS Code, this is typically handled by setting Prettier as the default formatter and explicitly disabling the built-in TypeScript formatting engine:

{
  "editor.defaultFormatter": "esbenp.prettier-vscode",
  "editor.formatOnSave": true,
  "[typescript]": {
    "editor.defaultFormatter": "esbenp.prettier-vscode"
  },
  "[typescriptreact]": {
    "editor.defaultFormatter": "esbenp.prettier-vscode"
  },
  "typescript.format.enable": false
}

Disabling typescript.format.enable ensures that editor formatting commands execute only through Prettier, preventing visual layout jitter and conflicting edits.

Coordinating Prettier with ESLint and TypeScript-ESLint

Many projects use ESLint alongside TypeScript via typescript-eslint. ESLint contains both code-quality rules (e.g., preventing unused variables) and stylistic rules (e.g., enforcing bracket spacing).

When stylistic ESLint rules overlap with Prettier, conflicts arise. To prevent this:

  1. Use eslint-config-prettier: This configuration disables all formatting rules in ESLint, including those provided by @typescript-eslint/eslint-plugin, that might conflict with Prettier.
  2. Run Tools Separately: The recommended approach is to let Prettier handle file formatting (e.g., via editor extensions or prettier --write) and let ESLint handle static analysis and type-aware linting (e.g., eslint --ext .ts).

What Prettier Does Not Do

Prettier intentionally avoids certain operations that alter code semantics or order:

  • Import Sorting: Prettier does not automatically reorder or group import statements out of the box, as changing import order can produce side effects. Sorting imports requires an explicit plugin, such as @ianvs/prettier-plugin-sort-imports.
  • Dead Code Elimination: Unused types and imports are ignored by Prettier and must be handled by the TypeScript compiler (noUnusedLocals) or ESLint.
  • Type Refactoring: Prettier will not infer types, complete type definitions, or suggest code modernization patterns.

By keeping visual layout completely isolated from the type system, Prettier ensures consistent code presentation across teams while leaving code integrity, analysis, and syntax validation entirely to TypeScript.
