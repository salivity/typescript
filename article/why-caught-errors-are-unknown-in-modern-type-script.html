Why Caught Errors Are Unknown in Modern TypeScript

Modern TypeScript types caught error variables as unknown instead of any to enforce type safety and eliminate runtime crashes caused by unvalidated assumptions. Because JavaScript permits throwing any arbitrary value—from strings and numbers to null or standard Error objects—typing errors as any created a false sense of security by completely disabling compiler checks. By defaulting caught errors to unknown, TypeScript forces developers to inspect and narrow the error’s type before accessing its properties, ensuring exception-handling code is genuinely resilient.

The Flaw of Typing Caught Errors as any

In early versions of TypeScript, caught errors were automatically typed as any. While convenient, this behavior undermined the primary goal of the type system. When an identifier is typed as any, TypeScript permits arbitrary property access, method calls, and assignments without validation:

try {
  performRiskyOperation();
} catch (error) {
  // If 'error' is 'any', the compiler allows this without warning:
  console.error(error.message.toUpperCase());
}

If performRiskyOperation() throws a string, a number, or an object missing a message property, the code above will crash at runtime with a TypeError: Cannot read properties of undefined. Typing caught errors as any silenced compiler warnings precisely where uncertainty was highest.

JavaScript Can Throw Any Value

Unlike languages such as Java or C#, JavaScript does not require thrown values to inherit from a base Error class. A program can legally throw any data type:

throw "Something went wrong";
throw 500;
throw { code: "NOT_FOUND", status: 404 };
throw null;
throw undefined;

Because external libraries, third-party APIs, and legacy code can throw non-standard values, the runtime type of a caught exception is genuinely unknowable until it is inspected.

Why unknown Is the Correct Representation

TypeScript introduced the unknown type in version 3.0 as a type-safe counterpart to any. While both types accept any value, unknown forbids you from reading properties, calling methods, or passing the value to other functions until you explicitly narrow it to a specific type.

By representing caught errors as unknown, the compiler accurately reflects the unpredictability of JavaScript's throw statement:

try {
  performRiskyOperation();
} catch (error: unknown) {
  // Compiler Error: 'error' is of type 'unknown'.
  console.log(error.message);
}

This restriction prevents accidental runtime errors by making unverified assumptions impossible to compile.

Handling unknown Errors Safely

Working with unknown catch variables requires explicit runtime type checks using narrowing techniques, such as the instanceof operator or custom type guards.

Using instanceof Error

The most common approach is verifying whether the caught value is an instance of JavaScript's built-in Error class:

try {
  performRiskyOperation();
} catch (error) {
  if (error instanceof Error) {
    console.error(error.message);
    console.error(error.stack);
  } else {
    console.error("An unexpected error occurred:", String(error));
  }
}

Using Type Narrowing Helpers

When working with custom error structures or non-standard payloads, you can write helper functions to safely extract error information:

function getErrorMessage(error: unknown): string {
  if (error instanceof Error) return error.message;
  if (typeof error === "string") return error;
  if (error && typeof error === "object" && "message" in error) {
    return String((error as { message: unknown }).message);
  }
  return "Unknown error";
}

try {
  performRiskyOperation();
} catch (error) {
  console.error(getErrorMessage(error));
}

The TypeScript Configuration Setting

Starting in TypeScript 4.0, catch clause variables could be explicitly annotated as either unknown or any. In TypeScript 4.4, the compiler introduced the useUnknownInCatchVariables flag, which is enabled by default under strict mode.

When enabled, all unannotated catch (error) variables default to unknown rather than any, cementing modern TypeScript's shift toward absolute type safety in exception handling.
