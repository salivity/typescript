Why TypeScript Allows Return Values in Void Callbacks

TypeScript allows functions with a void return type in callback signatures to return arbitrary values to balance practical usability with type safety. While this behavior might initially seem like a loophole in the type system, it is an intentional design choice rooted in function substitutability and common JavaScript idioms. By treating a void callback return type as "the caller will ignore the return value" rather than "the function must return nothing," TypeScript prevents unnecessary boilerplate without introducing runtime errors.

The Semantic Meaning of void in Callbacks

In TypeScript, a return type of void behaves differently depending on whether it is an explicit function declaration or a callback type definition:

  1. Explicit Function Declaration: When you declare a standalone function with an explicit void return type, returning a value is prohibited.

    function logMessage(): void {
  return true; // Error: Type 'boolean' is not assignable to type 'void'.
}

  2. Callback Type Definition: When a function signature defines a callback parameter as returning void (e.g., cb: () => void), it indicates that the caller will not observe, inspect, or rely on any returned value.

    function runCallback(cb: () => void) {
  cb(); // The caller simply executes the callback and ignores whatever it yields.
}

runCallback(() => 42); // Allowed

Preserving Idiomatic JavaScript

The primary motivation for this design is developer ergonomics when using standard JavaScript APIs. Many common built-in methods return values that are frequently ignored.

A classic example is Array.prototype.forEach, which expects a callback returning void:

const numbers = [1, 2, 3];
const numberSet = new Set<number>();

// Set.prototype.add() returns the Set instance itself
numbers.forEach(num => numberSet.add(num));

If TypeScript strictly enforced that () => void could only return undefined, the arrow function num => numberSet.add(num) would produce a type error because it returns Set<number>. Developers would be forced to write verbose curly-brace syntax with an empty return to discard the value:

// Unnecessary boilerplate if strict void were enforced:
numbers.forEach(num => {
  numberSet.add(num);
});

Allowing arbitrary return values permits single-expression arrow functions to remain concise and idiomatic.

Function Substitutability and Type Safety

This behavior aligns with the concept of function substitutability (subtyping). It is always runtime-safe to substitute a function that produces a value in a place where no value is expected.

Because the consuming function treats the result as void, it will not attempt to call methods on or read properties from that return value. Consequently, returning an arbitrary value cannot cause a runtime exception down the call stack.

TypeScript maintains safety by preventing the consumer from using the returned value:

function execute(callback: () => void) {
  const result = callback(); // 'result' is typed as 'void'
  result.toString(); // Error: Property 'toString' does not exist on type 'void'.
}

Enforcing Strict Undefined When Needed

If you strictly require a callback to return nothing other than undefined, you should type the return value as undefined rather than void:

function strictCallback(cb: () => undefined) {
  cb();
}

strictCallback(() => "hello"); // Error: Type 'string' is not assignable to type 'undefined'.
strictCallback(() => undefined); // Allowed

By distinguishing between void (ignore the return value) and undefined (require an explicit undefined return), TypeScript enables both flexibility in general callback handling and strictness when precise control over outputs is required.
