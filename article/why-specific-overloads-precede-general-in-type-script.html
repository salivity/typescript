Why Specific Overloads Precede General in TypeScript

In TypeScript, function overloads are evaluated sequentially from top to bottom, meaning the compiler resolves a function call to the very first overload signature that matches the provided arguments. If a more general overload is placed before a more specific one, the broader signature will eagerly capture the invocation, effectively shadowing and disabling the narrower signature beneath it. Arranging signatures from most specific to most general ensures that callers receive the most accurate return types and strictest argument checking possible.

The Mechanics of Overload Resolution

When you invoke an overloaded function, TypeScript checks the call against each overload signature in the exact order they are declared in the source code. The resolution algorithm halts immediately upon finding the first compatible match. It does not look ahead to see if a later signature offers a more precise fit.

Because TypeScript's type system is based on structural subtyping, broader types naturally encompass narrower types:

  • A literal type like 'submit' is a subtype of string.
  • A specific interface like HTMLInputElement is a subtype of HTMLElement.
  • Any type is a subtype of unknown or any.

If an overload accepting string appears before an overload accepting 'submit', an argument of value 'submit' satisfies the string condition. The compiler selects that first definition and skips the rest.

The Masking Problem in Practice

Consider an event-handling utility where different event names yield different event objects.

Incorrect Ordering (General First)

// Incorrect: The general string signature shadows the specific one
function on(event: string, callback: (e: Event) => void): void;
function on(event: "click", callback: (e: MouseEvent) => void): void;
function on(event: string, callback: (e: any) => void) {
  // implementation
}

// Result:
on("click", (e) => {
  // 'e' is inferred as Event, not MouseEvent!
  // MouseEvent-specific properties like e.clientX will trigger errors.
});

Because "click" is assignable to string, the compiler matches the first signature immediately. The specific "click" overload is rendered unreachable dead code.

Correct Ordering (Specific First)

// Correct: Most specific types appear first
function on(event: "click", callback: (e: MouseEvent) => void): void;
function on(event: string, callback: (e: Event) => void): void;
function on(event: string, callback: (e: any) => void) {
  // implementation
}

// Result:
on("click", (e) => {
  // 'e' is correctly inferred as MouseEvent
});

on("custom-event", (e) => {
  // 'e' falls back to generic Event
});

Here, TypeScript evaluates the "click" signature first. If the argument matches, it uses the precise MouseEvent type. If it does not match, it proceeds downward to the broader string fallback.

Impact on Return Type Inference

The ordering of overloads is equally critical for determining return types. When overloads map specific inputs to specific outputs, misordered signatures cause the compiler to return broadened types.

// Specific first guarantees exact return types
function parse(input: string): string[];
function parse(input: any): unknown;
function parse(input: any): any {
  return typeof input === "string" ? input.split(",") : input;
}

const result = parse("a,b,c"); // Inferred strictly as string[]

If parse(input: any): unknown were placed at the top, parse("a,b,c") would evaluate to unknown, forcing developers to use unnecessary type assertions (as string[]).

Summary of Best Practices

To prevent signature shadowing and maintain precise type inference:

  1. Sort by Narrowness: Place literal types before primitives, derived interfaces before base interfaces, and strict signatures before signatures accepting any or unknown.
  2. Use Broad Signatures as Fallbacks: Reserve generalized signatures for the bottom of the overload list to catch non-specific usage patterns.
  3. Consider Union Types or Generics: If multiple overloads differ only by parameter types and share identical structures, evaluate whether a single generic signature or a discriminated union provides a simpler alternative to function overloading.
