TypeScript Private Identifiers vs Protected Keyword

This article explores the differences between ECMAScript private identifiers (#field) and the TypeScript protected modifier in class inheritance. While both restrict access to class members from external consumers, they serve fundamentally distinct purposes regarding subclass visibility and runtime enforcement. You will learn how their scoping rules, runtime behaviors, and encapsulation models impact object-oriented software design in TypeScript.

The Purpose of the protected Keyword

The protected keyword is a TypeScript-specific access modifier designed specifically for class inheritance. A member marked as protected is accessible within the class that declares it and within any derived subclasses. However, it cannot be accessed from outside the class hierarchy.

Key characteristics of protected:

  • Subclass Visibility: Derived classes inherit the member and can read or modify it directly.
  • Compile-Time Only: Like TypeScript's private keyword, protected exists only during static type checking. Once compiled to JavaScript, the modifier is stripped away, and the property becomes a standard, fully public property at runtime.
  • Intended Use: Creating extensible base classes where subclasses need internal access to helper methods, state, or hooks without exposing those internals to public consumers.

The Purpose of Private Identifiers (#)

Private identifiers (prefixed with #, such as #name) are an ECMAScript standard feature natively supported by JavaScript and TypeScript. They enforce hard encapsulation at both compile time and runtime.

Key characteristics of private identifiers:

  • Strict Class Isolation: A # member is accessible only within the exact body of the class where it is declared. It is completely invisible and inaccessible to derived subclasses.
  • Runtime Enforcement: Encapsulation is guaranteed by the JavaScript engine itself. The property cannot be accessed, overridden, or inspected using standard reflection (like Object.keys() or bracket notation).
  • No Subclass Overriding: A subclass cannot declare a private field with the same name or override it.
  • Intended Use: Securing internal state against tampering and preventing subclasses or external code from depending on internal implementation details.

Comparing Behavior in Inheritance

Feature protected Private Identifier (#field)
Accessible in Subclasses Yes No
Accessible Outside Class No No
Enforcement Layer Compile-time (TypeScript) Compile-time and Runtime (JavaScript)
Runtime Output Standard public property Native private field
Subclass Override Can be overridden or made public Cannot be overridden or shadowed

Code Example

class BaseAccount {
  // Accessible to subclasses, stripped at runtime
  protected balance: number;

  // Accessible ONLY to BaseAccount, enforced at runtime
  #securityToken: string;

  constructor(initialBalance: number, token: string) {
    this.balance = initialBalance;
    this.#securityToken = token;
  }

  validateToken(input: string): boolean {
    return this.#securityToken === input;
  }
}

class SavingsAccount extends BaseAccount {
  applyInterest(rate: number) {
    // Allowed: Subclasses have access to protected members
    this.balance += this.balance * rate;

    // Compile Error: Property '#securityToken' is not accessible outside class 'BaseAccount'
    // console.log(this.#securityToken);
  }
}

const account = new SavingsAccount(1000, "secret-key");

// Compile Error: Property 'balance' is protected
// account.balance; 

// In pure JavaScript output, account.balance is actually accessible:
// (account as any).balance; // Works at runtime!

// Private identifiers cannot be accessed even through escape hatches:
// (account as any).#securityToken; // Syntax error / runtime failure

When to Use Which

Use the protected keyword when designing an inheritance hierarchy that requires shared functionality between base and child classes. It allows you to build an internal API meant exclusively for authors of subclasses.

Use private identifiers (#field) when building components that require absolute data privacy and protection from external interference. If allowing a subclass to view or mutate a field could corrupt the internal state of the base class, a private identifier is the appropriate choice.
