Covariance and Contravariance in TypeScript

This article provides a practical overview of how covariance and contravariance govern type compatibility for function parameters in TypeScript. It explains the theoretical principles of type variance, demonstrates why function parameters are inherently contravariant for type safety, and clarifies how TypeScript behaves under the strictFunctionTypes compiler flag compared to standard method declarations.

Understanding Variance

Variance describes how the subtyping relationship between complex types relates to the subtyping relationship of their underlying components.

Consider a basic hierarchy:

interface Animal {
  name: string;
}

interface Dog extends Animal {
  breed: string;
}

Here, Dog is a subtype of Animal (Dog extends Animal).

  • Covariance: Preserves the direction of the subtyping relationship. If Dog is a subtype of Animal, then Type<Dog> is a subtype of Type<Animal>.
  • Contravariance: Inverts the direction of the subtyping relationship. If Dog is a subtype of Animal, then Type<Animal> is a subtype of Type<Dog>.
  • Bivariance: The type is both covariant and contravariant.
  • Invariance: Neither type can be substituted for the other.

Why Function Parameters Are Contravariant

Return types in functions are covariant, while function parameters are contravariant.

When passing a function as a callback, the consumer determines what arguments will be passed into it. If a consumer expects a function that processes a Dog, passing a function that accepts any generic Animal is completely safe. The function only requires an Animal to do its job, and every Dog satisfies that requirement.

Conversely, passing a function that expects a specific Dog where any general Animal might be provided will lead to a runtime error if a non-dog Animal (like a Cat) is passed.

let processAnimal = (animal: Animal): void => {
  console.log(animal.name);
};

let processDog = (dog: Dog): void => {
  console.log(dog.breed);
};

// Target expects a function that can accept a Dog
let handleDog: (dog: Dog) => void;

// Safe (Contravariant): An Animal handler can safely receive a Dog
handleDog = processAnimal; 

// Target expects a function that can accept ANY Animal
let handleAnimal: (animal: Animal) => void;

// Unsafe: A Dog handler expects 'breed', which a generic Animal lacks
// Type error under strict settings:
handleAnimal = processDog;

Because Animal can be substituted where Dog was expected in the parameter list, the subtyping direction is inverted, making the parameter position contravariant.

TypeScript and strictFunctionTypes

Historically, TypeScript treated function parameters as bivariant (both covariant and contravariant) to maintain compatibility with common JavaScript patterns like event handling and array mutations.

When the strictFunctionTypes flag (or --strict) is enabled:

  1. Function Signatures Become Contravariant: Functions declared as values or object properties strictly enforce contravariance on their parameters.
  2. Method Declarations Remain Bivariant: Methods defined using the shorthand method syntax on interfaces and classes intentionally remain bivariant.
interface Logger {
  // Method syntax: Bivariant
  logMethod(animal: Dog): void;

  // Property syntax: Contravariant (with strictFunctionTypes)
  logProperty: (animal: Dog) => void;
}

The shorthand method exception exists for structural ergonomics with built-in JavaScript types, such as Array<T>, which would otherwise cause assignability errors between Array<Dog> and Array<Animal>. For maximum type safety, function properties with arrow syntax should be preferred over method syntax when defining strict interfaces.
